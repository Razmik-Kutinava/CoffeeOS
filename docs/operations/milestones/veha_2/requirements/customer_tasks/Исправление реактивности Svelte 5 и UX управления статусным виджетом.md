# Исправление реактивности Svelte 5 и UX управления статусным виджетом

**Артефакты:** `docs/operations/milestones/veha_2/artifacts/svelte5_status_widget_reactivity_ux/`  
**CBR:** #63 (доп к #35)  
**Дата интейка:** 2026-08-13

---

Задача: Исправление реактивности Svelte 5 и UX управления статусным виджетом
Бизнес-цель: Обеспечить обновление статуса заказа в PWA в реальном времени без перезагрузки страницы и устранить блокирование интерфейса статусным виджетом при навигации пользователя.
1. Связь с картой интеграций
Затронутые сервисы из @INTEGRATIONS.md: Rails ActionCable / Shop::GuestOrderChannel.
Смежные модули, которые НЕЛЬЗЯ ломать: авторизация гостя, оформление заказа, история заказов, Cart/Checkout flow, Push/SMS-уведомления, существующая подписка на ActionCable.
Внешний контракт ActionCable не изменяется: задача касается обработки уже существующих WS-событий на стороне PWA и управления отображением полученных данных.
2. Разрешенный и Запрещенный Scope
Разрешено менять/создавать:
app/frontend/lib/orderStatusSheet.js
app/frontend/components/OrderStatusSheet.svelte
app/frontend/components/CartSheet.svelte
app/frontend/App.svelte
соответствующие frontend-тесты для TASK-47
Строго запрещено менять:
app/frontend/lib/auth/*
backend ActionCable channels
API/контракты Shop::GuestOrderChannel
модели и миграции БД
логику оформления и оплаты заказа
Push/SMS backend-интеграции
сторонние интеграции и секреты .env
3. Сценарии и Чек-лист (Gherkin)
Subtask 1: Иммутабельное обновление заказа при ActionCable-событии
Given: В state.orders существует активный заказ, а PWA подписана на Shop::GuestOrderChannel.
When: В applyCableEvent приходит WS-событие с новым статусом существующего заказа.
Then: Заказ обновляется через создание нового массива (map/эквивалент без in-place мутации), ссылка на state.orders изменяется, Svelte 5 выполняет re-render без F5.
Subtask 2: Иммутабельная синхронизация заказов
Given: sync получает актуальный список заказов.
When: Выполняется синхронизация состояния state.orders.
Then: Состояние заменяется иммутабельно, а UI отображает актуальный список без перезагрузки страницы.
Subtask 3: Удаление завершенного заказа без мутации массива
Given: В state.orders присутствует заказ со статусом issued или closed.
When: Обрабатывается соответствующее WS-событие.
Then: Заказ удаляется через создание нового массива (filter/эквивалент), а UI автоматически обновляется.
Subtask 4: Проверка zero-refresh обновления статуса
Given: Открыт PWA с активным заказом в статусе preparing.
When: Бариста переводит заказ в ready.
Then: PWA отображает ready без F5 и без повторной инициализации страницы; обновление происходит в пределах целевого UX SLA < 300 мс после получения WS-события.
Subtask 5: Добавление ручного закрытия статусного виджета
Given: Статусный виджет отображается пользователю.
When: Пользователь нажимает кнопку X.
Then: Виджет плавно скрывается, а для соответствующего заказа сохраняется userDismissed: true.
Subtask 6: Сохранение ActionCable-подписки после закрытия виджета
Given: Пользователь закрыл статусный виджет через X.
When: ActionCable отправляет новое событие изменения статуса заказа.
Then: Событие принимается, данные заказа обновляются в состоянии, но закрытый пользователем виджет не открывается повторно поверх интерфейса.
Subtask 7: Отображение виджета на главном экране
Given: У гостя существует активный заказ и пользователь находится на главном экране каталога/категорий.
When: Статусный виджет рендерится.
Then: Виджет отображается по умолчанию и не требует дополнительного действия пользователя.
Subtask 8: Автоматическое скрытие при переходе в карточку товара
Given: Статусный виджет отображается на главном экране.
When: Пользователь переходит на #/product/:id.
Then: Виджет автоматически скрывается или сворачивается до минимального индикатора и не перекрывает контент карточки товара.
Subtask 9: Автоматическое скрытие при переходе в профиль
Given: Статусный виджет отображается на главном экране.
When: Пользователь переходит на #/profile.
Then: Виджет автоматически скрывается или сворачивается и не блокирует элементы профиля.
Subtask 10: Автоматическое скрытие во время оплаты/внешних свайпов
Given: Пользователь взаимодействует с экраном оплаты или выполняет переход/свайп, при котором статусный виджет мешает основному контенту.
When: Активируется соответствующее состояние навигации/UI.
Then: Виджет скрывается или сворачивается, освобождая интерактивную область.
Subtask 11: Обработка ready после ручного закрытия
Given: Заказ находится в активном состоянии, пользователь ранее закрыл его виджет через X.
When: Заказ получает статус ready.
Then: Фоновое обновление статуса выполняется, Push/SMS остаются независимыми от UI, а статусный виджет не всплывает повторно поверх текущего экрана.
Subtask 12: Возврат актуального статуса в истории заказов
Given: Пользователь закрыл виджет, а заказ после этого изменил статус.
When: Пользователь открывает историю заказов.
Then: В истории отображается последний полученный статус заказа независимо от userDismissed.
Subtask 13: Удаление заказа после issued/closed
Given: Активный заказ присутствует в state.orders.
When: ActionCable сообщает статус issued или closed.
Then: Заказ удаляется из массива активных заказов иммутабельным способом и больше не отображается как активный виджет.
Subtask 14: Сохранение userDismissed для конкретного заказа
Given: У пользователя несколько активных заказов.
When: Пользователь закрывает виджет одного конкретного заказа.
Then: userDismissed применяется только к этому заказу и не скрывает статусные виджеты остальных заказов.
Subtask 15: Регрессионные тесты навигации и видимости
Given: Существует активный заказ и доступна статусная модель.
When: Пользователь последовательно переходит между каталогом, карточкой товара, профилем и оплатой.
Then: Виджет соблюдает заданную модель видимости, навигация и основной контент остаются интерактивными, ActionCable-подписка не разрывается.
Subtask 16: Проверка frontend-тестов и типов
Given: Все изменения TASK-47 реализованы.
When: Запускаются тесты задачи, линтер и TypeScript-проверка.
Then: Все проверки завершаются без ошибок и регрессий.
