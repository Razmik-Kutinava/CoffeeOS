# Интеграция оплаты СБП (Deep Link) и токенизации карт (Т-Касса v2) в PWA CODE:BLACK

Бизнес-цель: Обеспечить бесшовную оплату в 2 тапа через СБП и повторные платежи в 1 тап через токенизированные карты, сохраняя строгую монохромную/терминальную эстетику CODE:BLACK без использования стандартных виджетов Т-Банка.

## Глобальные ограничения
- Запрещено использовать стандартный iframe/UI-виджет Т-Банка.
- Запрещено хранить `RebillId`, `CustomerKey` или платежные данные в открытом виде/локальном стейте без привязки к защищенному контексту пользователя.
- Запрещено изменять структуру массива `Receipt` (Items, Taxation), нарушающую требования 54-ФЗ.
- Запрещено хардкодить `Password` / `SecretKey` для генерации SHA-256 подписи (использовать только env-переменные).
- Запрещено оставлять UI в состоянии бесконечной загрузки (Loading) при разрыве соединения или отмене платежа пользователем.

## Сценарии и чек-лист (Для todo.md)
Каждый пункт `- [ ]` — атомарный таск для TDD-цикла (сначала тест, потом код).

### Сценарий 1: Инициализация и получение ссылки СБП (Backend)
- [ ] Шаг 1: Реализовать и протестировать `/v2/Init` с корректной сборкой чека 54-ФЗ
  - Given: Валидный `order_id`, `Amount` (в копейках), массив `Items`, `Taxation`, `CustomerKey`.
  - When: Вызывается внутренний метод инициации платежа Т-Кассы.
  - Then: Формируется корректный payload, возвращается `PaymentId`. При ошибке валидации (400) или сбое API (500) возвращается стандартизированная ошибка.
- [ ] Шаг 2: Реализовать и протестировать `/v2/GetQr` для получения Deep Link
  - Given: Валидный `PaymentId` из Шага 1.
  - When: Вызывается метод с `DataType="PAYMENT_LINK"`.
  - Then: Возвращается объект с `Data` (ссылка вида `https://qr.nspk.ru/...`). Обработка 400/500 ошибок API Т-Кассы.
- [ ] Шаг 3: Реализовать endpoint `POST /api/v1/payments/sbp/init`
  - Given: Запрос от Frontend с `order_id`.
  - When: Backend последовательно вызывает `/v2/Init` и `/v2/GetQr`.
  - Then: Возвращает `{ payment_url }`. При сетевом сбое возвращает 500 с логированием.

### Сценарий 2: Обработка Webhook и проверка статуса (Backend)
- [ ] Шаг 4: Реализовать валидацию SHA-256 подписи Webhook
  - Given: Входящий payload Webhook от Т-Кассы и `SecretKey`.
  - When: Вычисляется подпись (сортировка ключей по алфавиту + конкатенация с `SecretKey` + SHA-256).
  - Then: При несовпадении подписи возвращается HTTP 403 Forbidden. При совпадении — обработка продолжается.
- [ ] Шаг 5: Реализовать endpoint `POST /api/v1/payments/webhook`
  - Given: Валидно подписанный Webhook со статусом `CONFIRMED`, `AUTHORIZED`, `REJECTED` или `CANCELED`.
  - When: Backend получает запрос.
  - Then: Обновляет статус заказа в БД, возвращает HTTP 200 OK. Реализована идемпотентность (повторные вебхуки не ломают состояние).
- [ ] Шаг 6: Реализовать endpoint `GET /api/v1/payments/status/:order_id` (Fallback)
  - Given: `order_id`.
  - When: Frontend запрашивает статус (Long Polling / ручной вызов).
  - Then: Возвращается актуальный статус заказа из БД. При отсутствии заказа — 404.

### Сценарий 3: Оплата картой и токенизация (Backend)
- [ ] Шаг 7: Реализовать первичную привязку карты (Recurrent)
  - Given: Запрос на оплату картой с флагом сохранения.
  - When: Вызывается `/v2/Init` с параметром `Recurrent="Y"`.
  - Then: При успешном Webhook (`CONFIRMED`) извлекается `RebillId` и сохраняется в БД в связке с `CustomerKey`.
- [ ] Шаг 8: Реализовать повторную оплату (Charge)
  - Given: `CustomerKey`, привязанный `RebillId`, новый `order_id` и `Amount`.
  - When: Вызывается метод `/v2/Charge` API Т-Кассы.
  - Then: Платеж проходит без ввода данных карты. Обработка ошибок (невалидный токен, 400/500).

### Сценарий 4: UI/UX PWA (Frontend, стиль CODE:BLACK)
- [ ] Шаг 9: Реализовать компонент кнопки «Оплатить быстро» (СБП)
  - Given: Корзина оформлена, пользователь на экране оплаты.
  - When: Пользователь нажимает «Оплатить быстро».
  - Then: Вызывается `POST /api/v1/payments/sbp/init`, UI переходит в состояние Loading (монохромный индикатор). При успехе выполняется `window.location.href = payment_url`. При 400/500 — показывается терминальная ошибка.
- [ ] Шаг 10: Реализовать компонент отображения привязанной карты и оплаты в 1 тап
  - Given: У пользователя есть сохраненная карта (`RebillId`).
  - When: Отображается UI с маской `**** 1234` и кнопкой оплаты.
  - Then: При нажатии вызывается endpoint повторной оплаты. UI показывает Loading. Обработка 400 (токен устарел) с предложением привязать карту заново.
- [ ] Шаг 11: Реализовать обработку возврата из банковского приложения и Polling
  - Given: Пользователь вернулся в PWA после редиректа на `nspk.ru` (или отменил платеж).
  - When: Компонент монтируется/активируется.
  - Then: Автоматически запускается polling `GET /api/v1/payments/status/:order_id`. При статусе `CONFIRMED` — показывается финишный экран успеха. При `CANCELED`/`REJECTED` или таймауте polling — показывается экран «Оплата не завершена, попробовать снова». Бесконечный Loading запрещен.

## Стратегия тестирования
- **Фреймворк**: 
  - Backend: Jest (или аналогичный, используемый в проекте) + Supertest для API.
  - Frontend: Vitest + React Testing Library.
- **Путь к файлам тестов**: 
  - Backend: `backend/src/modules/payments/__tests__/`
  - Frontend: `frontend/src/features/payment/__tests__/`
- **Критические кейсы**:
  - Edge cases: Специальные символы в названиях товаров для 54-ФЗ чека (экранирование).
  - Лимиты времени: Таймаут polling на фронтенде (макс. 60 секунд, интервал 2 сек).
  - Асинхронность: Идемпотентность обработки Webhook (двойной вызов с одним `PaymentId` не должен создавать дубликаты транзакций в БД).
  - Безопасность: Тест на подделку SHA-256 подписи (должен строго возвращать 403).

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус, покрытие критического пути ≥ 80%).
2. Линтер (ESLint) и тайпчекер (tsc) выполняются без ошибок и предупреждений.
3. Ручная проверка чек-листа из исходного ТЗ: ссылка `qr.nspk.ru` валидна, триггер системного выбора банка на iOS/Android работает, `RebillId` успешно применяется для `/v2/Charge`.
