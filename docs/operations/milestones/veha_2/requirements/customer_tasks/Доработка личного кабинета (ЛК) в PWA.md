# Задача: Доработка личного кабинета (ЛК) в PWA

**CBR:** #69 · **Дата intake:** 2026-08-26  
**Артефакты:** `docs/operations/milestones/veha_2/artifacts/pwa_personal_account_lk/`

---

Задача: Доработка личного кабинета (ЛК) в PWA
Бизнес-цель: завершить пользовательский сценарий личного кабинета в PWA: просмотр истории заказов, просмотр деталей заказа, управление профилем и контактами, переход к юридической информации и информации о приложении. UI и UX должны соответствовать приложенным макетам и UX-референсам, без самостоятельного изобретения новых паттернов.
1. Связь с картой интеграций
Затронутые сервисы из @INTEGRATIONS.md: на текущем этапе новые внешние интеграционные контракты не добавляются.
Backend-контракты, требующие уточнения: API истории заказов, API изменения профиля, API/механика подтверждения email, API/механика подтверждения телефона, API управления уведомлениями, logout.
Внешние ссылки: экран «О нас» использует конфигурационный список URL; на текущем этапе ссылки ведут на Google Docs.
Смежные модули, которые НЕЛЬЗЯ ломать: авторизация и текущая сессия пользователя, существующий routing PWA, существующая система заказов, существующие платежные сценарии, существующие push/notification-механизмы, существующие UI-компоненты bottom sheet.
2. Разрешенный и Запрещенный Scope
Разрешено менять/создавать:
src/**/profile/*
src/**/account/*
src/**/personal-account/*
src/**/orders/* — только части, необходимые для отображения истории и деталей заказа
src/**/components/** — только новые/адаптируемые компоненты ЛК
src/**/config/** — конфигурация ссылок экрана «О нас»
src/**/routes/** — только маршруты экранов ЛК, деталей заказа и «О нас»
tests/** — тесты новой функциональности TASK-[НОМЕР]
Фактические пути должны быть адаптированы под структуру существующего репозитория после её проверки.
Строго запрещено менять:
src/**/auth/** — кроме необходимого вызова уже существующего logout-контракта
платежные модули и checkout
интеграцию ОФД банка
реализацию PLG-механик
подписку/реферальную программу
prisma/schema.prisma и структуру БД без отдельной задачи
существующие payment/webhook-контракты
существующие Telegram/Instagram/WebView-интеграции
глобальные дизайн-токены и базовые UI-компоненты без необходимости, подтвержденной существующей архитектурой
3. Сценарии и Чек-лист (Gherkin)
Subtask 1: Создать маршрут и базовый экран главного ЛК
Given: пользователь авторизован в PWA
When: пользователь открывает раздел личного кабинета
Then: отображается экран ЛК с шапкой, аватаром, именем и иконкой чата/уведомлений; существующая авторизация и routing не изменяются.
Subtask 2: Реализовать шапку ЛК с данными текущего пользователя
Given: текущий пользователь авторизован и его профиль доступен приложению
When: открывается главный экран ЛК
Then: имя и аватар отображаются из данных пользователя; при отсутствии аватара используется существующий fallback.
Subtask 3: Добавить контейнер PLG-блоков без бизнес-логики
Given: главный экран ЛК открыт
When: пользователь видит область под шапкой
Then: присутствуют две зарезервированные области под будущие маркетинговые блоки; контент не хардкодится и никакой PLG-логики не выполняется.
Subtask 4: Подготовить интерфейс конфигурации PLG-блоков
Given: PLG-контент в текущей итерации отсутствует
When: компонент маркетинговой секции инициализируется
Then: компонент принимает/предусматривает конфигурацию сущностей с данными изображения, CTA и ссылки, но не делает запросов и не содержит конкретного маркетингового контента.
Subtask 5: Подключить получение истории заказов
Given: существует согласованный backend API истории заказов
When: пользователь открывает главный экран ЛК
Then: PWA запрашивает историю заказов по согласованному контракту и отображает полученные данные; формат запроса и ответа фиксируется тестом.
Subtask 6: Отобразить элемент истории заказа
Given: API вернул хотя бы один заказ
When: список истории отображается
Then: каждый элемент содержит номер заказа, название, дату и кнопку «Повторить».
Subtask 7: Обработать пустую историю заказов
Given: API истории заказов вернул пустой список
When: пользователь открывает ЛК
Then: отображается предусмотренное макетами состояние пустого списка без ошибки приложения.
Subtask 8: Обработать ошибку загрузки истории заказов
Given: API истории заказов недоступен или возвращает ошибку 4xx/5xx
When: PWA пытается загрузить историю
Then: отображается состояние ошибки согласно существующему UX-паттерну приложения; приложение не падает и остальные элементы ЛК остаются доступными.
Subtask 9: Создать маршрут экрана деталей заказа
Given: пользователь находится в истории заказов
When: пользователь нажимает на «Повторить» у конкретного заказа
Then: открывается экран деталей соответствующего заказа с сохранением идентификатора заказа в маршруте/состоянии.
Subtask 10: Реализовать структуру экрана деталей заказа по UX-референсу
Given: экран деталей заказа открыт
When: пользователь просматривает экран
Then: отображаются дата, название продукта, позиции и суммы в структуре, соответствующей приложенному UX-референсу; используются существующие UI-паттерны проекта.
Subtask 11: Реализовать визуальное состояние деталей заказа без интеграции ОФД
Given: данные ОФД банка в текущей задаче недоступны
When: открывается экран деталей
Then: экран полностью сверстан и способен отображать подготовленные/заглушечные данные без вызова ОФД API.
Subtask 12: Добавить кликабельную кнопку «ПОВТОРИТЬ» без бизнес-логики
Given: экран деталей заказа открыт
When: пользователь нажимает «ПОВТОРИТЬ»
Then: нажатие обрабатывается без реального повторного оформления заказа; допускается пустой обработчик или переход в существующую заглушку.
Subtask 13: Запретить подключение ОФД в рамках текущей реализации
Given: разработка экрана деталей заказа выполняется в рамках TASK-[НОМЕР]
When: реализуется получение данных деталей
Then: код не выполняет запросы к интеграции ОФД банка и не изменяет существующий ОФД-контракт.
Subtask 14: Создать экран профиля/настроек
Given: пользователь авторизован
When: пользователь открывает настройки ЛК
Then: отображаются имя, кнопка «Сохранить», настройка уведомлений и блок контактов.
Subtask 15: Реализовать редактирование имени
Given: в профиле отображается текущее имя пользователя
When: пользователь изменяет имя и нажимает «Сохранить»
Then: выполняется согласованный запрос изменения профиля и после успешного ответа отображается сохраненное имя; при ошибке пользователь получает состояние ошибки.
Subtask 16: Реализовать состояние тумблера уведомлений
Given: согласовано, за какую настройку отвечает тумблер
When: пользователь изменяет состояние тумблера
Then: состояние сохраняется через существующий/согласованный механизм уведомлений; при ошибке UI возвращается к подтвержденному состоянию.
Subtask 17: Реализовать блок контактов
Given: профиль пользователя содержит email и телефон
When: пользователь открывает настройки
Then: email и телефон отображаются отдельно, каждый с собственной кнопкой «Подтвердить».
Subtask 18: Реализовать запуск подтверждения email
Given: согласован backend-флоу подтверждения email
When: пользователь нажимает «Подтвердить» рядом с email
Then: запускается согласованный флоу подтверждения; конкретный способ — код или ссылка — определяется backend-контрактом.
Subtask 19: Реализовать запуск подтверждения телефона
Given: согласован backend-флоу подтверждения телефона
When: пользователь нажимает «Подтвердить» рядом с телефоном
Then: запускается согласованный флоу подтверждения через SMS/код либо другой утвержденный механизм.
Subtask 20: Реализовать переход «О нас»
Given: пользователь находится в настройках
When: нажимает «О нас»
Then: открывается экран «О нас».
Subtask 21: Реализовать bottom sheet «Написать нам»
Given: пользователь находится в настройках
When: нажимает «Написать нам»
Then: открывается bottom sheet с двумя вариантами связи: email и Telegram-бот.
Subtask 22: Реализовать переход в Telegram-бота
Given: bottom sheet «Написать нам» открыт
When: пользователь выбирает Telegram
Then: открывается настроенная ссылка Telegram-бота через существующий механизм внешних ссылок.
Subtask 23: Реализовать email-сценарий обратной связи
Given: согласован способ связи по email
When: пользователь выбирает email в bottom sheet
Then: выполняется согласованный сценарий — открытие почтового клиента либо внутренней формы; email получателя не хардкодится в UI-компоненте.
Subtask 24: Реализовать logout
Given: пользователь авторизован
When: пользователь нажимает «ВЫХОД» и подтверждает действие, если такое подтверждение предусмотрено текущим UX
Then: выполняется существующий logout-механизм и пользователь перенаправляется на согласованный экран логина/онбординга.
Subtask 25: Создать экран «О нас»
Given: пользователь открыл экран «О нас»
When: экран загружается
Then: отображаются версия приложения, код сборки, кнопка «Скопировать информацию», список юридических/информационных ссылок и footer.
Subtask 26: Реализовать копирование версии и build-кода
Given: экран «О нас» открыт и браузер предоставляет Clipboard API
When: пользователь нажимает «Скопировать информацию»
Then: версия и код сборки копируются в буфер обмена; UI показывает существующее в проекте состояние успешного действия.
Subtask 27: Вынести ссылки экрана «О нас» в конфигурацию
Given: список ссылок предоставлен
When: компонент экрана «О нас» строит список
Then: URL берутся из конфигурации/констант, а не из JSX/Svelte-разметки; изменение URL не требует изменения структуры компонента.
Subtask 28: Добавить все пункты информационных ссылок
Given: конфигурация URL заполнена
When: пользователь открывает экран «О нас»
Then: доступны ссылки на политику обработки персональных данных, пользовательское соглашение, публичную оферту, полные правила акций, калорийность и состав, программу благодарности.
Subtask 29: Реализовать footer экрана «О нас»
Given: экран «О нас» открыт
When: пользователь достигает нижней части экрана
Then: отображаются копирайт/название юридического лица и email обратной связи из конфигурации.
Subtask 30: Проверить соответствие UI макетам и UX-референсам
Given: все экраны ЛК реализованы
When: выполняется визуальная проверка
Then: структура, spacing, карточки, списки, кнопки, bottom sheet и экран деталей заказа соответствуют предоставленным макетам и референсам без самостоятельного изменения UX-паттернов.
Subtask 31: Проверить отсутствие функциональности вне Scope
Given: функциональность ЛК реализована
When: выполняется регрессионная проверка
Then: отсутствуют вызовы ОФД, PLG-бизнес-логика, подписка и реферальная программа.
4. Команды TDD-проверки
Запуск тестов: npm test tests/integration/TASK-[НОМЕР].test.ts
Проверка типов: npx tsc --noEmit
Проверка production-сборки PWA: команда сборки, используемая текущим репозиторием.
Дополнительно: выполнить визуальную проверку экранов ЛК по приложенным макетам и UX-референсам.
5. Открытые вопросы / блокирующие зависимости
До реализации соответствующих subtasks необходимо получить:
API истории заказов: endpoint, метод, формат request/response, pagination и идентификатор заказа.
Контракт сохранения имени пользователя.
Семантику тумблера уведомлений и существующий backend/API-контракт.
Флоу подтверждения email: код или ссылка, endpoint, состояния pending/confirmed/error.
Флоу подтверждения телефона: SMS/код, endpoint и обработка ошибок.
Сценарий email через «Написать нам»: системный почтовый клиент или внутренняя форма.
Точное поведение logout и целевой экран после выхода.
Финальный список Google Docs URL.
Ссылка Telegram-бота.
Название юридического лица и email обратной связи.
UX-референсы и макеты, являющиеся источником истины для визуальной реализации.
