# Задача: Устранение утечки данных чужой карты при привязке

**Артефакты:** `docs/operations/milestones/veha_2/artifacts/card_binding_unique_hash/`  
**Группа:** security review (задача 1)

Задача: Устранение утечки данных чужой карты при привязке

Бизнес-цель: исключить возможность привязки одной банковской карты к нескольким аккаунтам и предотвратить раскрытие `card_masked`, банка-эмитента и других признаков чужой карты. Решение должно быть защищено на уровне БД от race condition при параллельных запросах.

## 1. Связь с картой интеграций

- **Затронутые сервисы из `@INTEGRATIONS.md`:** текущий платёжный/эквайринговый контур, через который формируется `card_token`.
- **Смежные модули, которые НЕЛЬЗЯ ломать:** авторизация и регистрация пользователей, существующий платёжный flow, существующие привязанные карты внутри одного аккаунта, история платежей.
- **Внешний сервис не должен получать информацию о внутренних причинах отказа.**

## 2. Разрешенный и Запрещенный Scope

- **Разрешено менять/создавать:**
  - `app/services/payments/saved_card_store.rb`
  - модель/репозиторий `mobile_payment_methods`
  - миграции БД, относящиеся только к `mobile_payment_methods`
  - data-migration для поиска и деактивации существующих дубликатов
  - `spec/services/payments/*`
  - `spec/models/*`
  - `spec/requests/*` или соответствующий существующий integration-test слой
- **Строго запрещено менять:**
  - `app/modules/auth/*`
  - регистрацию и OTP-flow, не связанный непосредственно с обработкой отказа привязки
  - платёжные API-контракты, не относящиеся к результату привязки карты
  - историю заказов и платежей
  - маркетинговое согласие
  - фронтенд UX, кроме минимально необходимого изменения сериализации отказа
  - сторонние интеграции вне существующего payment/card-binding flow

## 3. Сценарии и Чек-лист (Gherkin)

- [ ] **Subtask 1: Добавить стабильный `card_hash` для привязки карты**
  - Given: существует `mobile_payment_method` с идентификатором карты от эквайринга
  - When: система создаёт или обновляет привязку
  - Then: рассчитывается стабильный `card_hash`, пригодный для глобальной идентификации одной карты; исходный `card_token` не выводится пользователю

- [ ] **Subtask 2: Добавить `card_hash` в `mobile_payment_methods`**
  - Given: таблица `mobile_payment_methods` не содержит глобального идентификатора карты
  - When: применяется миграция
  - Then: таблица содержит nullable `card_hash` на период миграции существующих данных

- [ ] **Subtask 3: Найти существующие дубликаты карт**
  - Given: в БД могут существовать активные привязки одного `card_hash` к нескольким аккаунтам
  - When: запускается data-migration в dry-run режиме
  - Then: все группы потенциальных дубликатов находятся и формируется отчёт без изменения данных

- [ ] **Subtask 4: Деактивировать существующие дубликаты**
  - Given: dry-run подтвердил дубликаты одной карты между несколькими аккаунтами
  - When: выполняется data-migration
  - Then: конфликтующие лишние привязки деактивируются по заранее определённому детерминированному правилу, а исходные данные и результат операции журналируются

- [ ] **Subtask 5: Создать уникальность активного `card_hash` на уровне БД**
  - Given: существующие дубликаты устранены
  - When: применяется финальный DB constraint/index
  - Then: одновременно активными не могут быть две записи с одинаковым `card_hash`

- [ ] **Subtask 6: Обработать нарушение DB constraint как контролируемый отказ**
  - Given: `card_hash` уже активен у другого аккаунта
  - When: новый аккаунт пытается создать привязку
  - Then: исключение unique constraint перехватывается, API возвращает нейтральный результат отказа, HTTP 500 не возникает

- [ ] **Subtask 7: Исключить данные чужой карты из ответа**
  - Given: привязка отклонена из-за занятого `card_hash`
  - When: API формирует response
  - Then: response не содержит `card_masked`, BIN, банк-эмитент, `card_token`, `card_hash` или идентификатор владельца

- [ ] **Subtask 8: Зафиксировать race condition тестом**
  - Given: два разных аккаунта одновременно пытаются привязать один `card_hash`
  - When: запросы выполняются параллельно
  - Then: ровно одна привязка становится активной, второй запрос получает контролируемый отказ
