# Задача: Привязка способа оплаты и промо 11₽

**CBR:** #75 · **Дата intake:** 2026-09-04  
**Артефакты:** `docs/operations/milestones/veha_2/artifacts/payment_method_binding_promo_11rub/`  
**Группа:** эквайринг / PWA (задача 1 из 3)

---

Задача: Привязка способа оплаты и промо 11₽

Бизнес-цель: реализовать единую механику сохранения способа оплаты для карты и СБП как побочного эффекта первого заказа, при которой пользователь с включённым чекбоксом оплачивает 11₽ вместо полной суммы корзины. Одновременно закрыть возможность привязки одного и того же способа оплаты к нескольким аккаунтам, добавить антифрод-контроль, аудит попыток и единое правило дедупликации промо.

## 1. Связь с картой интеграций

- **Затронутые сервисы из `@INTEGRATIONS.md`:**
  - Т-Банк — карточная оплата, Init/Recurrent, `card_token` / RebillId.
  - Т-Банк СБП — bind/autopay через `RequestKey` / `AccountToken`.
  - SMS/OTP-провайдер — только существующий step-up flow.
- **Смежные модули, которые НЕЛЬЗЯ ломать:**
  - обычная оплата полной стоимости корзины;
  - существующий checkout;
  - существующие сохранённые карты;
  - существующая привязка СБП;
  - callback/webhook обработка платежей;
  - история заказов;
  - возвраты;
  - существующая авторизация и OTP;
  - существующий antifraud flow, не относящийся к новой проверке привязки.

## 2. Разрешенный и Запрещенный Scope

- **Разрешено менять/создавать:**
  - модуль сохранённых способов оплаты;
  - модуль payment method binding;
  - модуль промо/11₽;
  - модуль antifraud/velocity;
  - существующие payment service/use-case, отвечающие за динамическую сумму первого платежа;
  - миграции/индексы БД, необходимые для защиты `method_hash`;
  - таблицу/репозиторий `card_binding_attempts` с расширением до card/sbp;
  - backend-тесты payment/binding/antifraud/promo;
  - PWA-компоненты экрана выбора способа оплаты;
  - PWA-тексты и состояния блока промо.
- **Строго запрещено менять:**
  - auth/login/session flow;
  - пользовательский профиль вне необходимых полей для проверки телефона аккаунта;
  - бизнес-логику истории заказов;
  - cashback/loyalty;
  - существующие внешние webhook-контракты без отдельного согласования;
  - платёжный flow внутри банка после redirect/deep-link;
  - секреты и ключи интеграций;
  - существующие схемы платежей, не относящиеся к динамической сумме и сохранению способа оплаты.

## 3. Сценарии и Чек-лист (Gherkin)

- [ ] **Создать стабильный `method_hash` для карточного способа оплаты**
  - Given: получен существующий `card_token`/RebillId.
  - When: система определяет способ оплаты для сохранения.
  - Then: создаётся стабильный `card_hash`, который не содержит PAN/чувствительные данные и используется для дедупликации.

- [ ] **Создать стабильный `method_hash` для СБП**
  - Given: СБП возвращает `AccountToken`/`RequestKey`.
  - When: способ оплаты сохраняется.
  - Then: система создаёт стабильный хэш идентификатора СБП без хранения открытого токена в поле дедупликации.

- [ ] **Добавить тип способа оплаты к записи сохранённого метода**
  - Given: сохранённый способ оплаты может быть картой или СБП.
  - When: запись сохраняется.
  - Then: запись однозначно содержит `method_type = card | sbp` и соответствующий `method_hash`.

- [ ] **Запретить повторную привязку одного карточного способа оплаты к другому аккаунту на уровне БД**
  - Given: способ оплаты с тем же `method_hash` уже принадлежит `account_id=A`.
  - When: `account_id=B` пытается создать запись.
  - Then: БД отклоняет дубликат уникальным constraint/index независимо от конкурентности запросов.

- [ ] **Запретить повторную привязку одного СБП-способа оплаты к другому аккаунту на уровне БД**
  - Given: СБП-способ с тем же `method_hash` уже принадлежит `account_id=A`.
  - When: `account_id=B` пытается создать запись.
  - Then: БД отклоняет дубликат уникальным constraint/index.

- [ ] **Защитить дедупликацию от race condition**
  - Given: два аккаунта одновременно пытаются сохранить один способ оплаты.
  - When: запросы выполняются конкурентно.
  - Then: только одна операция создаёт запись; вторая получает контролируемый результат без утечки данных владельца.

- [ ] **Не возвращать данные занятого способа оплаты**
  - Given: способ оплаты уже привязан к другому аккаунту.
  - When: текущий пользователь пытается его сохранить.
  - Then: API возвращает безопасную ошибку без `account_id`, телефона, `card_hash`, токена или иных данных владельца.

- [ ] **Обработать ожидаемое нарушение уникального constraint**
  - Given: конкурентный запрос выиграл гонку и создал запись первым.
  - When: второй запрос получает DB unique violation.
  - Then: приложение преобразует её в штатный `blocked_method_taken`, а не в HTTP 500.

- [ ] **Провести аудит существующих дублей**
  - Given: в БД существуют исторические записи сохранённых карт/СБП.
  - When: выполняется audit/migration script.
  - Then: выявляются все дубли по стабильному идентификатору способа оплаты с разделением по `method_type`.

- [ ] **Деактивировать существующие дубли без удаления истории**
  - Given: audit обнаружил несколько активных владельцев одного способа оплаты.
  - When: выполняется процедура нормализации.
  - Then: сохраняется один валидный владелец, остальные конфликтующие записи деактивируются с audit trail.

- [ ] **Добавить тип способа оплаты в журнал попыток привязки**
  - Given: пользователь выполняет попытку привязки карты или СБП.
  - When: создаётся `card_binding_attempts`.
  - Then: запись содержит `method_type`, `method_hash`, `phone`, `account_id`, `device_fingerprint`, `ip`, `bin` при наличии, `point_id`, `result`, `reason`, `verification_charge_required`, `is_growth_event`, `created_at`.

- [ ] **Сделать `method_hash` основным идентификатором попытки**
  - Given: выполняется попытка карты или СБП.
  - When: создаётся audit record.
  - Then: логика не зависит от поля с названием `card_hash`; для карты используется card hash, для СБП — SBP method hash.

- [ ] **Реализовать velocity по `card_hash`**
  - Given: выполняются повторные карточные попытки.
  - When: количество попыток превышает установленный лимит.
  - Then: новая попытка получает `rate_limited` и не выполняет дальнейшую привязку.

- [ ] **Реализовать velocity по телефону**
  - Given: один телефон используется для большого числа попыток привязки.
  - When: превышен лимит.
  - Then: попытка блокируется с `rate_limited`.

- [ ] **Реализовать velocity по device fingerprint/IP**
  - Given: с одного device fingerprint/IP выполняется аномальное число попыток.
  - When: превышен лимит.
  - Then: новая попытка блокируется без раскрытия внутренних antifraud-признаков.

- [ ] **Реализовать карточный velocity по BIN**
  - Given: большое количество карточных попыток относится к одному BIN.
  - When: превышен лимит card testing.
  - Then: попытка блокируется как antifraud event.

- [ ] **Не применять BIN-проверку к СБП**
  - Given: пользователь сохраняет способ оплаты через СБП.
  - When: выполняется velocity.
  - Then: BIN-check не вызывается; используются применимые для СБП признаки, в первую очередь phone/device/IP.

- [ ] **Ввести явный `phone_status`**
  - Given: аккаунт имеет телефон с определённым состоянием.
  - When: antifraud определяет необходимость step-up.
  - Then: используется enum `phone_status`, а не проверка через `NULL`.

- [ ] **Использовать телефон аккаунта для step-up OTP**
  - Given: требуется дополнительное подтверждение.
  - When: запускается OTP.
  - Then: SMS отправляется на телефон, сохранённый в аккаунте, независимо от значения телефона в текущей форме.

- [ ] **Не доверять телефону из формы при step-up**
  - Given: пользователь изменил телефон в client request.
  - When: требуется OTP.
  - Then: введённый в форме номер не используется для адресации OTP.

- [ ] **Определять доступность промо до создания платежа**
  - Given: пользователь оформляет первый заказ с включённым чекбоксом.
  - When: backend проверяет eligibility.
  - Then: промо доступно только если точка разрешает промо, лимиты не исчерпаны и пользователь не использовал право ранее.

- [ ] **Дедуплицировать промо по телефону**
  - Given: ранее была успешная growth-привязка с `is_growth_event = true` для телефона пользователя.
  - When: создаётся новый заказ.
  - Then: промо 11₽ не предлагается независимо от выбранного способа оплаты.

- [ ] **Дедуплицировать промо по `method_hash`**
  - Given: конкретный способ оплаты уже участвовал в успешном growth event.
  - When: пользователь повторно выбирает этот способ.
  - Then: промо не предлагается.

- [ ] **Запретить получение промо дважды через разные способы**
  - Given: пользователь уже получил 11₽ через СБП.
  - When: он выбирает карту.
  - Then: карта оплачивается по полной цене, промо повторно не показывается.

- [ ] **Запретить получение промо дважды в обратном направлении**
  - Given: пользователь уже получил 11₽ через карту.
  - When: он выбирает СБП.
  - Then: промо повторно не показывается.

- [ ] **Не тратить право на промо при отказе от чекбокса**
  - Given: промо доступно, чекбокс включён по умолчанию.
  - When: пользователь выключает чекбокс и оплачивает полную стоимость.
  - Then: `is_growth_event` не создаётся как успешное использование промо; право сохраняется для следующего заказа.

- [ ] **Рассчитать сумму 11₽ при включённом чекбоксе**
  - Given: промо доступно и пользователь выбрал сохранение способа оплаты.
  - When: создаётся платёж.
  - Then: сумма единственного платежа равна 11₽.

- [ ] **Рассчитать полную сумму при выключенном чекбоксе**
  - Given: промо доступно, но пользователь отключил сохранение.
  - When: создаётся платёж.
  - Then: сумма платежа равна полной стоимости корзины.

- [ ] **Использовать единый payment object**
  - Given: выбран способ оплаты card или SBP.
  - When: создаётся первый платёж.
  - Then: используется один платёжный объект с динамической суммой; отдельная verification-транзакция не создаётся.

- [ ] **Сохранить способ оплаты только при успешном growth event**
  - Given: чекбокс включён и платёж на 11₽ успешно завершён.
  - When: приходит подтверждение успешной оплаты.
  - Then: способ оплаты сохраняется/активируется, а попытка получает `is_growth_event = true`.

- [ ] **Не считать неуспешный платёж growth event**
  - Given: платёж 11₽ отклонён/отменён.
  - When: система обрабатывает результат.
  - Then: способ оплаты не считается успешно привязанным для дедупликации промо.

- [ ] **Показать промо при доступном праве и включённом чекбоксе**
  - Given: способ оплаты выбран, промо доступно, чекбокс включён.
  - When: открывается экран оплаты.
  - Then: отображается текст `Сохрани — счёт сегодня 11 ₽.`

- [ ] **Показать nudge при выключении чекбокса**
  - Given: промо доступно и пользователь выключает чекбокс.
  - When: UI обновляет состояние.
  - Then: отображается `Сохрани — счёт станет 11 ₽ вместо [сумма корзины].`

- [ ] **Не показывать промо при недоступности**
  - Given: промо отключено на точке или достигнут лимит.
  - When: открывается экран оплаты.
  - Then: промо-блок не отображается.

- [ ] **Не показывать промо после использования**
  - Given: пользователь ранее использовал промо любым способом.
  - When: открывается экран оплаты.
  - Then: промо-блок не отображается.

- [ ] **Показать безопасный текст для занятого способа оплаты**
  - Given: способ оплаты принадлежит другому аккаунту либо сработал card-testing/BIN attack.
  - When: попытка блокируется.
  - Then: отображается `Код не принят. Попробуй другой способ.`

- [ ] **Показать step-up сообщение**
  - Given: обнаружен recycled SIM, риск или ATO.
  - When: antifraud требует дополнительное подтверждение.
  - Then: отображается `Нужно подтверждение. Ещё раз код с SMS.` и запускается OTP на телефон аккаунта.

- [ ] **Показать rate-limit сообщение**
  - Given: velocity превышен.
  - When: пользователь получает отказ.
  - Then: отображается `Слишком часто. Следующая попытка — через 15 мин.`

- [ ] **Отображать сохранённую карту в списке методов**
  - Given: карта успешно сохранена.
  - When: пользователь открывает список способов оплаты.
  - Then: карта отображается по существующему безопасному формату, например `Картой ****8782`.

- [ ] **Отображать сохранённый СБП в списке методов**
  - Given: СБП успешно привязан.
  - When: пользователь открывает список способов оплаты.
  - Then: СБП отображается отдельной строкой без `last4` карты.

- [ ] **Использовать единый TOV для сохранённого СБП**
  - Given: сохранённый СБП доступен для повторной оплаты.
  - When: пользователь видит список способов оплаты.
  - Then: используется согласованный вариант `СБП · как обычно` либо утверждённый вариант `СБП · привязан · как обычно`.

- [ ] **Не показывать `success_returning` как post-payment статус для СБП**
  - Given: пользователь подтвердил оплату через СБП в банковском приложении.
  - When: backend получает callback.
  - Then: `success_returning` не используется как отдельный UI-статус после оплаты.

- [ ] **Не вмешиваться в экран банка**
  - Given: пользователь выбрал сохранённый СБП.
  - When: происходит переход в банковское приложение.
  - Then: PWA не добавляет собственные тексты поверх банковского flow и ожидает callback.

- [ ] **Определить поведение смены карты**
  - Given: пользователь уже имеет growth event и добавляет новую карту.
  - When: новая карта проходит проверку.
  - Then: смена карты не считается новым growth event и не даёт повторное право на 11₽.

- [ ] **Зафиксировать алгоритм определения перевыпущенной карты**
  - Given: новая карта потенциально является перевыпуском существующей.
  - When: antifraud анализирует доступные стабильные признаки.
  - Then: используется согласованный matching algorithm; если надёжного признака нет, система не должна самостоятельно считать карты одинаковыми.

- [ ] **Покрыть конкурентную привязку нагрузочным тестом**
  - Given: несколько параллельных запросов привязывают один способ оплаты к разным аккаунтам.
  - When: тест выполняет конкурентные insert операции.
  - Then: только один аккаунт получает активную привязку; race condition отсутствует.

- [ ] **Проверить отсутствие утечки при конкурентной ошибке**
  - Given: конкурентная привязка завершается unique constraint violation.
  - When: API формирует ответ.
  - Then: response не содержит данных другого аккаунта или способа оплаты.

## Изменения в связке: Т-Банк — сохранение способов оплаты и промо 11₽

- **Точки входа:** используются существующие payment Init/Recurrent и callback/webhook endpoints из `INTEGRATIONS.md`; новые внешние endpoint'ы в рамках задачи не добавляются.
- **Identity Mapping:**
  - Card: внешний `card_token`/RebillId → внутренний `method_hash` (`card_hash`) → `account_id`.
  - СБП: внешний `RequestKey`/`AccountToken` → внутренний стабильный `method_hash` → `account_id`.
  - `phone` берётся из внутреннего аккаунта и используется для promo eligibility и step-up OTP.
  - `method_type` различает `card` и `sbp`.
- **Handling Errors:**
  - повторная привязка уже занятого способа оплаты обрабатывается как ожидаемый `blocked_method_taken`;
  - нарушение DB unique constraint не возвращает HTTP 500 и не раскрывает данные владельца;
  - неуспешный/отменённый платёж 11₽ не считается успешным growth event;
  - callback СБП после банковского подтверждения обрабатывается существующим payment flow;
  - переход пользователя в банковское приложение и UI внутри банка не изменяются;
  - step-up OTP отправляется только на телефон внутреннего аккаунта.
- **Security:**
  - внешние токены и секреты не используются как публичный идентификатор дедупликации;
  - `method_hash` хранится в безопасном хэшированном виде;
  - уникальность `method_hash` обеспечивается DB constraint, а не только application-level проверкой;
  - существующая проверка подписи/сигнатуры callback/webhook сохраняется;
  - секреты интеграций хранятся только через существующий `.env`/secret storage;
  - ответы при конфликте привязки не содержат `card_hash`, `AccountToken`, `RequestKey`, account identifiers или данных другого пользователя.
