## Текст заказчика (дословно)

# Быстрый повтор частых покупок (Quick Repeat Bottom Sheet)

**Бизнес-цель:** Сокращение времени до оформления заказа (Time-to-Checkout) для возвращающихся клиентов за счет повторения прошлых кастомизированных заказов в 1 клик через bottom sheet с режимами peek/expanded.

## Глобальные ограничения
- Запрещено менять существующую схему БД (таблицы `orders`, `order_items`, `modifiers`, `products`, `categories`).
- Запрещено использовать тяжелые `JOIN`'ы в основном потоке запроса (агрегация должна выполняться на уровне сервиса с оптимизацией под чтение).
- Запрещено хардкодить бизнес-лимиты (30–60 дней, 3 карточки в секции "повторить") — вынести в конфигурацию/константы сервиса.
- Запрещено блокировать UI-поток (main thread) при парсинге/сериализации `localStorage`.
- Запрещено создавать новые зависимости для фронтенд-кэширования (использовать паттерн из `shopCartCache.js`).
- Запрещено изменять существующие категории товаров — использовать только существующие (`Черный`, `Холодные`, `Сезонные напитки`).

## Сценарии и чек-лист (Для todo.md)

### Backend (Ruby on Rails)

- [ ] Шаг 1: TDD логики фильтрации и агрегации частых товаров (Backend Service)
  - **Given:** В БД есть история заказов пользователя: 5 заказов за 45 дней (источник `:mobile`), 3 из которых содержат один и тот же напиток с одинаковыми модификаторами (размер, молоко, сироп).
  - **When:** Вызывается `Shop::CustomerFrequentProductsService.call(customer_id)`.
  - **Then:** Сервис возвращает массив из 1–3 объектов для секции "повторить", отсортированных по частоте и свежести. Объекты содержат `product_id`, `name`, `price`, `image_url`, полный сет кастомизаций. При отсутствии подходящих заказов возвращается пустой массив. Ошибки БД (500) пробрасываются и логируются.

- [ ] Шаг 2: TDD выборки товаров по категориям (Backend Service)
  - **Given:** В системе существуют категории: `Черный`, `Холодные`, `Сезонные напитки` с активными товарами.
  - **When:** Вызывается сервис для получения товаров витрины.
  - **Then:** Возвращаются товары сгруппированные по категориям. Каждая карточка содержит: `id`, `name`, `price`, `image_url` (или заглушка "Нет фото"), `category`. Для товаров без изображения возвращается placeholder.

- [ ] Шаг 3: TDD кэширования и инвалидации (Backend Cache)
  - **Given:** Сервис успешно сформировал данные для `customer_id` и `tenant_id`.
  - **When:** Данные сохраняются в кэш, а затем пользователь создает/оплачивает новый заказ.
  - **Then:** Данные сохраняются в `Rails.cache` (`solid_cache_store`) по ключу `shop/freq/#{tenant_id}/#{customer_id}` с TTL 30 минут. При callback-хуке создания/оплаты заказа кэш по данному ключу принудительно сбрасывается (invalidate).

- [ ] Шаг 4: TDD API Endpoint (Backend Controller)
  - **Given:** Пользователь авторизован, кэш сформирован.
  - **When:** Отправляется `GET /shop/api/frequent_products`.
  - **Then:** Возвращается HTTP 200 с JSON: `{ frequent_items: [...], categories: { "Черный": [...], "Холодные": [...], "Сезонные напитки": [...] } }`. При падении сервиса или БД (внутренняя ошибка 500) возвращается стандартный error payload. При неавторизованном доступе — HTTP 401.

### Frontend (PWA / Svelte) - Bottom Sheet States

- [ ] Шаг 5: TDD клиентского кэша и инициализации bottom sheet (Frontend Cache)
  - **Given:** Пользователь ранее загружал данные, они сохранены в `localStorage` (по аналогии с `shopCartCache.js`).
  - **When:** Пользователь открывает bottom sheet (свайп вверх или клик по триггеру).
  - **Then:** Bottom sheet появляется в состоянии **peek** (видна верхняя часть ~200-250px) за < 50 мс из `localStorage`. Параллельно инициируется фоновый `GET` запрос для актуализации данных. При краше сети (offline/500) отображаются закешированные данные без блокировки UI.

- [ ] Шаг 6: TDD состояния bottom sheet "peek" (Frontend UI States)
  - **Given:** Bottom sheet в состоянии **peek**.
  - **When:** Пользователь видит шторку.
  - **Then:** Видима только секция "повторить" с 1–3 мини-карточками частых товаров. Каждая карточка показывает: изображение товара, название (обрезанное с многоточием), цену, счетчик количества (- 1 +). Внизу видна оранжевая кнопка "повторить в 1 клик" или "+ещё". Присутствует drag-handle (индикатор свайпа).

- [ ] Шаг 7: TDD состояния bottom sheet "expanded" (Frontend UI States)
  - **Given:** Bottom sheet в состоянии **peek**, пользователь делает свайп вверх.
  - **When:** Bottom sheet переходит в состояние **expanded**.
  - **Then:** Bottom sheet занимает ~90% высоты экрана (до safe area). Видимы все категории: `Черный`, `Холодные`, `Сезонные напитки`. Каждая категория имеет заголовок и ссылку "Смотреть все →". Карточки товаров в категориях показывают: изображение (120x120px), название (2 строки с обрезкой), цену (оранжевым). Секция "повторить" остается внизу с полной шириной.

- [ ] Шаг 8: TDD состояния bottom sheet "hidden" (Frontend UI States)
  - **Given:** Bottom sheet в состоянии **expanded** или **peek**.
  - **When:** Пользователь делает свайп вниз или кликает вне шторки (scrim click).
  - **Then:** Bottom sheet плавно анимируется в состояние **hidden** (не видна). Состояние корзины сохраняется. При повторном открытии восстанавливается последнее состояние (peek/expanded).

- [ ] Шаг 9: TDD карточки товара в категории (Frontend Component)
  - **Given:** Bottom sheet в состоянии **expanded**, видна категория "Холодные".
  - **When:** Рендерится карточка товара (например, "Бамбл", "Кофе-тоник", "Матча тоник").
  - **Then:** Карточка содержит: изображение (с заглушкой "Нет фото" если отсутствует), название товара, цену (оранжевым цветом, например "3₽", "205₽"). При клике на карточку товар добавляется в корзину с дефолтными параметрами. При ошибке сети (400/500) показывается тост с ошибкой.

- [ ] Шаг 10: TDD карточки быстрого повтора (Frontend Component)
  - **Given:** Bottom sheet в состоянии **peek** или **expanded**, секция "повторить" видна.
  - **When:** Рендерятся 1–3 мини-карточки частых товаров.
  - **Then:** Каждая карточка показывает: круглое/квадратное изображение товара, счетчик количества (- 1 +) под изображением. При изменении счетчика количество мгновенно обновляется в localStorage и UI. При клике на "+ещё" bottom sheet переходит в состояние **expanded**.

- [ ] Шаг 11: TDD кнопки действия "повторить в 1 клик" и "+ещё" (Frontend Actions)
  - **Given:** Bottom sheet в состоянии **peek**, видна секция "повторить".
  - **When:** Пользователь нажимает оранжевую кнопку "повторить в 1 клик" (если 1 товар) или "+ещё".
  - **Then:** Для "повторить в 1 клик": все товары из секции "повторить" добавляются в корзину с сохраненными модификаторами, bottom sheet закрывается (hidden), показывается success-тост. Для "+ещё": bottom sheet плавно переходит в состояние **expanded**. При ошибке сети (400/500) показывается error-тост, состояние не меняется.

- [ ] Шаг 12: TDD кастомизации товара (Frontend Edit Flow)
  - **Given:** Пользователь кликает по карточке товара в категории (например, "Фильтр-кофе без кофеина (декаф)").
  - **When:** Открывается модалка/шторка выбора модификаторов.
  - **Then:** Видимы опции: размер, альтернативное молоко, сиропы. После выбора и подтверждения товар добавляется в корзину с выбранными параметрами. При ошибке валидации на бэке (400) показывается инлайн-ошибка.

### Критические кейсы:
- **Edge cases:** 
  - У пользователя 0 заказов (пустая секция "повторить")
  - Ровно 1 частый заказ (показывать кнопку "повторить в 1 клик")
  - >3 частых заказов (показывать только топ-3)
  - Товары без изображений (заглушка "Нет фото")
  - Товары с очень длинными названиями (обрезка с многоточием)
  
- **Лимиты времени:** 
  - Проверка корректного истечения TTL (30 мин) с использованием `Timecop` в RSpec
  - Проверка фильтрации "последние 30-60 дней" на граничных датах
  - Bottom sheet должен открываться за < 50 мс из кэша
  
- **Асинхронность:** 
  - Race condition при фоновом обновлении `localStorage` и одновременном клике "Повторить"
  - Плавная анимация переходов между состояниями hidden/peek/expanded (300ms)
  - Drag-gesture обработка (свайп вверх/вниз)
  
- **Сеть:** 
  - Обработка таймаутов и 500/400 ошибок при фоновом фетче
  - Обработка ошибок при добавлении товара в корзину
  - Offline-режим (работа только с localStorage)
  
- **UI States:** 
  - Корректный рендер в состоянии peek (видна только секция "повторить")
  - Корректный рендер в состоянии expanded (видны все категории)
  - Корректный переход в hidden (анимация закрытия)
  - Сохранение состояния при перезагрузке страницы

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус).
2. Линтер и тайпчекер (tsc) выполняются без ошибок.
3. Bottom sheet корректно работает на всех устройствах (mobile-first, 320px+).
4. Анимации переходов между состояниями плавные (60fps).
5. Время открытия из кэша < 50 мс.
6. Все карточки товаров отображаются корректно (изображения, цены, названия).
7. Секция "повторить" показывает 1–3 товара с корректными счетчиками.
8. Кнопки "повторить в 1 клик" и "+ещё" работают корректно.

## Заметки агента (не текст заказчика)

### Разведка по кодовой базе (первичная, до SPEC)

- Существующая шторка корзины: `app/frontend/components/CartSheet.svelte` + `app/frontend/lib/shop/cartSheetStore.js` — режимы HIDDEN/PEEK/EXPANDED уже есть (канон высот зафиксирован `bottom_sheet_heights_canon_test.rb`). Новая секция «повторить» и режимы из этого ТЗ должны встроиться в существующую шторку, не ломая канон.
- Клиентский кэш-паттерн: `app/frontend/lib/shop/shopCartCache.js` (localStorage) — ТЗ прямо требует переиспользовать.
- Тестовые пути из ТЗ (`spec/…`, RSpec; `src/lib/…`, Vitest) — **не совпадают** с фактическим стеком репо: у нас Minitest (`test/…`) и фронт без Vitest-инфраструктуры (`app/frontend/…`, integration-тесты фиксируют разметку Svelte-исходников). Требует решения на SPEC: маппинг на наш стек тестов.
- Названия категорий «Черный / Холодные / Сезонные напитки» — это demo-контент витрины, не константы схемы; сервис категорий уже есть (`Shop::Catalog.tenant_menu`).
- Авторизация покупателя на витрине: гостевая сессия/телефон — «HTTP 401 для неавторизованных» нужно уточнить против фактической модели customer (см. `shop/api` контроллеры).
- Кэш Rails: в проекте `solid_cache` — ключ `shop/freq/#{tenant_id}/#{customer_id}` совместим; инвалидация — хук в создании заказа (`Shop::OrderCreator`) и/или callback оплаты (hot-path — только минимальный дифф).

### Вопросы к SPEC (PHASE 1)

1. Тестовый стек: RSpec/Vitest из ТЗ ↔ Minitest/integration факт. Предлагаю зеркалить сценарии в `test/services/shop/`, `test/integration/shop/api/`, `test/integration/shop/` (как во всех прошлых задачах).
