## Текст заказчика (дословно)

# Быстрый повтор частых покупок (Quick Repeat Bottom Sheet)

**Бизнес-цель:** Сокращение времени до оформления заказа (Time-to-Checkout) для возвращающихся клиентов за счет повторения прошлых кастомизированных заказов в 1 клик через bottom sheet с режимами peek/expanded.

**Ключевое правило:** Если у пользователя есть активный заказ (в процессе приготовления/доставки/ожидания), секция быстрого повтора скрывается, так как клиент уже совершил покупку.

## Глобальные ограничения
- **NEW:** При наличии активного заказа (статусы: `created`, `accepted`, `cooking`, `ready`) секция повтора не показывается (сервис возвращает пустой массив `frequent_items`).
- Запрещено менять существующую схему БД (таблицы `orders`, `order_items`, `modifiers`, `products`, `categories`).
- Запрещено использовать тяжелые `JOIN`'ы в основном потоке запроса (агрегация должна выполняться на уровне сервиса с оптимизацией под чтение).
- Запрещено хардкодить бизнес-лимиты (30–60 дней, 3 карточки в секции "повторить", статусы активного заказа) — вынести в конфигурацию/константы сервиса.
- Запрещено блокировать UI-поток (main thread) при парсинге/сериализации `localStorage`.
- Запрещено создавать новые зависимости для фронтенд-кэширования (использовать паттерн из `shopCartCache.js`).
- Запрещено изменять существующие категории товаров — использовать только существующие (`Черный`, `Холодные`, `Сезонные напитки`).

## Сценарии и чек-лист (Для todo.md)

### Backend (Ruby on Rails)

- [ ] Шаг 1: TDD логики фильтрации, активного заказа и агрегации частых товаров (Backend Service)
  - **Given:** В БД есть история заказов пользователя (5 заказов за 45 дней, источник `:mobile`).
  - **When:** Вызывается `Shop::CustomerFrequentProductsService.call(customer_id)`.
  - **Then:**
    - Если у пользователя есть активный заказ (`orders.where(status: ACTIVE_STATUSES).exists?`), сервис возвращает пустой массив `[]`.
    - Если активных заказов нет, сервис возвращает массив из 1–3 объектов для секции "повторить", отсортированных по частоте и свежести, с полным сетом кастомизаций.
    - Ошибки БД (500) пробрасываются и логируются.

- [ ] Шаг 2: TDD выборки товаров по категориям (Backend Service)
  - **Given:** В системе существуют категории: `Черный`, `Холодные`, `Сезонные напитки` с активными товарами.
  - **When:** Вызывается сервис для получения товаров витрины.
  - **Then:** Возвращаются товары, сгруппированные по категориям. Каждая карточка содержит: `id`, `name`, `price`, `image_url` (или плашка "Нет фото"), `category`.

- [ ] Шаг 3: TDD кэширования и инвалидации при смене статуса (Backend Cache)
  - **Given:** Сервис успешно сформировал данные для `customer_id` и `tenant_id`.
  - **When:** Данные сохраняются в кэш (`solid_cache_store`, ключ `shop/freq/#{tenant_id}/#{customer_id}`, TTL 30 минут).
  - **Then:**
    - При изменении статуса заказа (создание, прием в работу, завершение `completed`, отмена `cancelled`) кэш по данному ключу принудительно сбрасывается (invalidate), чтобы UI мгновенно узнал о появлении или завершении активного заказа.

- [ ] Шаг 4: TDD API Endpoint (Backend Controller)
  - **Given:** Пользователь авторизован.
  - **When:** Отправляется `GET /shop/api/frequent_products`.
  - **Then:** Возвращается HTTP 200 с JSON: `{ has_active_order: boolean, frequent_items: [...], categories: { ... } }`. Если `has_active_order: true`, поле `frequent_items` всегда содержит `[]`. При неавторизованном доступе — HTTP 401, при ошибке сервера — HTTP 500.

### Frontend (PWA / Svelte) - Bottom Sheet States

- [ ] Шаг 5: TDD клиентского кэша и инициализации bottom sheet (Frontend Cache)
  - **Given:** Данные закешированы в `localStorage`.
  - **When:** Пользователь открывает bottom sheet.
  - **Then:** Bottom sheet появляется за < 50 мс из `localStorage`. Параллельно инициируется фоновый `GET` запрос. Если фоновый ответ присылает `has_active_order: true` или пустой `frequent_items`, интерфейс мгновенно скрывает секцию повтора без перезагрузки всей шторки.

- [ ] Шаг 6: TDD состояния bottom sheet "peek" с учетом активного заказа (Frontend UI States)
  - **Given:** Bottom sheet в состоянии `peek`.
  - **When:** Рендерится шторка.
  - **Then:**
    - Если нет активного заказа и есть частые товары: Видима секция "повторить" с 1–3 мини-карточками, кнопкой "повторить в 1 клик" / "+ещё" и drag-handle.
    - Если есть активный заказ (`has_active_order: true`) или 0 частых товаров: Секция "повторить" скрывается. В состоянии `peek` отображается только компактный снайпет витрины/каталога или плашка статуса текущего заказа.

- [ ] Шаг 7: TDD состояния bottom sheet "expanded" (Frontend UI States)
  - **Given:** Bottom sheet переходит в состояние `expanded` (свайп вверх).
  - **When:** Пользователь изучает каталог.
  - **Then:** Отображаются категории (`Черный`, `Холодные`, `Сезонные напитки`). Секция "повторить" рендерится внизу только при условии, что `has_active_order: false` и есть товары для повтора.

- [ ] Шаг 8: TDD состояния bottom sheet "hidden" (Frontend UI States)
  - **Given:** Bottom sheet открыт (`peek`/`expanded`).
  - **When:** Пользователь свайпает вниз или кликает на scrim.
  - **Then:** Bottom sheet плавно уходит в `hidden` (не виден). При повторном открытии состояние синхронизируется с актуальным статусом заказа.

- [ ] Шаг 9: TDD карточки товара в категории (Frontend Component)
  - **Given:** Видна категория товаров в состоянии `expanded`.
  - **When:** Пользователь кликает по карточке.
  - **Then:** Товар добавляется в корзину с дефолтными параметрами (или открывается выбор модификаторов).

- [ ] Шаг 10: TDD карточки быстрого повтора (Frontend Component)
  - **Given:** Секция "повторить" активна (нет активного заказа).
  - **When:** Рендерятся мини-карточки.
  - **Then:** Отображаются изображения, название, цена и счетчик (- 1 +). Изменение количества мгновенно обновляет `localStorage` и итоговую сумму покупки в 1 клик.

- [ ] Шаг 11: TDD кнопки действия "повторить в 1 клик" (Frontend Actions)
  - **Given:** Пользователь видит кнопку "повторить в 1 клик".
  - **When:** Нажимает оранжевую кнопку.
  - **Then:** Все сохраненные товары с кастомизациями попадают в корзину, bottom sheet переходит в `hidden`, показывается success-тост.

- [ ] Шаг 12: TDD кастомизации товара (Frontend Edit Flow)
  - **Given:** Пользователь кликает по товару в категории.
  - **When:** Открывается выбор модификаторов (размер, молоко, сироп).
  - **Then:** После подтверждения сет кастомизаций передается в корзину.

### Критические кейсы:
- **Активный заказ (Active Order Edge Cases):**
  - Пользователь создал заказ (статус `created` / `accepted`) → `frequent_items` возвращает `[]`.
  - Статус заказа изменился на `completed` или `cancelled` → кэш инвалидируется, при следующем запросе `frequent_items` снова отдаёт топ-3 товаров.

- **История покупок:**
  - 0 прошлых заказов и нет активных → `frequent_items: []`, `has_active_order: false`.
  - 3 частых товара → отдаются строго первые 3 с учетом свежести и частоты.

- **Кэширование и реактивность:**
  - Проверка корректного сброса `Rails.cache` по сигналу смены статуса `Order`.
  - Работа клиентского fallback в PWA при мгновенном переключении `has_active_order`.

- **Лимиты времени:**
  - Bottom sheet должен открываться за < 50 мс из кэша.
  - Проверка корректного истечения TTL (30 мин) с использованием `Timecop` в RSpec.
  - Проверка фильтрации "последние 30-60 дней" на граничных датах.

- **Асинхронность:**
  - Race condition при фоновом обновлении `localStorage` и одновременном клике "Повторить".
  - Плавная анимация переходов между состояниями hidden/peek/expanded (300ms).
  - Drag-gesture обработка (свайп вверх/вниз).

- **Сеть:**
  - Обработка таймаутов и 500/400 ошибок при фоновом фетче.
  - Обработка ошибок при добавлении товара в корзину.
  - Offline-режим (работа только с `localStorage`).

- **UI States:**
  - Корректный рендер в состоянии `peek` при наличии активного заказа (секция скрыта).
  - Корректный рендер в состоянии `expanded` (видны все категории).
  - Корректный переход в `hidden` (анимация закрытия).
  - Сохранение состояния при перезагрузке страницы.

## Exit Criteria (Критерии выхода)
1. Все RSpec и Vitest тесты проходят (зеленый статус).

## Патч 1: 2026-10-05 — race condition Quick Repeat после оплаты

**Источник:** [Google Doc «Глюк патч_1»](https://docs.google.com/document/d/19cdAWN5Djobb2dUTmsana2uHctLUVk-uhrWsCXRRUUI/edit?usp=drivesdk) · intake 2026-10-06 · текст ниже — дословно.

Основание: runtime-аудит от 2026-10-05; подтверждённая гонка cache/payment в
`app/services/callbacks/payment_status_updater.rb:104`.

### Расхождение

Subtask: Quick Repeat должен быть скрыт при активном заказе.

Given:
у клиента есть история покупок, текущий заказ находится в `pending_payment`,
а `/frequent_products` может опрашиваться параллельно с обработкой оплаты.

When:
`PaymentStatusUpdater` переводит заказ в `accepted` и выполняет `bust_cache!`
внутри `@payment.with_lock` до завершения транзакции.

Параллельный `GET /frequent_products` может попасть между удалением cache и
COMMIT транзакции.

Then:
Quick Repeat должен быть скрыт, поскольку заказ уже становится активным.

Фактически:
`/orders/active` после COMMIT возвращает активный заказ, но
`/frequent_products` может записать в Rails.cache устаревшее
`has_active_order=false`.

Это значение затем отдаётся из cache до следующего изменения статуса
баристой либо до истечения TTL 30 минут.

Runtime подтверждение:
- гонка воспроизведена на реальном коде приложения;
- в тесте с инструментированной паузой `GET /frequent_products` записал
  `has_active_order=false` до COMMIT оплаты;
- после COMMIT cache содержал `has_active_order=false`, хотя заказ уже
  `accepted`;
- в естественной гонке без паузы stale `false` остался после COMMIT в
  12 из 23 прогонов;
- защитного теста на race delete-before-commit не было.

Фактические точки расхождения:
- `app/services/callbacks/payment_status_updater.rb:104`
  — `bust_cache!` выполняется внутри транзакции оплаты;
- `app/services/shop/customer_frequent_products_service.rb:41-45`
  — `cached_payload` после cache miss вычисляет `has_active_order` и
  записывает результат в cache;
- `app/frontend/components/CartSheet.svelte:99`
  — `showRepeat` зависит от `hasActiveOrderFlag` из `/frequent_products`.

### Исправленный сценарий

- [ ] Subtask: Quick Repeat скрывается при активном заказе
  (patch v[X])

  Given:
  у клиента есть история покупок;
  заказ переходит из `pending_payment` в `accepted`.

  When:
  параллельный `GET /frequent_products` выполняется во время транзакции
  оплаты, включая окно между инвалидированием cache и COMMIT.

  Then:
  результат `frequent_products` не должен после COMMIT фиксировать в cache
  состояние `has_active_order=false`, если заказ уже стал `accepted`.

  And:
  после успешной оплаты любой последующий `/frequent_products` должен
  получать согласованное состояние `has_active_order=true`.

  And:
  Quick Repeat должен оставаться скрытым во всех режимах
  `hidden / peek / expanded`, пока существует активный заказ.

  And:
  после перехода заказа в статус, при котором Quick Repeat снова разрешён,
  существующая логика Quick Repeat должна продолжить работать без изменений.

- [ ] Subtask: защитный тест на race condition
  (patch v[X])

  Given:
  оплата переводит заказ `pending_payment → accepted`.

  When:
  `frequent_products` вычисляется параллельно с транзакцией оплаты.

  Then:
  stale cache с `has_active_order=false` не должен переживать COMMIT
  принятого заказа.

  And:
  после COMMIT повторный вызов `cached_payload` должен вернуть
  `has_active_order=true`.

### Критерий готовности патча

После исправления необходимо доказать:

1. заказ `pending_payment → accepted`;
2. параллельный `/frequent_products` не оставляет stale
   `has_active_order=false` после COMMIT;
3. после COMMIT cache содержит согласованное состояние;
4. последующий `/frequent_products` возвращает `has_active_order=true`;
5. Quick Repeat скрыт при активном заказе;
6. после разрешённого статуса Quick Repeat снова появляется по существующей
   логике;
7. существующие Quick Repeat tests проходят;
8. существующие payment/cache tests проходят.

### Заметки агента к Патчу 1 (не текст заказчика) — SPEC

- `patch v[X]` = **v1** (первый патч к этому ТЗ). Классификация: ПАТЧ (сценарий «скрыт при активном заказе» был, кэш его нарушает).
- Отдельный SPEC не нужен — секция патча = SPEC; механизм выбран агентом (делегировано владельцем):
  1. `PaymentStatusUpdater`: `bust_cache!` внутри `with_lock` убран → `CustomerFrequentProductsService.mark_order_active_after_commit!(order:)`.
  2. Запись через `ActiveRecord.after_all_transactions_commit` (Rails 8.1): срабатывает после COMMIT **самой внешней** транзакции (job `with_order_tenant!`, controller tenant-txn), при rollback — не срабатывает.
  3. После COMMIT пишется `{ has_active_order: true, frequent_items: [] }` **без SQL** — `SET LOCAL app.current_tenant_id` после COMMIT уже снят (RLS на `orders`), пересчёт мог бы дать ложный `false`. Это ровно то, что вернул бы `payload` для `accepted` в окне `ACTIVE_ORDERS_WINDOW`; заказ старше окна → просто `bust_cache!` (существующая логика).
  4. `cached_payload` при cache miss пишет с `unless_exist: true` — GET, начавший расчёт до COMMIT, не перезапишет свежую post-commit запись. Явные записи (`refresh_cache!`, post-commit) по-прежнему перезаписывают.
- Не меняются: окно 45 дней, `COUNTED_STATUSES`, `HIDE_REPEAT_STATUSES`, TTL 30 мин, ключ v3, `/orders/active`, frontend.
- Тесты: Minitest (`test/services/shop/customer_frequent_products_cache_test.rb`), не RSpec из текста ТЗ.
