# TASK_101: Сумма заказа в блоке способов оплаты

> **ID заказчика:** TASK_101 · **CBR:** #101 · **Intake:** 2026-10-05  
> **Источник:** [Google Doc](https://docs.google.com/document/d/1pl-YrMIomC2sZGLnUYDFaIWJBlKSr7BhCtjyiBrL_X4/edit?usp=sharing)

Бизнес-цель: Сделать итоговую сумму заказа постоянно видимой гостю на экране checkout `/shop`, чтобы при выборе способа оплаты, изменении количества товаров и возникновении ошибки оплаты гость однозначно видел сумму, которая соответствует фактической сумме заказа и `Amount`, отправляемому в Т-Банк.

## 1. Связь с картой интеграций

1. **Затронутые сервисы из `@INTEGRATIONS.md`:** Т-Банк — только для проверки соответствия `total` и `Amount`; новых интеграционных контрактов с внешними сервисами не создаётся.
2. **Смежные модули, которые НЕЛЬЗЯ ломать:** расчёт стоимости корзины, модификаторы, скидки, сохранённые карты, СБП, способ оплаты «Картой», создание платежа, callback, Outbox, Circuit Breaker, обработка ошибок оплаты.

## 2. Связь с картой компонентов

1. **Затронутые компоненты из `@COMPONENT_MAP.md`:** блок способов оплаты checkout `/shop` — точный компонент и путь определить по актуальному `COMPONENT_MAP.md` до начала реализации.
2. **Общий файл с другой задачей:** необходимо проверить. Если компонент блока способов оплаты уже принадлежит задаче по сохранённым картам или другой checkout-задаче, текущая задача изменяет только участок, отвечающий за отображение `Итого`; существующую логику способов оплаты и карт не менять.
3. **Новый компонент (не в карте):** определить после сверки с `COMPONENT_MAP.md`. Если для строки `Итого` создаётся новый переиспользуемый компонент, он должен быть добавлен в карту через БЛОК 4.

## 3. Разрешенный и Запрещенный Scope

### Разрешено менять/создавать

1. Frontend-код checkout `/shop`, отвечающий за блок способов оплаты.
2. Компонент/слой отображения строки `Итого`.
3. Клиентский контракт данных корзины — только если `total` отсутствует в текущем API.
4. Backend `/shop/api/cart` — только для добавления `total`, если его действительно нет в текущем ответе.
5. Существующий utility форматирования денежных значений — использовать повторно; создать новый только при отсутствии подходящего общего utility.
6. Тесты затронутого checkout-компонента и API-контракта.
7. Документацию `shop-api.md` — только если изменяется контракт `/shop/api/cart`.

### Строго запрещено менять

1. Логику создания платежа.
2. Расчёт `Amount` в `Payments::TbankAdapter`.
3. Callback, Outbox и Circuit Breaker.
4. Алгоритмы расчёта цен, модификаторов и скидок.
5. Логику сохранённых карт.
6. Логику СБП и выбора способа оплаты.
7. Кнопку оплаты и её состояния.
8. Тексты и визуальную модель ошибок оплаты.
9. POS бариста и панели УК.
10. Файлы/компоненты, принадлежащие другим задачам согласно `COMPONENT_MAP.md`, кроме явно выделенного участка текущей задачи.
11. Создание отдельного `todo-[feature].md`.

### UX/UI-паттерны проекта

Перед реализацией обязательно использовать существующие UX/UI-паттерны CoffeeOS из переданных/актуальных референсов проекта:

1. повторить существующую типографику, размеры, начертания и иерархию денежных значений;
2. использовать существующие spacing/grid tokens, а не вводить локальные произвольные отступы;
3. использовать существующий паттерн выравнивания финансовых значений по правому краю;
4. сохранить существующую структуру блока способов оплаты и визуальную иерархию между заголовками, суммой и способами оплаты;
5. использовать существующие компоненты/токены для divider, состояния ошибки и вертикальных отступов, если они уже есть в проекте;
6. не создавать новый визуальный паттерн для `Итого`, если аналогичный паттерн суммы уже существует в checkout, корзине, заказе или статусной шторке;
7. обеспечить корректное поведение на узком экране PWA около 360 px и в In-App Browser;
8. при наличии нескольких референсов выбрать паттерн, уже используемый в checkout/финансовом контексте, а не переносить визуальное решение из несвязанного сценария;
9. UX-поведение ошибки оплаты не менять: строка `Итого` сохраняет своё положение, а существующее сообщение об ошибке остаётся без изменений.

## 4. Сценарии и Чек-лист (Gherkin)

1. **Subtask 1: Зафиксировать источник итоговой суммы**
   1. Given существует текущий API `/shop/api/cart`
   2. When разработчик проверяет фактический контракт ответа
   3. Then используется существующее поле `total`, если оно уже возвращается; если поля нет — добавляется `total` без изменения существующей логики расчёта стоимости
2. **Subtask 2: Покрыть контракт `total` тестом**
   1. Given корзина содержит товары, количества, модификаторы и/или скидки
   2. When вызывается `/shop/api/cart`
   3. Then `total` соответствует серверной итоговой стоимости корзины
3. **Subtask 3: Проверить соответствие `total` и `Amount`**
   1. Given сформирована корзина с итоговой стоимостью
   2. When backend формирует платежные данные для Т-Банка
   3. Then значение `total` соответствует `Amount` с корректной конвертацией рублей в копейки
   4. And логика `Payments::TbankAdapter` не изменяется
4. **Subtask 4: Отобразить строку `Итого` в блоке способов оплаты**
   1. Given гость находится на checkout и блок способов оплаты открыт
   2. When отображается список способов оплаты
   3. Then над первой сохранённой картой отображается строка `Итого`
   4. And сумма выровнена по правому краю
   5. And строка визуально находится выше первой карты, СБП и способа «Картой»
   6. And применяется существующий UX/UI-паттерн финансовых значений CoffeeOS
5. **Subtask 5: Форматировать сумму по правилам проекта**
   1. Given `total` равен 3245 рублям
   2. When значение отображается в UI
   3. Then пользователь видит `Итого 3 245 ₽`
   4. And разделитель тысяч — пробел
   5. And используется знак `₽`
   6. And форматирование выполняется через существующий utility проекта либо через новый общий utility, если аналог отсутствует
6. **Subtask 6: Отобразить сумму без сохранённых карт**
   1. Given у гостя отсутствуют сохранённые карты
   2. When открыт блок способов оплаты
   3. Then `Итого` отображается в начале блока над первым доступным способом оплаты
   4. And существующая структура способов оплаты не изменяется
7. **Subtask 7: Обновлять сумму после изменения корзины**
   1. Given блок способов оплаты открыт
   2. When гость увеличивает, уменьшает количество товара или удаляет товар
   3. Then UI получает актуальный `total`
   4. And значение `Итого` обновляется без полной перезагрузки экрана
   5. And значение совпадает с актуальной суммой корзины
8. **Subtask 8: Сохранить сумму при ошибке оплаты**
   1. Given платёж отклонён и UI показывает существующую ошибку оплаты
   2. When состояние checkout переходит в error state
   3. Then строка `Итого` остаётся видимой на прежнем месте
   4. And существующий текст и механизм отображения ошибки не изменяются
9. **Subtask 9: Учесть модификаторы и скидки**
   1. Given в корзине есть модификаторы с доплатой и/или применена скидка
   2. When отображается `Итого`
   3. Then значение берётся из серверного `total`
   4. And оно совпадает с суммой, используемой для формирования `Amount`
10. **Subtask 10: Не отображать некорректный нулевой total**
    1. Given корзина пустая или итоговая стоимость ещё не загружена
    2. When checkout отображает блок способов оплаты
    3. Then строка `Итого` не отображается
    4. And значение `0 ₽` не выводится
11. **Subtask 11: Проверить узкий экран**
    1. Given ширина viewport около 360 px
    2. When открыт блок способов оплаты
    3. Then `Итого` и сумма не ломают существующую сетку
    4. And сумма не обрезается и не создаёт горизонтальный overflow
    5. And применённый layout соответствует существующим mobile UX/UI-паттернам проекта
12. **Subtask 12: Проверить In-App Browser**
    1. Given checkout открыт в Telegram или Instagram In-App Browser
    2. When отображается блок способов оплаты
    3. Then строка `Итого` визуально и функционально соответствует обычному PWA checkout
    4. And существующие способы оплаты и кнопка оплаты работают без изменений
13. **Subtask 13: Проверить отсутствие регрессий**
    1. Given изменения задачи установлены
    2. When запускаются существующие shop integration/component tests
    3. Then тесты проходят
    4. And функциональность сохранённых карт, СБП, оплаты и ошибок не регрессирует

## 5. Команды TDD-проверки

1. **Запуск тестов:** использовать существующую команду тестирования `/shop` из проекта; точную команду определить по `package.json`/проектному канону.
2. **Проверка типов:** использовать существующую TypeScript-команду проекта, например `npm run typecheck`, если она присутствует в текущем `package.json`.
3. **Дополнительно:** запустить существующий lint/format check для затронутого frontend-кода.

## 6. Definition of Done

1. `Итого` отображается справа в блоке способов оплаты над первым способом оплаты/сохранённой картой.
2. Для корзины с сохранёнными картами и без них используется одинаковая согласованная UX-структура.
3. Сумма берётся из серверного `total`, а не вычисляется клиентом через `price × qty`.
4. `total` соответствует `Amount` Т-Банка.
5. Модификаторы и скидки корректно учитываются.
6. При изменении корзины сумма обновляется.
7. При ошибке оплаты сумма остаётся видимой.
8. При отсутствии валидного `total` строка не отображается.
9. Визуальное решение соответствует существующим UX/UI-паттернам и референсам CoffeeOS.
10. Проверены viewport около 360 px и Telegram/Instagram In-App Browser.
11. Все затронутые тесты проходят.
12. Scope других задач и существующая логика checkout не изменены.
