# Задача: УК — включение промо 11₽ при создании точки

**CBR:** #76 · **Дата intake:** 2026-09-04  
**Артефакты:** `docs/operations/milestones/veha_2/artifacts/uk_point_campaign_promo_11rub/`  
**Группа:** УК / point-level campaigns (продолжение #75)

---

Задача: УК — включение промо 11₽ при создании точки 

Бизнес-цель: дать администратору УК возможность включать пилотное промо 11₽ на уровне конкретной точки, контролировать лимит сохранённых способов оплаты и автоматически прекращать показ промо после достижения порога. Настройка не должна наследоваться другими точками города. Модель данных должна быть обобщённой для будущих точечных кампаний, включая пилоты подписки.

## 1. Связь с картой интеграций

- **Затронутые сервисы из `@INTEGRATIONS.md`:** внешние интеграции не изменяются.
- **Смежные модули, которые НЕЛЬЗЯ ломать:**
  - существующий checkout/payment flow;
  - существующую логику `card_binding_attempts`;
  - расчёт стандартной стоимости корзины;
  - существующую авторизацию и права администратора УК;
  - существующую логику промо для других точек;
  - будущую возможность добавления других `campaign_type`.

## 2. Разрешенный и Запрещенный Scope

- **Разрешено менять/создавать:**
  - backend-модуль настроек/управления точками;
  - API создания и редактирования точки;
  - API получения карточки точки;
  - бизнес-логику определения активности point-level кампании;
  - миграцию и модель `point_campaign_settings`;
  - запросы/репозитории агрегации `card_binding_attempts`;
  - frontend/PWA карточки создания и редактирования точки;
  - frontend отображение статуса, порога и счётчика;
  - тесты API, интеграционные тесты и UI-тесты новой функциональности;
  - типы/DTO, непосредственно связанные с `point_campaign_settings`.

- **Строго запрещено менять:**
  - архитектуру и семантику существующего `card_binding_attempts`;
  - существующую авторизацию/аутентификацию;
  - checkout flow, не связанный с определением активности point-level промо;
  - расчёт P&L и финансовую отчётность;
  - существующие интеграции с платёжными провайдерами;
  - существующую логику других промо;
  - автоматическое наследование настроек между точками;
  - реализацию подписочного пилота;
  - добавление отдельной таблицы `promo_point_settings`;
  - добавление отдельных колонок в `point_campaign_settings` под конкретные будущие типы кампаний.

## 3. Сценарии и Чек-лист (Gherkin)

- [ ] **Subtask 1: Создать обобщённую модель point_campaign_settings**
  - Given: в системе отсутствует специализированная настройка промо на уровне точки
  - When: создаётся миграция для точечных кампаний
  - Then: создаётся `point_campaign_settings` с полями `id`, `point_id`, `campaign_type`, `enabled`, `threshold`, `counter`, `config`, `created_at`; `point_id` связан с точкой через FK.

- [ ] **Subtask 2: Добавить campaign_type для промо привязки способа оплаты**
  - Given: используется `point_campaign_settings`
  - When: создаётся настройка промо 11₽
  - Then: используется `campaign_type = 'card_binding_promo'`; структура не содержит колонок, специфичных только для этого промо.

- [ ] **Subtask 3: Создать настройку промо при создании точки**
  - Given: администратор заполняет карточку новой точки
  - When: включает переключатель «Промо 11₽» и сохраняет точку
  - Then: создаётся запись `point_campaign_settings` для этой точки с `campaign_type = 'card_binding_promo'`, `enabled = true`, заданным `threshold` и `counter = 0`.

- [ ] **Subtask 4: Не создавать кампанию при выключенном переключателе**
  - Given: администратор создаёт новую точку
  - When: переключатель «Промо 11₽» выключен
  - Then: активная кампания `card_binding_promo` для точки не создаётся либо сохраняется как `enabled = false` согласно принятой модели upsert.

- [ ] **Subtask 5: Обновлять состояние промо при редактировании точки**
  - Given: у точки существует `card_binding_promo`
  - When: администратор меняет состояние переключателя и сохраняет карточку
  - Then: обновляется `enabled`, а исторический `counter` не обнуляется.

- [ ] **Subtask 6: Отображать состояние промо в карточке точки**
  - Given: точка имеет настройку `card_binding_promo`
  - When: администратор открывает карточку точки
  - Then: отображаются состояние промо, текущий счётчик и установленный порог.

- [ ] **Subtask 7: Рассчитывать счётчик по point_id**
  - Given: в `card_binding_attempts` существуют успешные growth-события для нескольких точек
  - When: запрашивается счётчик конкретной точки
  - Then: учитываются только записи с соответствующим `point_id` и `is_growth_event = true`.

- [ ] **Subtask 8: Суммировать карту и СБП в один счётчик**
  - Given: для точки существуют успешные growth-события через карту и СБП
  - When: рассчитывается счётчик точки
  - Then: оба типа способа оплаты суммируются в одну цифру; фильтр по `method_type` отсутствует.

- [ ] **Subtask 9: Заложить возможность дальнейшей агрегации по способу оплаты**
  - Given: разные способы оплаты должны в будущем анализироваться отдельно
  - When: проектируется модель данных/запрос агрегации
  - Then: существующий `method_type` в логах сохраняется и не используется для ограничения MVP-счётчика.

- [ ] **Subtask 10: Останавливать промо при достижении порога**
  - Given: счётчик точки достиг значения `threshold`
  - When: клиент оформляет новый заказ в этой точке
  - Then: `card_binding_promo` не показывается клиенту для этой точки.

- [ ] **Subtask 11: Не останавливать промо других точек**
  - Given: одна точка достигла своего `threshold`
  - When: клиент оформляет заказ в другой точке с активным пилотом
  - Then: промо продолжает работать во второй точке независимо от состояния первой.

- [ ] **Subtask 12: Сохранить исторический счётчик при ручном выключении**
  - Given: точка имеет накопленный `counter`
  - When: администратор выключает промо
  - Then: `enabled = false`, а историческое значение счётчика сохраняется без обнуления.

- [ ] **Subtask 13: Не наследовать кампанию новой точке того же города**
  - Given: первая точка города имеет завершённый или активный пилот
  - When: администратор создаёт вторую точку того же города
  - Then: настройки кампании первой точки не копируются автоматически; новая точка получает собственную настройку только на основании своего переключателя.

- [ ] **Subtask 14: Хранить специфические параметры кампании в config**
  - Given: промо 11₽ требует специфических параметров
  - When: создаётся или обновляется `card_binding_promo`
  - Then: специфические параметры, включая промо-цену при необходимости, хранятся в `config` JSONB, а не в новых колонках таблицы.

- [ ] **Subtask 15: Проверить отсутствие функциональности подписки**
  - Given: модель поддерживает несколько `campaign_type`
  - When: добавляется структура для будущих кампаний
  - Then: текущая задача не включает UI, бизнес-логику или платёжный flow подписки.

- [ ] **Subtask 16: Передавать актуальную сумму корзины при выключенном чекбоксе**
  - Given: клиент находится в checkout с промо-ценой и выбранным способом оплаты
  - When: клиент выключает чекбокс сохранения способа оплаты
  - Then: промо-текст/итоговая сумма переключается на актуальную сумму корзины независимо от того, выбран способ оплаты картой или СБП.

- [ ] **Subtask 17: Проверить корректность суммы для карты**
  - Given: клиент выбрал оплату картой
  - When: отключает чекбокс сохранения способа оплаты
  - Then: отображается актуальная стандартная сумма корзины без промо-цены 11₽.

- [ ] **Subtask 18: Проверить корректность суммы для СБП**
  - Given: клиент выбрал оплату СБП
  - When: отключает чекбокс сохранения способа оплаты
  - Then: отображается актуальная стандартная сумма корзины без промо-цены 11₽.

- [ ] **Subtask 19: Засчитать успешную привязку через СБП в счётчик точки**
  - Given: точка имеет активное промо
  - When: клиент сохраняет способ оплаты через СБП с промо-ценой
  - Then: соответствующее growth-событие учитывается в агрегированном счётчике точки.

- [ ] **Subtask 20: Проверить изоляцию порога между точками**
  - Given: две точки имеют собственные `threshold` и `counter`
  - When: одна точка достигает порога
  - Then: состояние второй точки не изменяется.

- [ ] **Subtask 21: Проверить идемпотентность сохранения настройки точки**
  - Given: для точки уже существует `card_binding_promo`
  - When: администратор повторно сохраняет карточку точки
  - Then: создаётся/обновляется одна актуальная настройка кампании без дублирования записей.

- [ ] **Subtask 22: Добавить интеграционные тесты API**
  - Given: существуют сценарии создания, редактирования и просмотра точки
  - When: запускаются тесты новой функциональности
  - Then: проверяются создание кампании, изменение `enabled`, сохранение `counter`, отображение threshold/counter и отсутствие наследования.

- [ ] **Subtask 23: Добавить тесты агрегации счётчика**
  - Given: `card_binding_attempts` содержит успешные и неуспешные события разных `method_type`
  - When: рассчитывается счётчик точки
  - Then: учитываются только `is_growth_event = true`, независимо от `method_type`.

- [ ] **Subtask 24: Проверить TypeScript-контракты**
  - Given: backend и frontend используют новые DTO/types
  - When: запускается проверка типов
  - Then: проект проходит `npx tsc --noEmit` без новых ошибок.
