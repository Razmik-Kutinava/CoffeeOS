## Текст заказчика (дословно)

UX-доработка сценария повторной оплаты после ошибки One-Click
Бизнес-цель: улучшить UX повторной оплаты после неуспешного списания по One-Click. Пользователь должен иметь возможность без лишних действий выбрать другую карту или ввести новую карту в полноценной шторке выбора способа оплаты.
Задача является дополнительной UX-доработкой уже реализованного и работающего сценария оплаты. Существующую бизнес-логику эквайринга, API и обработку платежа не изменять.
1. Контекст и проблема
При использовании One-Click происходит попытка списания с текущей привязанной карты. Если карта больше не работает, заблокирована или на ней недостаточно средств, платеж завершается ошибкой.
На основном экране заказа отображается состояние:
«Ошибка оплаты, попробуйте снова»
После этого пользователь должен иметь возможность сменить способ оплаты или выбрать другую карту.
Сейчас при переходе к выбору/смене карты возникают следующие UX-проблемы:
Шторка открывается не в полном размере.
Bottom Sheet открывается в промежуточном состоянии, из-за чего форма выбора/ввода карты и кнопка «Оплатить» могут быть обрезаны.
Несогласованный интерфейс формы оплаты.
В шторке используется визуальное представление, которое отличается от уже существующего понятного экрана «Способ оплаты».
Дублирование информации.
После раскрытия шторки внутри неё продолжают отображаться ошибка оплаты и динамические inline-кнопки (СБП, карта +), хотя эта информация уже присутствует на основном экране заказа.
2. Целевое поведение
2.1. Автоматическое раскрытие шторки
Если пользователь после ошибки оплаты открывает выбор/смену способа оплаты:
шторка должна сразу открываться в expanded / full-screen состоянии;
промежуточное collapsed / half-height состояние для этого сценария не использовать;
пользователь не должен самостоятельно растягивать шторку;
форма выбора карты, поля новой карты и основная кнопка «Оплатить» должны быть доступны пользователю.
2.2. Единый экран «Способ оплаты»
Внутри шторки использовать существующий понятный layout экрана «Способ оплаты».
В зависимости от текущей реализации он должен позволять пользователю:
выбрать существующую привязанную карту;
выбрать СБП;
выбрать добавление/ввод новой карты;
заполнить необходимые данные новой карты;
выполнить оплату через основную кнопку «Оплатить».
Не создавать отдельную альтернативную форму оплаты.
Не менять существующие цвета, отступы, радиусы и визуальные правила UI-kit без необходимости. Если соответствующий компонент уже существует, переиспользовать его.
2.3. Убрать дублирующие элементы из expanded-шторки
Внутри раскрытой шторки не должны отображаться:
красный блок «Ошибка оплаты, попробуйте снова»;
дублирующие inline-кнопки быстрой оплаты СБП / карта +, которые отображаются на основном экране в связи со статусом оплаты.
Ошибка оплаты должна оставаться на основном экране заказа.
Шторка должна быть самостоятельным функциональным экраном выбора/ввода способа оплаты.
3. Пользовательский сценарий
Пользователь выполняет оплату через One-Click.
Списание с текущей карты завершается ошибкой, например из-за отсутствия средств или невалидности/недоступности карты.
На основном экране заказа отображается «Ошибка оплаты, попробуйте снова».
Пользователь нажимает на текущую карту или действие смены способа оплаты.
Шторка выбора способа оплаты открывается сразу в Expanded / Full Screen.
Пользователь видит полноценный экран «Способ оплаты».
Пользователь выбирает другую привязанную карту или добавляет/вводит новую карту.
Пользователь нажимает «Оплатить».
Кнопка переходит в существующее состояние загрузки.
Далее используется существующая логика отправки платежа и обработки результата.
4. Ограничения реализации
Разрешено менять
UI-компонент Bottom Sheet / Payment Sheet;
layout и размеры шторки;
начальное состояние collapsed / expanded;
отображение элементов внутри шторки;
существующие UI-компоненты формы «Способ оплаты»;
UI-связь между ошибкой оплаты и открытием шторки;
UI-тесты данного сценария.
Запрещено менять
бизнес-логику One-Click;
бизнес-логику эквайринга;
API-контракты;
payload платежных запросов;
обработку ответов эквайринга;
статусы платежных операций;
логику привязки банковских карт;
структуру БД;
существующий успешный сценарий оплаты;
внешние интеграции.
Если для реализации UX-доработки обнаруживается необходимость изменить бизнес-логику платежа или интеграционный контракт, изменение не выполнять в рамках данной задачи.
5. Критерии приёмки
После ошибки One-Click при переходе к смене способа оплаты шторка сразу открывается в expanded / full-screen.
Шторка не открывается в промежуточном состоянии, из-за которого обрезается форма.
Форма выбора/смены карты полностью доступна пользователю.
Поля ввода новой карты не обрезаются.
Кнопка «Оплатить» полностью видима и доступна.
Внутри шторки используется существующий layout «Способ оплаты».
Внутри expanded-шторки отсутствует сообщение «Ошибка оплаты, попробуйте снова».
Внутри expanded-шторки отсутствуют дублирующие inline-кнопки СБП / карта +.
Сообщение об ошибке продолжает отображаться на основном экране заказа.
Существующий loading state кнопки «Оплатить» сохраняется.
Существующая логика отправки платежа не изменена.
Успешный One-Click сценарий работает без изменений.
Изменения не затрагивают API, БД и интеграционный контракт эквайринга.
6. TDD-проверки
Проверить сценарий ошибки One-Click → открытие выбора способа оплаты → смена/ввод карты → повторная оплата.
Также проверить:
отсутствие регрессии успешной оплаты;
отсутствие обрезания формы в expanded состоянии;
отсутствие дублирующих элементов внутри шторки;
корректное сохранение существующего payment flow.
