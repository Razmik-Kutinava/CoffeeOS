# Задача: Доработка личного кабинета (ЛК) в PWA

## Бизнес-цель

Завершить пользовательский сценарий личного кабинета в PWA: просмотр истории заказов, просмотр деталей заказа, управление профилем и контактами, переход к юридической информации и информации о приложении. UI и UX должны соответствовать приложенным макетам и UX-референсам, без самостоятельного изобретения новых паттернов.

---

## 1. Связь с картой интеграций

### Затронутые сервисы из @INTEGRATIONS.md
- На текущем этапе новые внешние интеграционные контракты не добавляются.

### Backend-контракты, требующие уточнения
- API истории заказов
- API изменения профиля
- API/механика подтверждения email
- API/механика подтверждения телефона
- API управления уведомлениями
- logout-механизм

### Внешние ссылки
- Экран «О нас» использует конфигурационный список URL
- На текущем этапе ссылки ведут на Google Docs

### Смежные модули, которые НЕЛЬЗЯ ломать
- авторизация и текущая сессия пользователя
- существующий routing PWA
- существующая система заказов
- существующие платежные сценарии
- существующие push/notification-механизмы
- существующие UI-компоненты bottom sheet

## 2. Разрешенный и Запрещенный Scope

### Разрешено менять/создавать
- `app/frontend/routes/personal-account/*` или `app/frontend/routes/profile/*` — маршруты ЛК
- `app/frontend/components/**` — только новые/адаптируемые компоненты ЛК
- `app/frontend/lib/config/**` — конфигурация ссылок экрана «О нас»
- `test/**` — тесты новой функциональности TASK-PERSONAL-CABINET
- Визуальные элементы в соответствии с макетами

### Строго запрещено менять
- `app/frontend/routes/auth/**` — кроме необходимого вызова уже существующего logout-контракта
- платежные модули и checkout
- интеграцию ОФД банка
- реализацию PLG-механик в коде (только контейнер под конфигурацию)
- подписку/реферальную программу
- `prisma/schema.prisma` и структуру БД
- существующие payment/webhook-контракты
- существующие Telegram/Instagram/WebView-интеграции
- глобальные дизайн-токены и базовые UI-компоненты без необходимости

## 3. Детальные требования по Subtasks

### Экран главного ЛК
**Subtask 1-4**: Маршрут, шапка пользователя, аватар, контейнер PLG-блоков с конфигурацией

### История заказов
**Subtask 5-8**: Загрузка истории, отображение элементов, обработка пустого списка, обработка ошибок

### Деталь заказа
**Subtask 9-13**: Маршрут, структура по макету, данные без ОФД, кнопка повтора, запрет на ОФД-интеграцию

### Экран профиля/настроек
**Subtask 14-24**: Редактирование имени, тумблер уведомлений, блок контактов (email/телефон), кнопки подтверждения, переход к «О нас», bottom sheet «Написать нам», Telegram-канал, email-сценарий, logout

### Экран «О нас»
**Subtask 25-29**: Версия приложения, build-код, копирование информации, конфигурируемые URL, footer

### Финальная проверка
**Subtask 30-31**: Соответствие макетам, отсутствие функциональности вне scope

## 4. Открытые вопросы / блокирующие зависимости

До реализации соответствующих subtasks необходимо получить:

- API истории заказов: endpoint, метод, формат request/response, pagination
- Контракт сохранения имени пользователя
- Семантика тумблера уведомлений и backend-контракт
- Флоу подтверждения email: код или ссылка, endpoint, состояния
- Флоу подтверждения телефона: SMS/код, endpoint
- Сценарий email через «Написать нам»
- Поведение logout и целевой экран
- Финальный список Google Docs URL
- Ссылка Telegram-бота
- Название юридического лица и email обратной связи
- UX-референсы и макеты (приложены в artifacts)
