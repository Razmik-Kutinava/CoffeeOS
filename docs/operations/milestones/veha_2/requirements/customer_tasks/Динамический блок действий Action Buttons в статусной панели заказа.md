# Динамический блок действий (Action Buttons) в статусной панели заказа CoffeeOS

**Бизнес-цель**: Заменить статические оранжевые кнопки-плейсхолдеры в правой части нижней статусной панели на динамический контекстный блок действий. Набор кнопок меняется реактивно при смене статуса заказа на табло бариста, предоставляя клиенту именно те быстрые действия, которые актуальны прямо сейчас (Отмена → Чат → Чаевые / Push).

## Глобальные ограничения
- Запрещено изменять общую структуру нижней статусной панели (progress bar с 4 этапами: Принят → Готовится → Готов → ???).
- Запрещено менять цветовую схему: основной фон `#1a1a1a`, акцентный оранжевый `#ff6b35`, зеленый для completed этапов `#4caf50`.
- Запрещено мутировать глобальный стейт заказа напрямую из компонента кнопок (использовать только dispatch/actions).
- Запрещено хардкодить URL интеграций или тексты заглушек (использовать `appConfig` и константы локализации).
- Строгая типизация TypeScript: запрет на использование `any`, все пропсы и возвращаемые значения функций должны быть типизированы интерфейсами.
- Компонент должен быть полностью изолирован (`OrderActionButtons.tsx`) и не должен содержать бизнес-логики маппинга (вынести в чистую функцию-утилиту).

## Сценарии и чек-лист (Для todo.md)
*Каждый пункт — атомарный таск для TDD-цикла: сначала пишется failing-тест, затем минимальный код для его прохождения.*

- [ ] **Шаг 1: Тестирование и реализация SupportChatAdapter**
  - Given: Вызывается функция `openSupportChat(orderId, chatUrl?)`.
  - When: `chatUrl` передан / не передан.
  - Then: При наличии URL вызывается `window.open(url, '_blank')`. При отсутствии URL в консоль пишется лог `[Chat Integration Pending] Order: ${orderId}` (или вызывается fallback-модалка, если предусмотрено конфигом).

- [ ] **Шаг 2: Тестирование и реализация TipsAdapter (нетмонет)**
  - Given: Вызывается функция `openTipsService(orderId, tenantId, tipsUrl?)`.
  - When: `tipsUrl` передан / не передан.
  - Then: При наличии URL вызывается `window.open(url, '_blank')`. При отсутствии URL в консоль пишется лог `[Tips Integration Pending] Order: ${orderId}`.

- [ ] **Шаг 3: Тестирование чистой функции маппинга состояний (ButtonMapper)**
  - Given: Входные параметры `status` ('accepted' | 'paid' | 'preparing' | 'ready') и `hasPushSubscription` (boolean), `isIOS` (boolean).
  - When: Вызывается функция маппинга.
  - Then: Возвращается корректный массив конфигураций кнопок (макс. 2) согласно Матрице состояний:
    - **accepted/paid**: Кнопка 1 — "Отменить заказ" (вторичная), Кнопка 2 — "Включить Push" (Android) / "Добавить в Wallet" (iOS)
    - **preparing**: Кнопка 1 — "Чат с поддержкой", Кнопка 2 — "Оставить чаевые" (если есть подписка) / "Включить Push"
    - **ready**: Кнопка 1 — "Чат с поддержкой", Кнопка 2 — "Оставить чаевые"
    - *Edge case*: Если `hasPushSubscription === false`, Кнопка 2 всегда возвращает Push/Wallet (до статуса ready включительно).

- [ ] **Шаг 4: Статический рендер компонента OrderActionButtons.tsx**
  - Given: Компонент смонтирован с моками пропсов: `status="paid"`, `hasPushSubscription=false`, `isIOS=true`.
  - When: Рендер завершен.
  - Then: В правой части статусной панели (справа от progress bar) присутствуют ровно 2 оранжевые кнопки с текстами "Отменить заказ" и "Добавить в Wallet". Кнопки имеют корректные атрибуты `data-testid`, стилизованы согласно макету (оранжевый фон `#ff6b35`, скругленные углы).

- [ ] **Шаг 5: Реактивное обновление через WebSocket (ActionCable)**
  - Given: Компонент отрендерен со статусом `paid` (видны кнопки "Отмена" + "Push").
  - When: Симулируется получение события WebSocket со статусом `preparing` (бариста нажал "Готовится" на табло).
  - Then: Компонент перерисовывается без перезагрузки страницы. Progress bar обновляется (второй этап подсвечивается зеленым). Кнопка "Отмена" исчезает. Появляются кнопки "Чат с поддержкой" и "Оставить чаевые" (или "Push", если подписки нет).

- [ ] **Шаг 6: Сценарий отмены заказа (Cancel Flow) с обработкой ошибок**
  - Given: Статус `accepted`, пользователь нажимает оранжевую кнопку "Отменить заказ".
  - When: Пользователь подтверждает действие в Confirm Sheet (модальное окно).
  - Then: Отправляется POST-запрос на `/shop/api/orders/:id/cancel`. 
    - При ответе 200: статус локально обновляется на `cancelled`, progress bar показывает отмененное состояние, блок кнопок скрывается.
    - При ответе 400/500 или ошибке сети: показывается Snackbar/Toast с сообщением об ошибке, статус заказа не меняется, кнопки остаются активными.

- [ ] **Шаг 7: Адаптация под мобильные устройства**
  - Given: Приложение открыто на мобильном устройстве (ширина экрана < 768px).
  - When: Компонент OrderActionButtons рендерится.
  - Then: Кнопки остаются кликабельными, не вылазят за пределы экрана, текст кнопок переносится при необходимости. Минимальная высота кнопки 44px (touch target).

## Стратегия тестирования
- **Фреймворк**: Jest + React Testing Library (RTL).
- **Путь к файлам тестов**: 
  - `pwa/src/services/__tests__/SupportChatAdapter.test.ts`
  - `pwa/src/services/__tests__/TipsAdapter.test.ts`
  - `pwa/src/utils/__tests__/orderButtonMapper.test.ts`
  - `pwa/src/components/OrderActionButtons/__tests__/OrderActionButtons.test.tsx`
- **Критические кейсы**:
  - Отсутствие `chatUrl` / `tipsUrl` в конфигурации (проверка fallback-логики).
  - Смена статуса заказа через WebSocket во время выполнения pending-запроса на отмену (блокировка повторных нажатий, состояние `isLoading`).
  - Сетевые ошибки (400, 500, timeout) при вызове API отмены.
  - Корректное определение iOS через `navigator.userAgent` для выбора между Wallet и Web Push.
  - Асинхронность: кнопки не должны блокировать UI при загрузке.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус, покрытие ветвлений логики маппинга ≥ 90%).
2. Линтер (ESLint) и тайпчекер (`tsc --noEmit`) выполняются без ошибок и предупреждений.
3. На макете в правой части статусной панели вместо оранжевых плейсхолдеров рендерятся реальные кнопки с текстом согласно матрице состояний.
4. При смене статуса бариста кнопки меняются на лету через WebSocket без моргания или перезагрузки компонента.
5. Отмена заказа работает до перехода в статус `preparing` и корректно обрабатывает ошибки сети.
6. Клики по «Чат» и «Чаевые» вызывают заготовленные изолированные функции-хэндлеры (готовность к подключению ключей нетмонет и мессенджера в 1 строку конфигурации).
7. Компонент корректно отображается на всех разрешениях экрана (desktop, tablet, mobile).
