## Текст задачи (дословно) — Google Doc Spec

TASK_116: История заказов клиента по всем точкам CODE:BLACK

**Тип:** новая задача (сценарий нигде не зафиксирован)
**Версия:** v5 (2026-10-25)
**Зависит от:** TASK-CODE-BLACK-NETWORK-MEMBERSHIP; TASK-PRODUCTION-RLS-VERIFY-HARDEN (этап 1 обязательно: роль приложения и политики определяют механизм чтения; этап 2 — если RLS действует)
Бизнес-цель: клиент видит в истории и может открыть чеки своих заказов во всех точках сети CODE:BLACK, включая точки разных франчайзи и закрытые точки, и понимает, в какой точке был каждый заказ; без доступа к заказам других клиентов и точек вне сети. Эта задача владеет историей: список, чек, выделение, метка точки. Повтор заказа с проверкой цен определяет TASK-HISTORY-REPEAT-PRICE-CHECK-EXT.

### 1. Карта интеграций — затронуто / нет
Затронуто: серверная выборка истории по клиенту сессии и точкам сети; проверка владельца и членства; API и экран истории ("#/profile"); чтение чека заказа другой точки без смены текущей точки; данные точки в строке и в чеке; выделение заказа по параметру; тесты.
Не затронуто: объединение записей клиентов; платежи, checkout, Quick Repeat, Wallet, FCM; повтор заказа (задача G); смена текущей точки и корзина (задача F); каскад SMS.

Политика "shop_city_lookup" открывает все заказы всех точек без условий: для истории её использовать запрещено; "Rls::GucContext.with_shop_city_lookup" ("app/services/rls/guc_context.rb:20-21,33-41") при вызове внутри внешней транзакции действует до её конца, поэтому в истории не применяется.

### 3. Текущее поведение — факты аудитов
- История: "GET /shop/api/orders/history?page=1&per_page=20" (максимум 50), фильтр по текущей точке и "customer_id" ("orders_controller.rb:113-117", "shopAccountOrders.js:13-16"). Ответ: id, order_number, title, status, total, created_at, items_count; данных о точке нет ("orders_controller.rb:130-138").
- Клиент ("mobile_customers") один на платформу: телефон уникален глобально ("db/schema.rb:452-455"), поля точки нет ("db/schema.rb:433-456"); поиск по телефону и email глобальный ("phone_verified_customer_linker.rb:21", "checkout_identity.rb:43,70"). Разделение по точкам держится на фильтре "orders.tenant_id" и на ячейке сессии по точке ("customer_session.rb:7,22-29"). Комментарий в "customer_session.rb:4" («один телефон — разные customer_id») противоречит схеме и не учитывается.
- Строка → чек: "push('/order/:id/receipt')" ("Profile.svelte:62-64,128"); чек загружается по "GET /orders/:id" с фильтром по текущей точке: заказ другой точки даёт 404 ("orders_controller.rb:28-32", "OrderReceipt.svelte:27-31,118-119"). - Метки точки нет: в шапке только "display_address" ("Header.svelte:71,79,105").
- RLS: при "app.shop_city_lookup = on" политика читает все заказы всех точек, заказы неактивных точек видны на уровне RLS, точки в "tenants" — только активные торговые ("20260918123000_…:5-26", "20260320120001_…:83-86"); роль приложения в production, вероятно, обходит RLS (не проверено).

### 4. Scope
Разрешено: серверный путь истории по заказам клиента сессии в точках, явно включённых в CODE:BLACK; проверка владельца и членства; существующая пагинация или обоснованное изменение; актуальный статус и данные точки в строке и в чеке; чтение чека заказа другой точки без смены текущей точки; выделение заказа; метка закрытой точки; тесты.
Запрещено: объединять или изменять записи клиентов; принимать от клиента список точек или чужой "customer_id"; удалять фильтр "tenant_id" без замены проверяемой границей членства и проверки RLS; считать все точки CoffeeOS сетью; использовать политику "shop_city_lookup" и "with_shop_city_lookup" для истории; использовать "CustomerTenantHistory" как источник заказов; менять OTP-merge и linkers; ослаблять "OrderOwnership" или обходить RLS; менять "historyRepeatAdapter" и поведение «Повторить» (задача G); переключать текущую точку и менять корзину ради просмотра; переписывать общую авторизацию; менять Quick Repeat.
Решения владельца 2026-10-24: R7 А — история показывает клиенту его заказы и чеки во всех точках сети; R8 А — заказы закрытых точек остаются в истории; название точки показывается на каждой строке и в чеке (по умолчанию); выделение заказа до первого касания экрана, максимум 3 секунды (константа). Решение 2026-10-25 (по умолчанию, R11): закрытая точка — любой статус, кроме "active".

### 5. Gherkin

- [ ] Subtask 2 (вне сети): Given заказ клиента в точке вне CODE:BLACK, When открывается история, Then заказ не включается.
- [ ] Subtask 3 (чужие данные): Given другой клиент имеет заказ в точке сети, When текущий клиент запрашивает историю, Then чужой заказ не возвращается; клиент не может передать чужой "customer_id" или список точек.
- [ ] Subtask 4 (чек другой точки): Given клиент открывает чек заказа другой точки сети, When заказ его, Then чек открывается на месте без смены текущей точки и без изменения корзины, с указанием точки; When заказ чужой или точка вне сети, Then сервер не раскрывает заказ и не обходит проверку владельца.
- [ ] Subtask 5 (статус): Given заказ в истории, Then строка содержит актуальный статус, возвращённый сервером.
- [ ] Subtask 6 (пагинация): Given заказов больше одной страницы, When запрашивается следующая, Then история продолжается в порядке убывания даты без пропусков и дублей между точками; лимиты существующего API не обходятся.
- [ ] Subtask 7 (выделение): Given история открыта с параметром целевого заказа ("#/profile?order=<id>"), When заказ есть на загруженной странице, Then он прокручивается в видимую область и обводится контуром до первого касания экрана, но не дольше 3 секунд; When заказа нет на странице, Then выделение пропускается без ошибки, остальные заказы не меняют порядок и статус; маршрут с параметром сопоставляется с маршрутом экрана (покрыто тестом).
- [ ] Subtask 8 (точка в строке и чеке): Given заказ в истории, Then сервер отдаёт данные точки (id, название, отображаемый адрес), And в строке и в чеке показывается название точки.
- [ ] Subtask 9 (закрытая точка): Given точка заказа в сети и её статус не "active", Then заказ остаётся в истории, в строке метка «Точка закрыта» без названия; чек открывается; безопасное чтение неактивных точек определяют этап 1 и этап 2 задачи TASK-PRODUCTION-RLS-VERIFY-HARDEN.
- [ ] Subtask 10 («Повторить»): Given строка истории любой точки сети, Then кнопка «Повторить» доступна, её поведение определяет TASK-HISTORY-REPEAT-PRICE-CHECK-EXT; эта задача её не меняет.
- [ ] Subtask 11 (известное ограничение): Given заказ оформлен под другой записью клиента, Then он в историю текущего клиента не включается; объединение записей вне задачи.
- [ ] Subtask 12 (безопасность выборки): Given запрос истории и чека, Then фильтр по "customer_id" клиента сессии и по списку точек сети применяется в самом запросе независимо от RLS; список точек сети и "customer_id" определяются на сервере.
