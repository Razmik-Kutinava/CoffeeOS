# Интеграция Автоплатежей СБП (Т-Касса) в PWA

Артефакты: `docs/operations/milestones/veha_2/artifacts/tbank_sbp_autopayments_account_token/`

Бизнес-цель: Сократить время чекаута до 1 клика (Zero-Click checkout) для постоянных гостей take-away кофейни, чтобы увеличить пропускную способность точки и возвращаемость клиентов.

## Глобальные ограничения
- **Запрещено** рассчитывать сумму заказа на фронтенде (сумма всегда валидируется и считается на бэкенде).
- **Запрещено** хранить пароль терминала Т-Кассы где-либо, кроме `.env` на бэкенде.
- **Запрещено** удалять `AccountToken` из БД при мягких отказах автоплатежа (недостаточно средств, лимиты). Удаление только по явному запросу пользователя (отвязка) или при фатальных ошибках (счет закрыт).
- **Запрещено** формировать подпись (Token) для Т-Кассы на фронтенде. Строго SHA-256 конкатенация параметров с паролем на бэкенде.
- **Запрещено** использовать сторонние библиотеки для работы с Т-Кассой, если они не покрывают специфичные методы `GetAddAccountQRState` и `ChargeQr` (используем прямые HTTP-запросы к API).

## Сценарии и чек-лист (Для todo.md)

- [ ] Шаг 1: Инициализация первой оплаты с привязкой счета (Setup)
  - **Given:** Пользователь авторизован, корзина сформирована, у пользователя нет сохраненных `AccountToken` в БД. В UI чекаута отображается кастомный чекбокс "Привязать счет для покупок в один клик".
  - **When:** Пользователь активирует чекбокс (`save_sbp_account: true`) и нажимает "Оплатить".
  - **Then:** Фронтенд отправляет POST `/api/payments/init`. Бэкенд вызывает Т-Касса `Init` с `Recurrent=Y`, `Description="..."`, `DATA={"QR":"true"}`. Бэкенд вызывает `GetQr` (или парсит ответ `Init`), получает Deep link. Фронтенд редиректит юзера в банк. При ошибке сети (500/400) на бэкенде — фронтенд показывает Toast "Сервис временно недоступен" и блокирует кнопку.

- [ ] Шаг 2: Обработка Webhook и сохранение AccountToken
  - **Given:** Пользователь успешно оплатил заказ и дал согласие в приложении банка.
  - **When:** Т-Касса отправляет POST-запрос (webhook) на `NotificationURL` со статусом успеха и параметром `RequestKey`.
  - **Then:** Бэкенд валидирует подпись вебхука. Бэкенд вызывает `GetAddAccountQRState` (передавая `TerminalKey`, `Token`, `RequestKey`). Бэкенд получает `AccountToken`. Бэкенд сохраняет `AccountToken` в БД (в массив токенов пользователя, чтобы поддерживать несколько счетов). Бэкенд возвращает HTTP 200 Т-Кассе. При падении БД (500) — вебхук повторяется Т-Кассой (реализовать идемпотентность обработки `RequestKey`).

- [ ] Шаг 3: Zero-Click Checkout (Повторная покупка)
  - **Given:** Пользователь авторизован, в БД есть валидный `AccountToken`. В UI чекаута метод оплаты "Ваш счет СБП" выбран по умолчанию (рендерится логотип СБП).
  - **When:** Пользователь нажимает кнопку "Оплатить".
  - **Then:** Фронтенд отправляет POST `/api/payments/charge` и показывает полноэкранный лоадер. Бэкенд вызывает `Init` (получает `PaymentId`), затем вызывает `ChargeQr` (передавая `PaymentId` и `AccountToken`). При успехе — бэкенд возвращает статус, фронтенд скрывает лоадер и рендерит экран "Заказ оплачен". При ошибке Т-Кассы (400/500) — фронтенд скрывает лоадер и показывает Toast "Ошибка соединения, попробуйте еще раз".

- [ ] Шаг 4: Fallback Flow (Отклонение автоплатежа банком)
  - **Given:** Пользователь нажал "Оплатить" для Zero-Click чекаута.
  - **When:** Бэкенд вызывает `ChargeQr`, но банк отклоняет транзакцию (статус: недостаточно средств, превышен лимит, счет закрыт).
  - **Then:** Бэкенд возвращает специфичный error code (например, `CHARGE_DECLINED`). Фронтенд снимает лоадер. Фронтенд показывает Toast: "Не удалось выполнить быстрый платеж. Пожалуйста, подтвердите оплату вручную". Фронтенд динамически переключает UI на стандартный flow: вызывает `/api/payments/init` (без флага привязки), получает новый QR/Deep link и редиректит в банк. `AccountToken` в БД **не удаляется** (если ошибка не фатальная, например "счет закрыт").

## Стратегия тестирования
- **Фреймворк:** Vitest (для Unit/Integration), Supertest (для API endpoints), React Testing Library (для UI).
- **Путь к файлам тестов:** 
  - Backend: `src/modules/payments/**/*.test.ts`
  - Frontend: `src/components/checkout/**/*.test.tsx`, `src/hooks/**/*.test.ts`
- **Критические кейсы:**
  - Генерация SHA-256 подписи для Т-Кассы (сравнение с эталонными векторами).
  - Идемпотентность обработки вебхуков (повторная отправка `RequestKey` не должна дублировать токены в БД).
  - Асинхронность и таймауты: мокирование задержек ответа `ChargeQr` (проверка, что лоадер не исчезает раньше времени).
  - Edge cases БД: сохранение `AccountToken`, когда у пользователя уже есть 1+ токенов (проверка, что массив расширяется, а не перезаписывается).
  - UI State Machine: переход из состояния `loading` -> `declined` -> `manual_payment_redirect` без потери данных корзины.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус), покрытие бизнес-логики (Init, Webhook, Charge, Fallback) составляет 100%.
2. Линтер (ESLint) и тайпчекер (tsc) выполняются без ошибок.
3. В БД успешно создается и мигрируется таблица/поле для хранения массива `AccountToken` с привязкой к `UserID`.
4. В `.env.example` добавлены все необходимые переменные для Т-Кассы (`TERMINAL_KEY`, `TERMINAL_PASSWORD`).
