# Автоматический возврат платежа (Т-Банк) при отмене заказа в PWA

**Бизнес-цель**: Реализовать функционал автоматического 100% возврата средств через эквайринг Т-Банка при отмене заказа пользователем в PWA, минимизируя нагрузку на службу поддержки и исключая возможность возврата на стадиях, когда заказ уже принят в работу кухней/бариста.

## Глобальные ограничения
- Запрещено передавать объект `Receipt` в payload запроса `/v2/Cancel` (Т-Банк формирует чек возврата автоматически).
- Запрещено изменять существующую логику перехода статусов `preparing`, `ready`, `issued`, кроме добавления валидации на блокировку отмены.
- Запрещено менять существующий механизм генерации `Token` (sha256) для аутентификации запросов к Т-Банку.
- Фронтенд: запрещено использование типа `any` при описании ответов API и пропсов модальных окон (строгий TypeScript).
- Бэкенд: запрещено проводить возвраты для платежей со статусом, отличным от `succeeded` (CONFIRMED).

## Сценарии и чек-лист (Для todo.md)
*Каждый пункт — атомарный таск для TDD-цикла (сначала пишется failing-тест, затем реализация).*

- [ ] **Шаг 1: Бэкенд. Реализация метода отмены в TbankAdapter**
  - Given: Валидные `TerminalKey`, `PaymentId` и настроенный механизм генерации `Token`.
  - When: Вызывается метод `TbankAdapter.cancel_payment(payment_id)`.
  - Then: Отправляется POST-запрос на `https://securepay.tinkoff.ru/v2/Cancel` с корректным JSON-payload (без `Receipt`), и метод возвращает распарсенный успешный ответ (`Success: true`, `ErrorCode: "0"`).

- [ ] **Шаг 2: Бэкенд. Отмена заказа в статусе `pending_payment` (локальная)**
  - Given: Заказ находится в статусе `pending_payment`.
  - When: Вызывается `GuestOrderCancellationService` для этого заказа.
  - Then: Статус заказа меняется на `cancelled`, вызов `TbankAdapter` не происходит, платеж не затрагивается.

- [ ] **Шаг 3: Бэкенд. Успешный автовозврат в статусе `accepted`**
  - Given: Заказ в статусе `accepted`, связанный платеж имеет статус `succeeded`.
  - When: Вызывается `GuestOrderCancellationService` и `TbankAdapter` возвращает `Success: true`.
  - Then: Статус платежа в БД обновляется на `refunded`, статус заказа меняется на `cancelled`.

- [ ] **Шаг 4: Бэкенд. Блокировка отмены в статусах `preparing` / `ready` (защита от обхода)**
  - Given: Заказ находится в статусе `preparing` (или `ready` / `issued`).
  - When: Отправляется прямой API-запрос на отмену заказа (в обход фронтенда).
  - Then: Сервис возвращает ошибку валидации `422 Unprocessable Entity`, статус заказа и платежа остаются без изменений.

- [ ] **Шаг 5: Фронтенд. Маппинг UI-состояний кнопки отмены**
  - Given: Экран деталей заказа в PWA.
  - When: Рендерится компонент действий в зависимости от статуса заказа (`pending_payment`, `accepted`, `preparing`, `ready`).
  - Then: Для `pending_payment` и `accepted` отображается кнопка «Отменить заказ» (для `accepted` с подписью «Вернем 100% суммы»), для `preparing`/`ready` — кнопка «Написать в поддержку».

- [ ] **Шаг 6: Фронтенд. Модальное окно подтверждения для статуса `accepted`**
  - Given: Пользователь нажал «Отменить заказ» при статусе `accepted`.
  - When: Открывается модальное окно.
  - Then: Отображается заголовок «Отменить заказ №{Order_ID}?», текст с суммой возврата `{Sum} ₽`, акцентная кнопка «Да, отменить и вернуть {Sum} ₽» и вторичная «Оставить заказ».

- [ ] **Шаг 7: Фронтенд. Обработка API-запроса отмены и сетевых состояний**
  - Given: Пользователь подтвердил отмену в модальном окне.
  - When: Отправляется запрос на отмену.
  - Then: 
    - *Loading*: Кнопка заблокирована, отображается индикатор загрузки.
    - *Success (200)*: Показывается Toast 🟢 «Заказ отменён. Деньги ушли на возврат и поступят на счет в течение 1–3 дней.», заказ помечается как отмененный.
    - *Error (422/500)*: Показывается Toast 🔴 «Заказ уже взяли в работу, автовозврат недоступен. Пожалуйста, обратитесь в поддержку.», UI-статус заказа принудительно обновляется на «Готовится».

## Стратегия тестирования
- **Фреймворк**: 
  - Backend: RSpec (Ruby on Rails).
  - Frontend: Jest + React Testing Library.
- **Путь к файлам тестов**: 
  - `spec/services/payments/tbank_adapter_spec.rb`
  - `spec/services/shop/guest_order_cancellation_service_spec.rb`
  - `src/components/OrderCancellation/__tests__/OrderCancellationModal.test.tsx`
  - `src/services/__tests__/orderCancellationApi.test.ts`
- **Критические кейсы**:
  - Таймаут или ответ `500/504` от API Т-Банка (должен корректно обрабатываться на бэкенде и пробрасываться как 500 на фронтенд).
  - Race condition: двойной клик по кнопке «Отменить» (должен быть предотвращен блокировкой UI и идемпотентностью/проверкой статуса на бэкенде).
  - Попытка отмены заказа с платежом в статусе `failed` или `refunded` (должна быть отвергнута).
  - Несоответствие суммы в модальном окне и реальной сумме платежа (проверка типизации и форматирования валюты).

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус, покрытие новых сервисов RSpec > 90%).
2. Линтер (RuboCop, ESLint) и тайпчекер (`tsc --noEmit`) выполняются без ошибок и предупреждений.
3. Ручная проверка сценариев в staging-окружении с использованием тестового `TerminalKey` Т-Банка успешна (включая сценарии успеха и имитации 422/500 ошибок).
