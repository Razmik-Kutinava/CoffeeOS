## Текст задачи (дословно) — Google Doc Spec

TASK_119: Проверка и обеспечение безопасности межточечной истории CODE:BLACK в production

**Тип:** новая задача (сценарий нигде не зафиксирован)
**Версия:** v5 (2026-10-25)
Бизнес-цель: подтвердить, что история CODE:BLACK и чеки других точек не раскрывают заказы других клиентов или точек вне сети, и что фактическая конфигурация production RLS соответствует серверной модели авторизации. Два этапа: этап 1 только чтение, этап 2 исправления после отдельного согласования.

### 1. Карта интеграций — затронуто / нет
Затронуто: production PostgreSQL (роли, владельцы таблиц, RLS, политики); таблицы заказов, клиентов и точек; "app.current_tenant_id" и другие GUC; "shop/api/base_controller.rb"; "/o/:hash" и "OrderOwnership"; политика "shop_city_lookup"; "CustomerTenantHistory"; "PhoneVerifiedCustomerLinker"; тесты RLS и изоляции.
Не затронуто: изменение production-данных ради тестирования; отключение RLS или временное расширение доступа; платежи, checkout; SMS-каскад, Wallet, FCM; объединение клиентов.

### 2. Текущее поведение — факты аудитов
- Политики заказов и связанных таблиц основаны на "app.current_tenant_id": миграции "20250115000001_…:139-181", "20260320120001_…:83-150".
- Миграция "20260918123000_add_rls_tenants_shop_city_lookup_policy.rb:21-26": при "app.shop_city_lookup='on'" политика читает все заказы всех точек без условий по точке, статусу заказа или статусу точки; политики складываются через OR с изоляцией по точке; в "tenants" видны только активные торговые точки (":5-26"); заказы неактивных точек видны на уровне RLS, точки нет; отсекает код ("customer_tenant_history.rb:72-83,103-105").
- RLS на "tenants" включён без FORCE (":9"). Если бы роль приложения подчинялась RLS, "Tenant.find_by" в "base_controller.rb:27" без GUC ничего бы не находил: вывод из кода, роль приложения в production, скорее всего, владелец таблиц или обходит RLS, и политики фактически не действуют. Роль БД не проверена.
- Клиент ("mobile_customers") один на платформу, RLS на таблице нет намеренно ("20250115000007_create_stage_7_mobile.rb:69-70"); разделение по точкам держится на фильтре "orders.tenant_id" и ячейке сессии.
- "PhoneVerifiedCustomerLinker#deactivate_empty_guest!" проверяет заказы клиента через "Order.where(customer_id:)" ("phone_verified_customer_linker.rb:71-76"): если RLS применяется к роли, гость с заказами только в другой точке может считаться пустым и быть деактивирован.
- "Rls::GucContext.with_shop_city_lookup": "SET LOCAL" внутри транзакции; при вызове в уже открытой внешней транзакции действует до её конца ("app/services/rls/guc_context.rb:20-21,33-41").
- "shop/api/base_controller.rb:38,48-58": session-level "SET"/"RESET"; ошибка сброса только логируется.
- "/o/:hash" находит заказ без установки tenant-контекста в самом контроллере: "order_short_links_controller.rb:8".
- Тестовая база строится из "schema.rb" без политик, миграция "20260918123000" не применяется ("test/support/rls_test_bootstrap.rb:3,25-36"); тестов политики "shop_city_lookup" и чтения между точками нет.
- Таблица событий окружения (TASK-PUSH-ENV-SNAPSHOT) создаётся без RLS осознанно (решение владельца 2026-10-15), персональных данных не содержит.
- Локальная dev-база эквивалентной production RLS-конфигурации не имеет и безопасность production не доказывает. Атрибуты роли приложения, владельцы таблиц, политики и состояние миграций в production не проверены.

### 3. Scope
Разрешено на этапе 1: read-only запросы к каталогам production (набор ниже); фиксация фактов; сравнение с миграциями и "db:rls:ensure"; проверка путей включения "shop_city_lookup"; проверка сброса GUC и повторного использования соединения; перечень мест кода, рассчитанных на обход RLS; проверка авторизации "/o/:hash", межточечной истории и чека заказа другой точки.
Разрешено на этапе 2 (только после этапа 1 и отдельного Scope): исправления политик, узкий механизм межточечного чтения (заказы и чеки клиента сессии в точках сети, в том числе неактивных, и признак сети), тестовая база с политиками и регрессионные тесты.
Запрещено: изменяющие команды в production на этапе 1; доказывать состояние production локальной базой; отключать RLS или снимать tenant-фильтры; включать применение RLS к роли приложения без перечня мест, рассчитанных на обход (Subtask 10); считать отсутствие доступа доказательством отсутствия уязвимости; менять политики без тестов и обоснованной границы.

### 5. Порядок и набор разрешённых запросов (этап 1, только чтение)
Запрос 1 выполняется под той же ролью, под которой работает приложение ("DATABASE_URL").
```sql
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;
SELECT c.relname, pg_get_userbyid(c.relowner) AS owner, c.relrowsecurity, c.relforcerowsecurity
  FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
  WHERE n.nspname = 'public' AND c.relkind = 'r' ORDER BY c.relname;
SELECT tablename, policyname, permissive, roles, cmd, qual, with_check
  FROM pg_policies WHERE schemaname = 'public' ORDER BY tablename, policyname;
SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 20;
```
Порядок: 1) получить разрешённый read-only доступ; 2) выполнить запросы и сохранить результат; 3) сопоставить с миграциями и конфигурацией; 4) составить перечень доказанных расхождений и мест, рассчитанных на обход; 5) только после этого формировать исправления и тесты (этап 2); 6) проверить изоляцию межточечной истории и существующие RLS-тесты.
Ограничение: если read-only доступ недоступен, задача остаётся на этапе 1; утверждений о фактическом состоянии production не делается.
Статус: этап 1 готов к выполнению; этап 2 не готов.
