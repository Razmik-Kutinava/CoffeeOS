# Интеграция виджета быстрой оплаты Т-Кассы и One-Click сценария в PWA

Артефакты: `docs/operations/milestones/veha_2/artifacts/tbank_widget_oneclick_fallback/`

**Бизнес-цель:** Снизить трение на этапе повторных заказов за счет внедрения механики «Оплатить в клик». Обеспечить удержание пользователя в воронке при отказах эквайринга за счет бесшовного fallback-сценария (инлайн-выбор СБП, сохраненных карт или ввод новой) без потери контекста текущего заказа.

## Глобальные ограничения

- **Запрещено** принимать или использовать сумму заказа, переданную с клиента. Сумма должна запрашиваться исключительно из БД на бэкенде по `orderId`.
- **Запрещено** инвалидировать данные корзины и `orderId` при переходе в fallback-сценарий.
- **Обязательно** передавать параметр `"connection_type": "Widget"` в объекте `DATA` при вызове метода `Init` API Т-Кассы.
- **Зависимости:** `TerminalKey` и креды API Т-Кассы должны читаться из переменных окружения (`.env`).

## Сценарии и чек-лист (Для todo.md)

- [ ] **Шаг 1: Бэкенд. Валидация и инициализация сессии (`POST /api/v1/payments/init`)**
  - **Given:** Получен запрос с `orderId` и токеном сессии.
  - **When:** Бэкенд обрабатывает запрос.
  - **Then:** Бэкенд игнорирует любую сумму из payload, запрашивает итоговую сумму из БД по `orderId`. При отсутствии заказа возвращает 404. При успехе формирует запрос к API Т-Кассы с `"connection_type": "Widget"`.

- [ ] **Шаг 2: Бэкенд. Обработка ответа от Т-Кассы и возврат клиенту**
  - **Given:** Успешный ответ от API Т-Кассы на метод `Init`.
  - **When:** Бэкенд формирует ответ для фронтенда.
  - **Then:** Возвращается JSON `{ "paymentUrl": "https://securepayments.tinkoff.ru/..." }`. При ошибке сети (500) или неверных кредах (400) возвращается стандартизированная ошибка без утечки внутренних деталей.

- [ ] **Шаг 3: Фронтенд. Инъекция и инициализация SDK Т-Кассы**
  - **Given:** Пользователь открывает главный экран или меню с блоком истории заказов («повторить»).
  - **When:** Компонент списка прошлых заказов монтируется.
  - **Then:** Официальный скрипт Т-Кассы инжектируется в `<head>`. Вызывается `PaymentIntegration.init(initConfig)` с `terminalKey` из `.env`. Ошибки загрузки скрипта логируются (тихая деградация).

- [ ] **Шаг 4: Фронтенд. Пайплайн «Оплатить в клик» и инлайн-лоадер (State Management)**
  - **Given:** Пользователь видит карточку прошлого заказа в блоке «повторить» и нажимает кнопку «оплатить в клик».
  - **When:** Инициируется процесс оплаты для конкретного заказа.
  - **Then:** Интерфейс карточки блокируется (prevent double-tap). Под карточкой появляется оранжевая инлайн-плашка с текстом «статусы от банка» (выполняет роль лоадера). Инициируется запрос к `POST /api/v1/payments/init` (или напрямую `Charge`, если это рекуррент). При успехе выполняется транзакция.

- [ ] **Шаг 5: Фронтенд. Fallback Flow 1 — Выбор альтернативы при ошибке**
  - **Given:** Получен статус ошибки списания (недостаточно средств, отказ эмитента) или требуется ручной выбор способа.
  - **When:** Обрабатывается статус отказа под карточкой заказа.
  - **Then:** Плашка «статусы от банка» обновляется, информируя об ошибке. Под ней динамически появляются две кнопки выбора метода: **«СБП»** и **«карта +»** (как показано на макете). Контекст заказа (`orderId`) сохраняется.

- [ ] **Шаг 6: Фронтенд. Fallback Flow 2 — Развертывание сохраненных карт и ввод новой**
  - **Given:** В fallback-сценарии пользователь нажал на кнопку **«карта +»**.
  - **When:** Отрисовывается интерфейс выбора карт.
  - **Then:** Блок расширяется (expanded state), показывая список ранее сохраненных карт (например, `Картой *1594`, `Картой *1567`). Также предусмотрен переход к экрану ввода новой карты — появляется форма ввода (Номер, MM/YY, CVC) с обязательным свитчером (toggle) **«Использовать карту для будущих заказов»**.

- [ ] **Шаг 7: Фронтенд. Платформенная адаптивность и вызов виджета**
  - **Given:** Пользователь выбирает метод оплаты (СБП или новую карту) на разных ОС.
  - **When:** Отрисовываются методы оплаты.
  - **Then:** Механика СБП и виджет оплаты корректно отрабатывают редиректы. На iOS виджет корректно деградирует (Mir Pay скрыт).

## Стратегия тестирования

- **Фреймворк:** Jest / Vitest + React Testing Library (Frontend), Jest + Supertest (Backend).
- **Путь к файлам тестов:** 
  - Backend: `src/api/v1/payments/__tests__/init.spec.ts`
  - Frontend: `src/components/order-history/payment-flow/__tests__/`
- **Критические кейсы:**
  - Проверка, что клик по «оплатить в клик» корректно триггерит появление плашки «статусы от банка» именно под нужным элементом списка.
  - Проверка корректного расширения блока (expanded) при клике на «карта +» и рендера списка маскированных сохраненных карт.
  - Эмуляция ошибки транзакции не должна перебрасывать юзера на отдельную страницу чекаута — весь fallback должен происходить инлайн в карточке заказа.
  - Проверка корректной работы toggle «Использовать карту для будущих заказов».

## Exit Criteria (Критерии выхода)

1. Все тесты проходят (зеленый статус). Линтер и тайпчекер (tsc) выполняются без ошибок.
2. Логика UI полностью соответствует макетам: лоадер («статусы от банка») и флоу восстановления (кнопки СБП / Карта → сохраненные карты → форма с тогглом) работают инлайн в блоке истории заказов.
3. В сетевых запросах к Т-Кассе на инициализацию строго присутствует `"connection_type": "Widget"`.
