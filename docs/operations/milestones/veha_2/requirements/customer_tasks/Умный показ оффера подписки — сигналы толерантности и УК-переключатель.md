Задача: Умный показ оффера подписки — сигналы толерантности + УК-переключатель

Бизнес-цель: Показывать оффер подписки на статусе `ready` только тем гостям, которые уже продемонстрировали минимальную вовлечённость в продукт, сохраняя возможность управлять включением оффера и порогом толерантности на уровне конкретной точки.

## 1. Связь с картой интеграций

- **Затронутые сервисы из `@INTEGRATIONS.md`:**
  - `docs/integrations/pwa-realtime.md` — CTA state machine, push/FCM и передача состояния заказа.
  - `docs/integrations/shop-api.md` — `profile/config`, через который фронту передаётся eligibility.
  - Существующий `POST /orders/:id/email` — источник сигнала `email_collected_at`.
  - Существующий FCM registration flow — источник сигнала `push_enabled_at`.

- **Новые изменения интеграционного контракта:**
  - Shop должен передавать на backend факт успешной установки PWA через событие `appinstalled`.
  - Backend должен возвращать Shop агрегированный флаг `eligible_for_subscription_offer`.
  - УК должен иметь API для чтения и изменения point-scoped настроек оффера.

- **Смежные модули, которые НЕЛЬЗЯ ломать:**
  - существующий `orders_count` в `profile_json`;
  - `orderStatusCtaMachine.js` — сохранить текущую логику чатов, уведомлений и чаевых;
  - существующий FCM registration flow;
  - `POST /orders/:id/email`;
  - реализацию чаевых;
  - PWA install banner `ShopPwaBanner.svelte`;
  - `Payments::TbankAdapter`;
  - фискализацию;
  - `promo_point_settings` и 11₽-промо;
  - архитектуру подписки и биллинг.

## 3. Сценарии и Чек-лист (Gherkin)

- [ ] **Subtask 1: Добавить хранение сигналов вовлечённости**
  - Given: `mobile_customer` существует.
  - When: применяется миграция.
  - Then: доступны nullable timestamps `pwa_installed_at`, `push_enabled_at`, `email_collected_at`; существующие записи не теряют данные.

- [ ] **Subtask 2: Реализовать `completed_orders_count` без изменения `orders_count`**
  - Given: у клиента есть заказы со статусами `issued`, `closed`, `cancelled`, `pending_payment`.
  - When: backend вычисляет количество завершённых заказов.
  - Then: учитываются только `issued` и `closed`; существующий `orders_count` остаётся без изменений.

- [ ] **Subtask 3: Зафиксировать первый `pwa_installed_at`**
  - Given: клиент ещё не имеет `pwa_installed_at`.
  - When: backend получает событие успешной установки PWA.
  - Then: `pwa_installed_at` заполняется текущим временем.
  - And: повторное событие не перезаписывает первоначальное значение.

- [ ] **Subtask 4: Зафиксировать первый `push_enabled_at`**
  - Given: клиент успешно регистрирует FCM token.
  - When: существующий registration flow завершается успешно.
  - Then: `push_enabled_at` заполняется текущим временем только при первом успешном включении push.
  - And: повторная регистрация token не меняет первоначальное значение.

- [ ] **Subtask 5: Зафиксировать первый `email_collected_at`**
  - Given: клиент сохраняет email через существующий `POST /orders/:id/email`.
  - When: email успешно сохранён.
  - Then: `email_collected_at` заполняется текущим временем только при первом успешном сохранении.
  - And: существующая функциональность email collection не меняется.

- [ ] **Subtask 6: Добавить модель `subscription_offer_settings`**
  - Given: точка существует.
  - When: применяется миграция.
  - Then: для точки может существовать одна конфигурация с `enabled`, `min_completed_orders`, `required_signals_count` и режимом второй CTA.
  - And: настройки изолированы по `point_id`.

- [ ] **Subtask 7: Реализовать `SubscriptionOfferEligibility.check(customer, point)`**
  - Given: для точки задана конфигурация eligibility.
  - When: проверяется клиент.
  - Then: eligibility равен `true` только если `completed_orders_count >= min_completed_orders` и количество заполненных сигналов >= `required_signals_count`.
  - And: учитываются только `pwa_installed_at`, `push_enabled_at`, `email_collected_at`.
  - And: дефолт `required_signals_count = 1`.
  - And: значение не должно быть жёстко зашито в коде.

- [ ] **Subtask 8: Реализовать валидацию диапазона `required_signals_count`**
  - Given: доступно три сигнала вовлечённости.
  - When: сохраняется `required_signals_count`.
  - Then: принимаются значения от `1` до `3`.
  - And: некорректное значение отклоняется с `400`.

- [ ] **Subtask 9: Добавить API-флаг eligibility**
  - Given: клиент запрашивает существующий `profile/config`.
  - When: backend рассчитывает состояние клиента для текущей точки.
  - Then: response содержит `eligible_for_subscription_offer: boolean`.
  - And: значение рассчитывается сервером, а не доверяется frontend.

- [ ] **Subtask 10: Добавить API настроек оффера для УК**
  - Given: администратор имеет доступ к точке.
  - When: он читает или изменяет настройки оффера.
  - Then: API возвращает/сохраняет `enabled`, `second_cta_mode`, `min_completed_orders`, `required_signals_count`.
  - And: настройки применяются только к выбранной точке.

- [ ] **Subtask 11: Реализовать УК-переключатель второй CTA**
  - Given: администратор открывает настройки точки.
  - When: выбирает режим `Чаевые` или `Подписка`.
  - Then: выбранный `second_cta_mode` сохраняется для конкретной точки.

- [ ] **Subtask 12: Реализовать настройку порога толерантности в УК**
  - Given: администратор открывает advanced-настройки оффера.
  - When: меняет `required_signals_count`.
  - Then: значение сохраняется и используется backend eligibility.
  - And: при значении `2` клиент с одним сигналом не считается eligible.

- [ ] **Subtask 13: Отправлять `appinstalled` на backend из Shop**
  - Given: браузер успешно завершил установку PWA.
  - When: срабатывает `appinstalled`.
  - Then: Shop отправляет backend событие установки.
  - And: ошибка отправки события не ломает пользовательский интерфейс или текущий PWA flow.

- [ ] **Subtask 14: Расширить `orderStatusCtaMachine.js`**
  - Given: заказ находится в статусе `ready`.
  - When: `second_cta_mode = subscription` и `eligible_for_subscription_offer = true`.
  - Then: второй CTA отображает оффер подписки вместо чаевых.

- [ ] **Subtask 15: Сохранить существующее поведение при выключенном переключателе**
  - Given: `subscription_offer_settings.enabled = false` либо настройки отсутствуют.
  - When: заказ переходит в `ready`.
  - Then: используется существующая логика второй CTA без оффера подписки.

  - Then: оффер подписки не отображается.

  - When: заполнен ровно один из `pwa_installed_at`, `push_enabled_at`, `email_collected_at`.

## Умный показ оффера подписки — изменения в связке Shop ↔ Backend ↔ УК

### PWA / Shop → Backend

- **Точка входа:** новый backend endpoint для фиксации успешной установки PWA.
- **Trigger:** браузерное событие `appinstalled`.
- **Identity Mapping:** текущий идентификатор гостя/`mobile_customer` должен использоваться существующим механизмом идентификации Shop; новый endpoint не создаёт отдельную customer identity.
- **Handling Errors:** ошибка отправки telemetry-сигнала не должна блокировать текущий PWA flow или UI.
- **Idempotency:** `pwa_installed_at` устанавливается только при первом успешном событии и не перезаписывается.

### Push → Backend

- **Точка входа:** существующий FCM token registration flow.
- **Identity Mapping:** зарегистрированный FCM token связывается с существующим `mobile_customer`.
- **Handling Errors:** `push_enabled_at` фиксируется только после успешной регистрации token.
- **Idempotency:** повторная регистрация token не перезаписывает первоначальное значение `push_enabled_at`.

### Email → Backend

- **Точка входа:** существующий `POST /orders/:id/email`.
- **Identity Mapping:** email сохраняется для существующего клиента/заказа; после успешного сохранения фиксируется `mobile_customer.email_collected_at`.
- **Handling Errors:** при неуспешном сохранении email `email_collected_at` не устанавливается.
- **Idempotency:** первое успешное сохранение фиксирует timestamp; последующие сохранения не меняют его.

### Shop API → Eligibility

- **Точка входа:** существующий `profile/config` API.
- **Identity Mapping:** текущий клиент + текущая `point_id` используются для расчёта eligibility.
- **Response Contract:** backend возвращает `eligible_for_subscription_offer: boolean`.
- **Source of truth:** eligibility вычисляется backend через `SubscriptionOfferEligibility`; frontend не рассчитывает его самостоятельно.
- **Handling Errors:** при невозможности получить eligibility нельзя считать клиента eligible по умолчанию.

### УК → Subscription Offer Settings

- **Точка входа:** API CRUD настроек `subscription_offer_settings`.
- **Identity Mapping:** `point_id` → настройки оффера конкретной точки.
- **Configuration:** `enabled`, `second_cta_mode`, `min_completed_orders`, `required_signals_count`.
- **Handling Errors:** невалидные пороги отклоняются с `400`; настройки одной точки не должны влиять на другую.

### Shop CTA

- **Точка входа:** существующая `orderStatusCtaMachine.js`, статус `ready`.
- **Условие показа:** `enabled = true` + `second_cta_mode = subscription` + `eligible_for_subscription_offer = true`.
- **Fallback:** поведение при `second_cta_mode = subscription`, но `eligible = false`, должно быть согласовано до реализации.
- **Совместимость:** существующие chat/notification/tips CTA не должны менять поведение при выключенном переключателе подписки.

### Не входит в интеграционный контракт этой задачи

- `Payments::TbankAdapter`;
- фискализация;
- `promo_point_settings`;
- 11₽-промо;
- subscription billing;
- `subscription_plans`;
- `subscriptions`.
