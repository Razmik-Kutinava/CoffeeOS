# Задача: Архитектура подписки — планы, биллинг и автосписание

**CBR:** #78 · **Дата intake:** 2026-09-05  
**Артефакты:** `docs/operations/milestones/veha_2/artifacts/subscription_billing_architecture/`  
**Группа:** Витрина / PWA / Payments — подписка (plans + billing + recurring)

---

Задачи-3: Архитектура подписки: subscription_plans, subscriptions, автосписание

Бизнес-цель: Запустить пилотную подписку для гостей PWA с недельной оплатой, лимитом льготных напитков, скидкой после исчерпания лимита и opt-out автопродлением через сохранённый способ оплаты. Подписка должна работать независимо от точки покупки и использования, а цена и лимиты должны быть конфигурируемыми через БД.

## 1. Связь с картой интеграций
- **Затронутые сервисы из `@INTEGRATIONS.md`:**
  - `Payments::TbankAdapter`
  - Shop API
  - PWA realtime / CTA state machine
- **Смежные модули, которые НЕЛЬЗЯ ломать:**
  - существующий checkout flow;
  - привязка карт и сохранённые способы оплаты;
  - RebillId/SBP token;
  - антифрод;
  - фискализация;
  - текущая корзина и расчёт стоимости заказа;
  - eligibility и сигналы вовлечённости;
  - TelegramAlertJob / AlertService.
- **Ключевой принцип интеграции:** `Payments::TbankAdapter` остаётся единой точкой входа для платёжных вызовов. Новый recurring-flow не должен дублировать Init/Charge.
- **Webhook idempotency:** `tbank:callback:{PaymentId}:{Status}` обязателен для recurring-flow.

## 3. Сценарии и Чек-лист (Gherkin)

### Модель данных

- [ ] **Subtask 1: Создать модель плана подписки**
  - Given: В системе отсутствует `subscription_plans`.
  - When: Создаётся схема хранения планов.
  - Then: План содержит `code`, `price`, `currency`, `period_days`, `drink_limit`, `discount_price_per_drink`, `over_limit_discount_percent`, `launch_price_valid_until`, `active`, timestamps.

- [ ] **Subtask 2: Создать модель подписки**
  - Given: Существует активный customer и subscription plan.
  - When: Создаётся подписка.
  - Then: Сохраняются `customer_id`, `plan_id`, `purchase_point_id`, `status`, период, параметры периода, `auto_renew` и `payment_method_id`.

- [ ] **Subtask 3: Зафиксировать параметры плана на начало периода**
  - Given: Подписка создаётся или начинается новый период.
  - When: Инициализируется период подписки.
  - Then: `price_at_period_start`, `drink_limit_at_period_start` и `discount_percent_at_period_start` фиксируют значения актуального плана на начало периода.

- [ ] **Subtask 4: Создать события использования подписки**
  - Given: Активная подписка используется в заказе.
  - When: Применяется льготная цена или скидка подписки.
  - Then: Создаётся `subscription_usage_events` с `subscription_id`, `order_id`, фактическим `point_id`, применённой ценой и экономией.

### Покупка подписки

- [ ] **Subtask 5: Реализовать user-initiated покупку подписки**
  - Given: Гость eligible для оффера и доступен активный план.
  - When: Гость оплачивает подписку через обычный checkout flow.
  - Then: Используется `Payments::TbankAdapter`, создаётся подписка со статусом `active`, начинается новый период и `drinks_used_this_period = 0`.

- [ ] **Subtask 6: Покрыть покупку подписки тестом**
  - Given: Валидный customer и активный subscription plan.
  - When: `Subscriptions::PurchaseService` успешно завершает покупку.
  - Then: Создаётся корректная запись подписки с зафиксированными параметрами периода.

### Цена и использование

- [ ] **Subtask 7: Реализовать единый reader параметров подписки**
  - Given: В `subscription_plans` заданы цена и лимиты.
  - When: Бизнес-логика подписки запрашивает параметры.
  - Then: Цена, лимит и процент скидки читаются из БД через единый метод-ридер, без дублирующих констант.

- [ ] **Subtask 8: Покрыть reader тестом на override**
  - Given: В БД значение параметра отличается от стандартного значения.
  - When: Pricing-код получает параметр через reader.
  - Then: Используется значение из БД, а не захардкоженная константа.

- [ ] **Subtask 9: Реализовать лимитную цену фильтр-кофе**
  - Given: Активная подписка и `drinks_used_this_period < drink_limit_at_period_start`.
  - When: В заказ добавляется подходящий SKU фильтр-кофе.
  - Then: Для напитка применяется `discount_price_per_drink = 119₽`, счётчик использования увеличивается на 1 и создаётся usage event.

- [ ] **Subtask 10: Реализовать over-limit скидку**
  - Given: `drinks_used_this_period >= drink_limit_at_period_start`.
  - When: Гость добавляет товар из меню.
  - Then: Применяется `over_limit_discount_percent` от текущей цены товара с округлением по правилу `...9₽`.

- [ ] **Subtask 11: Проверить point-agnostic использование**
  - Given: Подписка куплена в точке A.
  - When: Льготный товар приобретается в точке B.
  - Then: Цена подписки применяется, а `subscription_usage_events.point_id` содержит точку B.

- [ ] **Subtask 12: Проверить сгорание неиспользованного лимита**
  - Given: Текущий период завершён, использовано меньше полного лимита.
  - When: Начинается новый период.
  - Then: `drinks_used_this_period` сбрасывается в `0`, остаток напитков не переносится.

### Отмена и автопродление

- [ ] **Subtask 13: Реализовать отмену без использования**
  - Given: `drinks_used_this_period = 0`.
  - When: Гость отменяет подписку.
  - Then: Подписка переходит в `canceled`, создаётся Telegram-алерт администратору на ручной возврат.

- [ ] **Subtask 14: Реализовать отключение автопродления после использования**
  - Given: `drinks_used_this_period >= 1`.
  - When: Гость отключает автопродление.
  - Then: `auto_renew = false`, текущий период продолжает действовать до `current_period_end`, новое списание не выполняется.

- [ ] **Subtask 15: Реализовать сервис merchant-initiated продления**
  - Given: У подписки наступил `current_period_end` и `auto_renew = true`.
  - When: Запускается `Subscriptions::RenewalService`.
  - Then: Выполняется фоновое списание через `Payments::TbankAdapter` без использования `RecurrentOrderCreator`.

- [ ] **Subtask 16: Обработать успешное продление**
  - Given: Фоновое списание успешно завершено.
  - When: `RenewalService` обрабатывает результат.
  - Then: Создаётся новый период, счётчик использования сбрасывается, а параметры нового периода фиксируются из актуального плана.

- [ ] **Subtask 17: Обработать 3DS при фоновом продлении**
  - Given: Т-Банк возвращает `3DS_CHECKING` или аналогичный статус, требующий участия пользователя.
  - When: Продолжить платёж без активной пользовательской сессии невозможно.
  - Then: Подписка переводится в `past_due` и не остаётся в неопределённом состоянии.

- [ ] **Subtask 18: Реализовать уведомление о необходимости подтверждения**
  - Given: Подписка получила `past_due` из-за невозможности завершить 3DS.
  - When: Состояние обрабатывается системой.
  - Then: Гость получает уведомление с призывом подтвердить оплату, а использование льготной цены приостанавливается.

- [ ] **Subtask 19: Реализовать подтверждение оплаты**
  - Given: Подписка находится в `past_due`.
  - When: Гость вызывает `confirm_payment` и успешно подтверждает платёж.
  - Then: Подписка возвращается в рабочее состояние с корректным периодом и доступом к льготной цене.

- [ ] **Subtask 20: Реализовать idempotency webhook recurring-flow**
  - Given: Один и тот же webhook Т-Банка может быть доставлен повторно.
  - When: Обрабатывается повторный callback с теми же `PaymentId` и `Status`.
  - Then: Повторная доставка не создаёт дублирующее состояние или повторное начисление.

## Архитектура подписки — изменения в интеграционной связке

### Т-Банк
- **Точки входа:** Существующий `Payments::TbankAdapter` используется как единая точка входа для user-initiated покупки и merchant-initiated продления. Новый subscription-код не дублирует Init/Charge.
- **Identity Mapping:** Subscription связывает внутренний `customer_id` с `payment_method_id`; для recurring-списания используется сохранённый способ оплаты с `RebillId`/SBP token.
- **Handling Errors:** Успешное списание запускает новый период. `3DS_CHECKING` или аналогичный статус, требующий пользователя, переводит подписку в `past_due`; при полном отказе подписка не должна оставаться в неопределённом состоянии. Подтверждение выполняется через `confirm_payment`.
- **Idempotency:** Для webhook используется ключ `tbank:callback:{PaymentId}:{Status}`.
- **Refund:** Автоматический Refund не реализуется; при отмене без использования создаётся Telegram-алерт администратору для ручного возврата.
- **Security:** Используется существующий `Payments::TbankAdapter`; платёжные секреты и credentials не дублируются в subscription-сервисах.

### Shop API
- **Точки входа:** `GET /shop/api/subscriptions/current`, `POST /shop/api/subscriptions`, `PATCH /shop/api/subscriptions/current/auto_renew`, `POST /shop/api/subscriptions/current/cancel`, `POST /shop/api/subscriptions/current/confirm_payment`.
- **Identity Mapping:** API работает с текущим авторизованным customer и его subscription.
- **Handling Errors:** Некорректные операции над отсутствующей/неактивной подпиской возвращают соответствующую ошибку API; состояние `past_due` возвращается явно.
- **Security:** Используется существующий механизм авторизации Shop API.

### PWA realtime / CTA state machine
- **Точки входа:** CTA на статусе заказа `ready`.
- **Identity Mapping:** `eligible_for_subscription_offer` определяет доступность subscription CTA для текущего гостя.
- **Handling Errors:** CTA подписки ведёт на реальный экран оформления; переход на subscription stub через `/#/profile` не используется. `tips` удаляется из CTA-матрицы.
- **Security:** Новых внешних credentials или интеграционных секретов не добавляется.
