# Связка профилей Email ↔ Phone и управление данными пользователя в PWA 

Бизнес-цель: Исключить дублирование аккаунтов в таблице `mobile_customers`, реализовать логику бесшовного объединения (Merge) данных одного пользователя при авторизации через разные каналы и предоставить интерфейс управления контактами в PWA.

## Глобальные ограничения
- Запрещено физическое удаление записей в `mobile_customers` при слиянии (использовать мягкое удаление: `is_active: false` или аналогичный статус).
- Запрещено терять историю заказов, привязанные карты и данные корзины целевого профиля при слиянии.
- Запрещено менять существующую схему базовой аутентификации (использовать текущие механизмы OTP).
- Строго сохранять существующие нейминги сущностей: `mobile_customers`, `Shop::OrderCreator`.

## Сценарии и чек-лист (Для todo.md)

### Бэкенд: API и логика слияния
- [ ] Шаг 1: Реализовать GET эндпоинт профиля
  - Given: Пользователь авторизован.
  - When: Отправлен запрос `GET /shop/api/profile`.
  - Then: Возвращается статус 200 и JSON с полями: `id`, `email`, `email_verified`, `phone`, `phone_verified`, `first_name`, `last_name`. При ошибке авторизации — 401.
- [ ] Шаг 2: Реализовать PATCH эндпоинт обновления профиля
  - Given: Пользователь авторизован, валидные данные имени/фамилии.
  - When: Отправлен запрос `PATCH /shop/api/profile` с новыми данными.
  - Then: Статус 200, данные в `mobile_customers` обновлены. При невалидных данных — 422.
- [ ] Шаг 3: Реализовать POST `/shop/api/profile/link_email` (Сценарий А: Чистое привязывание)
  - Given: Пользователь авторизован по телефону, вводимый email отсутствует в других записях `mobile_customers`, OTP подтвержден.
  - When: Отправлен запрос `POST /shop/api/profile/link_email`.
  - Then: Email записан в текущую карточку, `email_verified: true`, статус 200.
- [ ] Шаг 4: Реализовать POST `/shop/api/profile/link_email` (Сценарий Б: Конфликт/Дубликат)
  - Given: Пользователь авторизован по телефону, вводимый email уже принадлежит другой записи в `mobile_customers`, OTP подтвержден.
  - When: Отправлен запрос `POST /shop/api/profile/link_email`.
  - Then: История заказов, карты и корзина старой записи перенесены в текущую; старая запись помечена `is_active: false`; текущая запись получает email и `email_verified: true`; статус 200.
- [ ] Шаг 5: Реализовать POST `/shop/api/profile/link_phone` (Сценарии А и Б)
  - Given: Пользователь авторизован по email, вводимый телефон отсутствует или принадлежит другой записи, OTP подтвержден.
  - When: Отправлен запрос `POST /shop/api/profile/link_phone`.
  - Then: Применяется логика Шага 3 или Шага 4 зеркально для телефона; статус 200.
- [ ] Шаг 6: Интеграция сквозной подстановки в `Shop::OrderCreator`
  - Given: Авторизованный пользователь имеет подтвержденный email и/или phone в `mobile_customers`.
  - When: Вызывается сервис создания заказа `Shop::OrderCreator`.
  - Then: В создаваемый заказ автоматически подставляются подтвержденные email и phone из профиля пользователя.

### Фронтенд: PWA UI/UX
- [ ] Шаг 7: Экран «Профиль пользователя» (Отображение)
  - Given: Пользователь на экране профиля.
  - When: Экран загружается.
  - Then: Отображаются email и телефон со статусом (Галочка «Подтвержден» или кнопка «Привязать»), доступны поля для редактирования имени и фамилии. При ошибке сети (500) — показан тост-уведомление.
- [ ] Шаг 8: Флоу «Допривязать второй контакт»
  - Given: Пользователь нажимает «Добавить телефон» или «Добавить Email» в профиле.
  - When: Пройден короткий OTP-вход (SMS/Flash Call/Email) успешно.
  - Then: Контакт привязывается к текущему аккаунту, UI обновляется без разлогина или перезагрузки страницы. При неверном OTP — 400 и сообщение об ошибке.
- [ ] Шаг 9: Автозаполнение в корзине / чекауте
  - Given: Пользователь переходит на экран оформления заказа.
  - When: Экран чекаута рендерится.
  - Then: Поля «Имя», «Телефон» и «Email» автоматически заполнены данными из профиля. Если контакт отсутствует, при его ручном вводе появляется предложение «Сохранить в профиль».

## Стратегия тестирования
- **Фреймворк:** RSpec (Backend), Vitest/Jest + Playwright/Cypress (Frontend).
- **Путь к файлам тестов:** 
  - Backend: `spec/requests/shop/api/profile_spec.rb`, `spec/services/shop/order_creator_spec.rb`
  - Frontend: `src/features/profile/__tests__/`, `e2e/checkout-profile-fill.spec.ts`
- **Критические кейсы:**
  - Race condition: одновременные запросы на слияние (link) с двух разных сессий одного пользователя.
  - Слияние профилей с большой историей заказов (проверка целостности внешних ключей).
  - Обработка сетевых ошибок (400 Bad Request при неверном OTP, 500 Internal Server Error) на всех POST/PATCH эндпоинтах.
  - Асинхронное обновление UI в PWA после успешного связывания контактов без перезагрузки.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус, покрытие критических путей > 90%).
2. Линтер и тайпчекер (tsc / rubocop) выполняются без ошибок и предупреждений.
3. Реализовано бесшовное слияние: при входе по телефону пользователя с существующим email аккаунты корректно объединяются, история заказов не теряется.
4. В PWA в настройках приложения виден статус привязки каналов связи и работает флоу добавления недостающего контакта.
5. Покупателю не нужно заново вводить имя, телефон или email при повторных заказах — данные подтягиваются из профиля через `Shop::OrderCreator`.
