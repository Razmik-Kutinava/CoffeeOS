# Интеграция статусной модели в компактную шторку PWA и Push-уведомления из POS

Артефакты: `docs/operations/milestones/veha_2/artifacts/order_status_compact_sheet_push/`

**Бизнес-цель:** Обеспечить бесшовный трекинг активных заказов в PWA (на главном экране и в карточке товара) исключительно в процессе их приготовления. Когда бариста переводит заказ в статус `ready`, карточка уходит с табло бариста и одновременно исчезает из PWA, а гость получает push-уведомление о том, что заказ готов и его можно забрать.

## Глобальные ограничения
- **UI/UX:** Статусная модель отображается в виджете *только* для заказов в статусах `accepted`, `paid`, `preparing`. При достижении статуса `ready` виджет полностью исчезает.
- **UI/UX (Неблокирующий интерфейс):** Виджет не перекрывает навигацию и клики по карточкам товаров (корректная обработка `z-index` и `pointer-events`).
- **Бэкенд (БД):** Запрещено ломать базовую схему таблицы `orders`. Допускается добавление колонки `ready_notified_at` для защиты от повторных пушей.
- **Связь (Real-time):** Использовать исключительно штатный ActionCable для бродкастинга из POS в PWA.
- **Асинхронность:** Все отправки пушей и тяжелые операции — строго через фоновые задачи ActiveJob (Sidekiq / GoodJob), без блокировки ответа для POS-терминала.

## Сценарии и чек-лист (Для todo.md)

### Блок A — Динамический виджет заказов в PWA (Показ только во время готовки)

- [ ] Шаг A1: ActionCable-канал OrderStatusChannel
  - **Given:** Заказ перешёл в статус `preparing` на табло бариста.
  - **When:** POS-терминал отправляет запрос на смену статуса.
  - **Then:** Сервер сохраняет статус и `OrderStatusChannel` бродкастит событие `{ order_id, status }` на клиент.
  - *Обработка ошибок:* Если сохранение падает (500), бродкаст не происходит, POS показывает ошибку сети.

- [ ] Шаг A2: Отображение в процессе готовки, авто-скрытие при ready и скролл (Multi-order)
  - **Given:** У пользователя есть заказы в статусах принятия/оплаты/подготовки.
  - **When:** Приходят обновления статусов через WebSocket.
  - **Then:** 
    1. Виджет отображается на главном экране и в карточке товара только пока идет процесс.
    2. Если активных заказов в работе > 2, в виджете автоматически включается вертикальный скролл.
    3. При переходе заказа в статус `ready` карточка заказа мгновенно скрывается из PWA.
  - *Обработка ошибок:* При обрыве WS (краш сети) виджет показывает индикатор "Нет связи", каталог и клики по товарам остаются полностью функциональными.

- [ ] Шаг A3: Обработка обрыва связи и реконнекта
  - **Given:** Произошел обрыв и последующее восстановление интернет-соединения в PWA.
  - **When:** WebSocket успешно реконнектится.
  - **Then:** PWA запрашивает актуальное состояние активных (не готовых) заказов через GET-запрос и обновляет виджет без перезагрузки страницы.
  - *Обработка ошибок:* Если API возвращает 404 (заказов нет) или 500 (ошибка сервера), виджет скрывается, выводится toast-уведомление, ретрай по экспоненциальной задержке.

### Блок B — Триггеры Push-уведомлений по переходу в статус ready

- [ ] Шаг B1: Обработчик события OrderStatusChangedEvent
  - **Given:** Бариста нажимает кнопку готовности на планшете.
  - **When:** Статус заказа обновляется на `ready`.
  - **Then:** Модель через `after_update_commit` ставит в очередь асинхронную задачу `ReadyPushJob`.
  - *Обработка ошибок:* Если транзакция БД падает (500), хук не срабатывает, джоба не создается, POS показывает ошибку сохранения.

- [ ] Шаг B2: Пуш при переходе в статус ready («Готов / Заберите»)
  - **Given:** Бариста нажал «Заказ готов» (карточка уходит со слотов табло).
  - **When:** Фоновый воркер обрабатывает `ReadyPushJob`.
  - **Then:** Гостю уходит Web Push (Android) / обновление `.pkpass` (iOS Wallet) с текстом: «Ваш заказ готов, заберите на кассе!».
  - *Обработка ошибок:* Если Push-сервис возвращает 4xx/5xx, ошибка логируется, джоба уходит в retry в Sidekiq. POS-терминал не блокируется.

### Блок C — Защита от спама и дублей (Idempotency)

- [ ] Шаг C1: Флаг ready_notified_at
  - **Given:** Заказ впервые переведён в статус `ready`.
  - **When:** `ReadyPushJob` начинает выполнение.
  - **Then:** В БД фиксируется `ready_notified_at = Time.current`, пуш уходит ровно один раз.
  - *Обработка ошибок:* При race-condition (одновременные клики) используется атомарное обновление БД (`UPDATE ... WHERE ready_notified_at IS NULL`). Если обновление не прошло (конфликт), пуш пропускается, джоба завершается успешно.

## Стратегия тестирования
- **Backend (RSpec):** 
  - Путь: `spec/channels/order_status_channel_spec.rb`, `spec/jobs/ready_push_job_spec.rb`, `spec/models/order_spec.rb`.
  - Покрытие: Бродкасты ActionCable, идемпотентность джоб `ReadyPushJob`, корректность работы хуков `after_update_commit`.
- **Frontend PWA (Vitest + Testing Library):** 
  - Путь: `src/components/OrderStatusWidget/OrderStatusWidget.test.tsx` (или аналогичный).
  - Покрытие: Появление виджета при `preparing` и его полное исчезновение при `ready`. Рендеринг на главном экране и в карточке товара. Эмуляция скролла при количестве активных заказов > 2. Проверка `pointer-events: none` на контейнере виджета (неблокирующий интерфейс).
- **Критические кейсы:** Эмуляция обрыва сети и реконнекта WebSocket, проверка лимитов ретраев в Sidekiq, race-condition при установке `ready_notified_at`.

## Exit Criteria (Критерии выхода)
1. Заказ виден в PWA (главный экран, карточка товара) *только* пока он готовится (статусы `accepted`, `paid`, `preparing`).
2. При смене статуса на `ready` бариста убирает карточку с табло, у гостя скрывается виджет в PWA и отправляется ровно один пуш «Забирайте».
3. При > 2 заказах в работе включается вертикальный скролл внутри виджета, при этом интерфейс каталога остается полностью кликабельным.
4. Все новые тесты проходят (зеленый статус: `bundle exec rspec` и `yarn test`).
5. Линтер и тайпчекер выполняются без ошибок.
