# Интеграция статусной модели в компактную шторку PWA и Push-уведомления из POS

Артефакты: `docs/operations/milestones/veha_2/artifacts/order_status_compact_sheet_push/`

**Бизнес-цель:** Не блокировать пользователя на отдельном экране ожидания заказа. Статусная модель транслируется в сквозную нижнюю шторку PWA (в свернутом состоянии hidden/peek), позволяя клиенту свободно пользоваться каталогом и совершать новые покупки. Смена статусов инициируется бариста в POS, синхронизируется с PWA в реальном времени и сопровождается Push-уведомлениями.

## Глобальные ограничения
- **UI/UX:** Статусная модель отображается как сквозной липкий виджет (Sticky Bar / Bottom Sheet) внизу экрана PWA. Он не должен перекрывать или блокировать навигацию по меню и клики по карточкам товаров.
- **Бэкенд (БД):** Запрещено изменять базовую схему таблицы `orders` (структура поля `status` и основные связи не трогаются). *Примечание: для Шага C1 допускается добавление колонки `ready_notified_at` в `orders` или создание связанной таблицы `order_push_logs`.*
- **Связь (Real-time):** Использовать исключительно штатный ActionCable для бродкастинга событий из POS в PWA.
- **Асинхронность:** Все отправки пушей, генерация `.pkpass` и тяжелые операции — строго через фоновые задачи ActiveJob (Sidekiq / GoodJob). Запрос от POS-терминала не должен блокироваться.

## Сценарии и чек-лист (Для todo.md)

### Блок A — Сквозной Real-time виджет заказа в PWA (Bottom Sheet)

- [ ] Шаг A1: ActionCable-канал OrderStatusChannel
  - **Given:** Заказ `order#42` перешёл в статус `preparing` на табло бариста.
  - **When:** POS-терминал отправляет запрос на смену статуса.
  - **Then:** Сервер успешно сохраняет статус и `OrderStatusChannel` бродкастит событие `{ order_id: 42, status: "preparing" }` на клиент. 
  - *Обработка ошибок:* Если ActionCable недоступен, POS получает 500/Timeout, UI POS показывает ошибку сети, бродкаст не происходит.

- [ ] Шаг A2: Сквозное отображение в нижней шторке PWA (Non-blocking UI)
  - **Given:** Пользователь находится на главном экране / витрине PWA, у него есть активный заказ.
  - **When:** Приходит событие смены статуса через WebSocket.
  - **Then:** Внизу экрана (в свернутом состоянии peek/hidden) обновляется 4-шаговый прогресс-бар (Принят → Оплачен → Готовится → Готов). Пользователь сохраняет полный доступ к сёрфингу по каталогу (z-index шторки не блокирует клики).
  - *Обработка ошибок:* При обрыве WS (краш сети) шторка показывает индикатор "Потеряно соединение" или "Обновление...", каталог остается полностью функциональным.

- [ ] Шаг A3: Обработка обрыва связи и реконнекта
  - **Given:** Пользователь ходит по приложению, интернет пропал и восстановился.
  - **When:** Соединение WebSocket восстанавливается.
  - **Then:** PWA делает фоновый GET-запрос актуального состояния активного заказа и обновляет статусную полосу в шторке без перезагрузки всей страницы.
  - *Обработка ошибок:* Если API возвращает 404 (заказ отменен/удален) или 500 (ошибка сервера), шторка скрывается или показывает статус "Ошибка загрузки", выводится toast-уведомление, ретрай по экспоненциальной задержке.

### Блок B — Триггеры Push-уведомлений от действия бариста

- [ ] Шаг B1: Обработчик события OrderStatusChangedEvent
  - **Given:** Бариста нажимает кнопку смены статуса на планшете.
  - **When:** Статус заказа обновляется на `preparing` или `ready`.
  - **Then:** Модель через `after_update_commit` генерирует асинхронную задачу (`PreparingPushJob` / `ReadyPushJob`).
  - *Обработка ошибок:* Если транзакция БД падает (500), хук не срабатывает, джоба не создается, POS показывает ошибку сохранения.

- [ ] Шаг B2: Push при статусе preparing («Готовится»)
  - **Given:** Бариста нажал «Начать готовку».
  - **When:** Фоновый воркер (Sidekiq/GoodJob) обрабатывает `PreparingPushJob`.
  - **Then:** Отправляется фоновый Web Push с текстом: «Бариста уже готовит ваш заказ!».
  - *Обработка ошибок:* Если Push-сервис возвращает 400 (невалидный токен) или 500 (сервис недоступен), джоба логирует ошибку, помечается как failed в Sidekiq с настройкой ретраев, POS-терминал не блокируется.

- [ ] Шаг B3: Push и обновление Apple Wallet при статусе ready («Готов»)
  - **Given:** Бариста нажал «Заказ готов».
  - **When:** `ReadyPushJob` выполняется.
  - **Then:** 
    1. Android (Web Push): Отправляется уведомление «Ваш кофе готов! Заберите на кассе».
    2. iOS (Apple Wallet): Обновляется `.pkpass` на сервере и посылается сигнал в APNs для смены статуса на заблокированном экране.
  - *Обработка ошибок:* Если APNs/Web Push возвращает 4xx/5xx, ошибка логируется. Если генерация `.pkpass` падает (500), задача падает в retry. Fallback: если Wallet недоступен, отправляется только стандартный Web Push.

### Блок C — Защита от спама и дублей (Idempotency)

- [ ] Шаг C1: Флаг ready_notified_at
  - **Given:** Заказ впервые переведён бариста в статус `ready`.
  - **When:** Система отправляет пуш.
  - **Then:** В БД фиксируется timestamp `ready_notified_at = Time.current` (в таблице `orders` или связанной).
  - *Обработка ошибок:* Если запись в БД не проходит (конфликт блокировок / 500), транзакция откатывается, пуш не отправляется, джоба уходит в retry.

- [ ] Шаг C2: Защита от случайных нажатий на табло бариста
  - **Given:** Заказ уже в статусе `ready` (и `ready_notified_at` заполнен). Бариста случайно переключил назад на `preparing` и снова на `ready`.
  - **When:** Триггер пуша (`ReadyPushJob`) срабатывает повторно.
  - **Then:** Система видит заполненный `ready_notified_at`, пропускает отправку пуша и обновление Wallet, но успешно обновляет виджет в PWA через ActionCable.
  - *Обработка ошибок:* При race-condition (одновременные клики) используется атомарное обновление БД (`UPDATE ... WHERE ready_notified_at IS NULL`), чтобы избежать дублей.

## Exit Criteria (Критерии выхода)
1. При оформлении заказа внизу PWA появляется сквозная шторка со статусом; каталог товаров остаётся полностью функциональным (клики по товарам проходят сквозь/мимо шторки).
2. Клик бариста на табло мгновенно меняет шаги на прогресс-баре шторки через WebSocket без перезагрузки страницы.
3. При переходе в статус «Готов» уходит ровно 1 пуш (без повторов при ошибочных кликах бариста и flip-flop статусов).
4. Все новые тесты проходят (зеленый статус: `bundle exec rspec` и `yarn test`).
5. Линтер (`yarn lint` / `rubocop`) и тайпчекер (`tsc --noEmit`) выполняются без ошибок.
