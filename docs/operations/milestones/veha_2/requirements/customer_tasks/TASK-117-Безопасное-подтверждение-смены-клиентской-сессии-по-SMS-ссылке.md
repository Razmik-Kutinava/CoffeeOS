## Текст задачи (дословно) — Google Doc Spec

TASK_117: Безопасное подтверждение смены клиентской сессии по SMS-ссылке

**Тип:** новая задача (сценарий нигде не зафиксирован)
**Версия:** v3 (2026-10-22)
**Зависит от:** TASK-PUSH-ENV-SNAPSHOT (сборка раньше: в "App.svelte" одна вставка); TASK-SHOP-CART-ON-TENANT-SWITCH
Бизнес-цель: открывать историю по SMS-ссылке, не подменяя текущего клиента без его явного согласия и не допуская гонок, из-за которых профиль, корзина или настройки другого клиента показываются в текущей сессии.

### 1. Карта интеграций — затронуто / нет
Затронуто: "OrderShortLinksController"; "GuestOrderReconnect"; "CustomerSession" (клиент хранится отдельно по точкам: "session[:shop_customers_by_tenant][tenant_id]"); "SessionRefresh"; "shop/api/session_controller.rb"; "shopTenantHeader.js"; "App.svelte", "restoreGuestSession.js", "silentRefreshSession.js"; кэш профиля и оффера на уровне модулей ("subscriptionOfferCta.js", "subscriptionOffer.js"); отметка "coffeeos_shop_push_registered_v1"; корзина; загрузка профиля, корзины, статуса заказа и push-регистрации при смене клиента.
Не затронуто: автоматическое объединение клиентов по телефону или email; существующий OTP-merge; платежи, checkout, Quick Repeat, Wallet; общая перестройка startup flow; каскад SMS.

### 2. Текущее поведение — факты аудитов
- "/o/:hash" проверяет подпись и срок, затем привязывает сессию к клиенту заказа без подтверждения и без сравнения с текущим клиентом, затем редирект на "/shop?tenant_id=…&reconnect_token=…#/order/:id" ("order_short_links_controller.rb:12-27", "guest_order_reconnect.rb:9-23"). Клиент параметр "reconnect_token" из адреса не читает (поиск по app/frontend пуст).
- Клиент в сессии хранится по точкам ("customer_session.rb:4-16", "set_customer_id!" — "22-30"): смена клиента возникает только если для точки заказа в сессии уже есть другой клиент. "SessionRefresh" может записать клиента из refresh-токена ("session_refresh.rb:20-41").
- Загрузка профиля, корзины, конфигурации и заказа идёт параллельно; механизма отмены устаревших ответов нет.
- Корзина: общий ключ серверной сессии ("cart_service.rb:7,19"); поведение при смене точки определяет TASK-SHOP-CART-ON-TENANT-SWITCH.
- Отметка «уведомления включены» лежит на устройстве ("orderStatusNotifyActions.js:64-66,231-235"); автоподписка при открытии экрана заказа с разрешением granted регистрирует токен для текущего клиента ("OrderStatus.svelte:240-243").
- Профиль для баннеров кешируется на уровне модуля ("subscriptionOfferCta.js:24-46").
- Step-up применяется в некоторых OTP-linker сценариях, в "GuestOrderReconnect.bind!" не найден.

### 3. Scope
Разрешено: разделить проверку ссылки и изменение сессии; запросить подтверждение до смены клиента; безопасный отказ; игнорирование запоздавших ответов старого клиента; очистка корзины при подтверждённой смене клиента с предупреждением; сброс отметки «уведомления включены» и кэшей профиля и оффера при подтверждённой смене; регрессионные тесты.
Запрещено: автоматически объединять клиентов; менять OTP-merge; снимать проверку владельца заказа; менять платежи и checkout; переписывать startup flow; менять глобальную модель сессии для несвязанных сценариев; менять порядок вызовов в "App.svelte onMount" и место вызова снимка окружения (TASK-PUSH-ENV-SNAPSHOT); менять имя, формат и правила ключа "coffeeos_shop_push_registered_v1" (TASK-PUSH-STORAGE-SAFE): допустимо только его удаление при подтверждённой смене клиента; нарушать порядок вызовов TASK_99 (requestPermission первым); менять состояние предварительной карточки уведомлений (TASK-PUSH-PREPROMPT): оно относится к устройству.
Решения владельца 2026-10-21: R2 — при подтверждённой смене клиента корзина очищается, окно подтверждения об этом предупреждает; R5 — отметка «уведомления включены» сбрасывается.

### 4. Gherkin
- [ ] Subtask 1: Given для точки заказа в сессии нет клиента или он совпадает с владельцем заказа, When открывается SMS-ссылка, Then подтверждения нет (клиенты других точек в сессии не меняются).
- [ ] Subtask 2: Given для точки заказа в сессии есть другой клиент, When ссылка действительна, Then до изменения сессии показывается подтверждение; данные владельца заказа до подтверждения не раскрываются и не подставляются.
- [ ] Subtask 3: Given подтверждение показано, When гость отказывается, Then сессия, корзина и состояние не меняются.
- [ ] Subtask 4: Given подтверждение показано, When гость подтверждает, Then выполняется контролируемый переход: корзина очищается (в окне есть предупреждение), отметка «уведомления включены» и кэши профиля и оффера сбрасываются, затем открывается история заказов владельца с выделенным заказом.
- [ ] Subtask 5: Given одновременно идут refresh, восстановление сессии и загрузка заказа, When гость подтверждает смену, Then запоздавшие ответы старого клиента не перезаписывают новую сессию, кэш профиля старого клиента не показывается.
- [ ] Subtask 6: Given сессия переключается, When запускаются загрузка статуса и регистрация push, Then устройство не связывается с клиентом из неподтверждённой или устаревшей сессии; повторная подписка выполняется только по действию гостя или автоподпиской экрана заказа уже для подтверждённого клиента.
- [ ] Subtask 7: Given две ссылки открыты подряд, Then вторая не меняет сессию, пока не завершена обработка первой.
- [ ] Subtask 8: Given ссылка недействительна или истекла, Then сессия не меняется (сообщения определяет TASK-39-SMS-READY-LINK-ORDER-HISTORY-EXT).
- [ ] Subtask 9: Given переход по ссылке, Then параметр "reconnect_token" не остаётся в адресной строке и не передаётся в Referer; если клиент его не использует, он не добавляется в редирект. [подтвердить аудитом, что параметр нигде не читается]
- [ ] Subtask 10: Given регрессия, Then существующие способы входа и восстановления сессии, OTP-linkers и OTP-merge не меняются.
