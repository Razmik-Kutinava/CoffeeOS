## Текст заказчика (дословно) — ревизия 2026-06-24

### Задача 1 — B1.12-R1: Архитектура СУБД и интеграция API Т-Банка (Рекуррентные платежи)

**Приоритет:** Высокий  
**Компонент:** Бэкенд / СУБД

**Описание**

Для реализации бесшовной оплаты в один клик без перехода на внешние платежные шлюзы необходимо настроить бэкенд-интеграцию с эквайрингом Т-Банка (сценарий nonPCI). Система должна поддерживать токенизацию карт при первой оплате и проведение рекуррентных платежей (списание по токену) без участия пользователя.

**Технические требования**

**СУБД (Таблица UserCards):**

Создать или обновить структуру таблицы для хранения привязанных карт:

- `id` (UUID) — внутренний ID карты.
- `user_id` (INT/UUID) — внешний ключ пользователя.
- `rebill_id` (STRING) — токен рекуррентного платежа от Т-Банка.
- `card_id` (STRING) — ID карты в системе банка.
- `pan` (STRING) — маскированный номер для UI (формат: *5953, как на макете 1000008924.png).
- `exp_date` (STRING) — срок действия (ММ/ГГ).
- `card_type` (STRING) — платежная система (MIR, VISA, MASTERCARD) для отображения иконок.

Ограничение безопасности: Хранение полных данных (PAN, CVC/CVV) категорически запрещено.

**Логика API-методов:**

**Эндпоинт 1: Инициализация оплаты новой карты.** Принимает зашифрованный на фронте CardData, amount и флаг save_card.

- Вызывает метод Т-Банка /Init с уникальным CustomerKey. Получает PaymentId.
- Вызывает метод Т-Банка /FinishAuthorize, передавая PaymentId и CardData.
- При успехе и save_card == true извлекает RebillId, CardId и маску карты, сохраняя их в таблицу UserCards.

**Эндпоинт 2: Оплата в 1 клик (По токену).** Принимает card_id (из нашей БД) и amount.

- Достает из базы соответствующий RebillId.
- Вызывает метод Т-Банка /Init (получает PaymentId).
- Вызывает метод Т-Банка /Charge, передавая PaymentId и RebillId. Транзакция проходит скрыто (silent request).

**Обработка 3D-Secure:** Если банк на любом этапе возвращает статус 3DS_CHECKING, бэкенд должен транслировать фронтенду параметры ACSUrl, PaReq и MD для прохождения аутентификации.

**Критерии приёмки (Acceptance Criteria)**

- API полностью покрывает сценарии первой оплаты и рекуррентного списания.
- При успешной эмуляции вебхука от Т-Банка RebillId гарантированно записывается в БД.
- Ошибки API Т-Банка логируются и пробрасываются на фронтенд в неизменном виде (с сохранением исходных кодов ошибок ErrorCode).

### Задача 2 — B1.12-R2: Фронтенд. Кастомный ввод карты и клиентское RSA-шифрование

**Приоритет:** Высокий  
**Компонент:** Фронтенд (PWA / Mobile First)

**Описание**

Необходимо сверстать полностью кастомный интерфейс ввода новой карты внутри приложения, полностью отказавшись от стандартных iframe-виджетов банка, которые ломают темную тему и дизайн-систему. Передача данных карты должна быть безопасной и соответствовать требованиям сценария nonPCI Т-Банка.

**Технические требования**

**Верстка интерфейса:**

- Сверстать шторку/экран «Новая карта» строго по макету 1000008925.png.
- Поля: Номер карты, ММ/ГГ, CVC/CVV.
- Кастомный тумблер: «Использовать карту для будущих заказов» (по умолчанию активен).
- Блок с логотипами систем безопасности внизу экрана.

**Валидация и маски:**

- Навесить маску на ввод номера карты (разделение по 4 цифры) и срок действия (автоматический слэш /).
- Реализовать валидацию номера карты по алгоритму Луна (Luhn algorithm) на лету. При невалидном номере или пустых полях кнопка «Оплатить» блокируется, инпуты подсвечиваются ошибкой.

**Безопасность и шифрование (Критично):**

- Запрещено отправлять данные карты на наш бэкенд в открытом виде.
- Реализовать сбор данных из инпутов в строку формата: PAN;ExpDate;CVV.
- Реализовать шифрование этой строки на стороне клиента алгоритмом RSA-2048 с использованием публичного ключа нашего терминала Т-Банка (в соответствии с документацией Т-Банка по ручной сборке параметра CardData).
- На бэкенд отправляется исключительно готовая зашифрованная строка CardData.

**Критерии приёмки (Acceptance Criteria)**

- Визуальное соответствие макету 1000008925.png — 100% (цвета, шрифты, скругления, поведение тумблера).
- Вкладка Network в DevTools подтверждает: открытый PAN и CVV не фигурируют ни в одном сетевом запросе.
- Валидация полей отрабатывает до отправки запроса на сервер.

### Задача 3 — B1.12-R3: Фронтенд. Реализация стейт-машины динамической кнопки оплаты

**Приоритет:** Блокирующий  
**Компонент:** Фронтенд (PWA / Mobile First)

**Описание**

Для максимизации конверсии повторных покупок необходимо избавиться от промежуточных экранов ошибок и модальных окон. Кнопка «Оплатить» на экране выбора способов оплаты (1000008924.png) должна работать как конечный автомат (State Machine), транслируя текущий статус соединения и ответы банка прямо внутри своего интерфейса.

**Технические требования**

Реализовать стейт-машину для кнопки «Оплатить». Текст, цвет и доступность кнопки должны меняться в зависимости от этапа выполнения запроса и привязываться к ErrorCode от бэкенда/Т-Банка:

| Состояние (State) | Событие (Триггер) | Визуальное состояние кнопки | Действие системы / Логика |
|-------------------|-------------------|----------------------------|---------------------------|
| 0. Default | Экран загружен, карта выбрана | Синяя кнопка, текст: Оплатить. Кликабельна. | Ожидание тапа пользователя. |
| 1. Connecting | Пользователь нажал кнопку | Текст: Установка соединения... + лоадер. Кнопка disabled. | Отправка запроса инициализации на наш бэкенд. |
| 2. Processing | Бэк вернул успешный /Init | Текст: Обработка банком... + лоадер. Кнопка disabled. | Ожидание ответа от шлюза Т-Банка (/Charge или /FinishAuthorize). |
| 3. 3D-Secure | Банк вернул 3DS_CHECKING | Текст: Подтвердите по СМС. Кнопка disabled. | Открытие банковского ACSUrl внутри iframe поверх текущего экрана для ввода кода. |
| 4. Success | Банк вернул CONFIRMED | Зеленый фон, текст: Оплачено ✔. Кнопка disabled. | Фиксация стейта на 1.5 секунды, затем автоматический редирект на экран «Спасибо за покупку». |
| 5. Client Error | Отказ банка по карте юзера (коды Т-Банка: лимиты, неверный код, баланс) | Красный фон, текст: Отказ: смените карту. Кликабельна. | Кнопка «трясется» (shake-анимация). Список карт разблокируется. При тапе юзера на другую карту (например, с *5953 на *5938), кнопка сбрасывается в State 0. |
| 6. Bank Error | Ошибка шлюза банка / Backend 500 | Серый/Красный фон, текст: Сбой банка: позже. Кликабельна. | Дает пользователю возможность повторить отправку платежа без изменения параметров. |
| 7. Net Error | Пропала сеть (navigator.onLine == false) или timeout > 10 сек | Серый фон, текст: Нет сети: повторить. Кликабельна. | Кнопка разблокируется. Повторный клик запускает процесс заново с State 1. |

**Дополнительные UX-требования**

- Защита от микро-мерцания: Если бэкенд/банк отвечает быстрее, чем за 600 мс, искусственно удерживать лоадер (сумму стейтов Connecting + Processing) до 600 мс, чтобы текст в кнопке не моргал слишком быстро.
- Никаких алертов: Запрещено выводить стандартные всплывающие окна ошибок (alert, toast, modal), если они не касаются критического падения всего приложения. Вся коммуникация по платежу идет через кнопку.

**Критерии приёмки (Acceptance Criteria)**

- Поведение кнопки при различных сценариях (успех, отказ, оффлайн) строго соответствует описанной матрице состояний.
- Время реакции кнопки на клик (переход в State 1) составляет не более 100 мс.
- При ошибке карты («Отказ: смените карту») выбор любого другого сохраненного метода оплаты из списка на макете 1000008924.png мгновенно возвращает кнопку в исходное синее состояние.
