## Текст заказчика (дословно)

### B1.12-R1 — Архитектура и рекуррентные платежи (Бэкенд + СУБД)

| Свойство задачи | Правила заполнения / Значение |
|-----------------|-------------------------------|
| Название задачи | Реализовать бэкенд-логику и структуру БД для рекуррентных платежей и токенизации карт |
| Приоритет | Наследуется от родительского эпика |
| Исполнитель | [Указать ответственного разработчика] |

**Описание:**

**Проблема:** Текущий процесс оплаты требует явного отображения внешних форм банка, что увеличивает время оформления заказа. Отсутствие механизма сохранения токенов карт не позволяет реализовать сценарий оплаты без повторного ввода реквизитов, что снижает конверсию повторных покупок.

**Решение:**

**Продуктовые требования:** Система запоминает привязанную карту после первой успешной оплаты, позволяя клиенту совершать повторные покупки без ввода данных карты, повышая скорость и надежность транзакции.

**Технологические требования:** Интеграция с API банка по рекуррентным платежам. Создание сущности UserCards в базе данных.

**User Story:** Как владелец продукта, я хочу, чтобы система сохраняла токены карт после первой успешной оплаты, чтобы в будущем инициировать списание средств через API банка без участия пользователя.

**Use Case:**

1. Пользователь инициирует первую оплату через фронтенд.
2. Бэкенд передает данные в банк для инициализации.
3. Банк возвращает webhook с успешным статусом, bank_token и masked_pan.
4. Бэкенд сохраняет полученные данные в таблицу UserCards.
5. При повторной оплате бэкенд принимает от фронтенда card_id и amount, формирует и отправляет скрытый запрос в банк на списание по сохраненному токену.

**Ограничения (чего не делаем):** Категорически запрещено сохранять полные реквизиты карты (PAN, CVV/CVC) в базе данных приложения. Хранению подлежат исключительно bank_token и masked_pan.

**Критерии приёмки:**

- **Измеритель:** Наличие реализованных API-методов и корректных записей в таблице UserCards при тестировании через Postman/Swagger.
- **Целевой показатель:** 100% успешное сохранение bank_token и masked_pan при имитации успешного webhook от банка.
- **Критерий успеха:** Отклонение 0%. Любая ошибка валидации или сохранения приводит к падению автотеста.

### B1.12-R2 — Родной ввод и привязка карты (Фронтенд + Бэкенд)

| Свойство задачи | Правила заполнения / Значение |
|-----------------|-------------------------------|
| Название задачи | Интегрировать SDK/Web-фреймы банка для нативного ввода данных карты и прохождения 3D-Secure |
| Приоритет | Наследуется от родительского эпика |
| Исполнитель | [Указать ответственного разработчика] |

**Описание:**

**Проблема:** Внешние формы банка визуально выбиваются из интерфейса приложения/сайта, создавая разрыв в пользовательском опыте и повышая вероятность отказа от оплаты на этапе ввода данных из-за недоверия к стороннему интерфейсу.

**Решение:**

**Продуктовые требования:** Бесшовный интерфейс ввода карты, стилизованный под дизайн-систему приложения, сохраняющий при этом стандарты безопасности банка.

**Технологические требования:** Внедрение SDK банка (для iOS/Android) или защищенных Web-фреймов (для Web). Реализация обработки 3D-Secure через WebView или нативный браузер.

**User Story:** Как пользователь, я хочу вводить данные карты в интерфейсе, который выглядит как часть приложения, чтобы чувствовать безопасность процесса и не отвлекаться на сторонние визуальные элементы.

**Use Case:**

1. Пользователь нажимает «Оплатить впервые».
2. Открывается стилизованная форма SDK или Web-фрейма.
3. Данные передаются напрямую в банк, приложение ожидает ответ от собственного бэкенда (реализованного в Задаче 1).
4. При запросе банка открывается WebView для ввода SMS-кода (3D-Secure).
5. После подтверждения приложение получает статус от бэкенда и перенаправляет пользователя на экран статуса операции («Карта успешно привязана / Оплачено»).

**Ограничения (чего не делаем):** Не модифицировать внутреннюю логику безопасности и шифрования банка. Стилизовать исключительно визуальную оболочку, доступную для кастомизации согласно официальной документации банка.

**Критерии приёмки:**

- **Измеритель:** Прохождение тестовых сценариев первой привязки карты в тестовой среде.
- **Целевой показатель:** 100% успешных сценариев ввода карты и прохождения 3D-Secure. 100% соответствие визуального оформления гайдлайнам дизайн-системы.
- **Критерий успеха:** Отклонение 0%. Любое отображение стандартных, не подлежащих стилизации элементов банка, фиксируется как дефект.

### B1.12-R3 — Оплата в 1 клик и логика состояний кнопки (Фронтенд)

| Свойство задачи | Правила заполнения / Значение |
|-----------------|-------------------------------|
| Название задачи | Реализовать интерфейс оплаты в «один клик» с управлением состояниями кнопки «Оплатить» |
| Приоритет | Наследуется от родительского эпика |
| Исполнитель | [Указать ответственного разработчика] |

**Описание:**

**Проблема:** Наличие лишних экранов и задержек при повторной оплате снижает скорость совершения покупки. Отсутствие понятной индикации статуса операции на кнопке приводит к многократным нажатиям и ошибкам со стороны пользователя.

**Решение:**

**Продуктовые требования:** Мгновенная оплата с визуальной обратной связью прямо на кнопке, без переходов на промежуточные экраны, с четкой инструкцией к действию при возникновении ошибок.

**Технологические требования:** Реализация стейт-машины (state machine) для кнопки «Оплатить» и отображение блока сохраненной карты (формат: [Платежная система] •••• [последние 4 цифры]).

**User Story:** Как постоянный клиент, я хочу совершать повторную покупку нажатием одной кнопки с мгновенной визуальной реакцией, чтобы экономить время и понимать текущий статус транзакции без перехода на другие экраны.

**Use Case:**

1. На экране заказа отображается блок сохраненной карты (при ее наличии в ответе бэкенда).
2. Пользователь нажимает «Оплатить».
3. State 2 (Загрузка): Кнопка блокируется, появляется индикатор загрузки, отправляется запрос на бэкенд.
4. State 3 (Успех): Индикатор заменяется на иконку подтверждения (галочку), через 1.5 секунды происходит автоматический редирект на экран «Спасибо за покупку».
5. State 4 (Ошибка): Кнопка разблокируется. Под кнопкой выводится текст ошибки на основе кодов ответа (например, «Недостаточно средств» или «Истек срок действия»). При получении критического кода ошибки (например, «Карта заблокирована») рядом отображается кнопка «Привязать другую карту», инициирующая сценарий из Задачи 2.

**Ограничения (чего не делаем):** Не использовать модальные окна для отображения стандартных ошибок оплаты, если это не предусмотрено дизайн-макетом для критических сбоев системы.

**Критерии приёмки:**

- **Измеритель:** Корректное отображение 4-х состояний кнопки (Дефолтное, Загрузка, Успех, Ошибка) и корректность редиректа.
- **Целевой показатель:** 100% срабатывание переходов между состояниями согласно Use Case при имитации ответов бэкенда (коды 200, 400, 500).
- **Критерий успеха:** Отклонение 0%. Время смены состояния на «Загрузка» после клика ≤ 100 мс. Время редиректа при успехе составляет 1.5 ± 0.2 секунды.
