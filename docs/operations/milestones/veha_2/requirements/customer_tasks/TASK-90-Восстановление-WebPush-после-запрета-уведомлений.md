TASK_90: Восстановление WebPush после запрета уведомлений

Расширяет: docs/operations/milestones/veha_2/requirements/customer_tasks/TASK-81-...md — задачу восстановления уведомлений `denied → settings`

Бизнес-цель: после отказа пользователя от уведомлений дать ему понятный и повторно используемый путь к разрешению уведомлений для текущего сайта, не заставляя повторно проходить исходный сценарий подписки и не ломая существующую статусную модель заказа.

3. Текущее поведение (факт)

При `Notification.permission === "denied"` существующий flow:
1. показывает сообщение: `Уведомления запрещены в настройках браузера`;
1. предлагает открыть настройки;
1. для Android используется попытка перехода через Android intent;
1. для desktop при отсутствии доступного URL переход не выполняется;
1. после возврата пользователь должен снова видеть существующую статусную модель заказа.

Текущий механизм открытия настроек не гарантирует фактического перехода к настройке разрешения уведомлений текущего сайта во всех браузерах.

4. Scope

Разрешено

1. Доработать существующий сценарий `denied → settings`.
1. После отказа показывать пользователю понятный recovery UI:
  1. объяснение причины;
  1. кнопку «Открыть настройки»;
  1. кнопку «Смотреть готовность».
1. При возможности открыть настройки непосредственно для разрешения уведомлений текущего сайта.
1. Если браузер не позволяет выполнить автоматический переход:
  1. не оставлять пользователя без действия;
  1. показать универсальную инструкцию, как вручную разрешить уведомления для текущего сайта.
1. Сделать инструкции понятными для Android + Chrome как обязательного acceptance-case.
1. Сохранить поддержку всех браузеров, в которых текущий WebPush flow уже работает.
1. После нажатия «Смотреть готовность» возвращать пользователя к обычному экрану/статусной модели заказа.
1. Сохранить существующую логику определения состояния заказа: отдельный механизм «возврата из настроек» не вводить.
1. После повторного разрешения уведомлений существующий WebPush flow должен иметь возможность продолжить работу штатным способом.

Запрещено

1. не менять iOS/Apple Wallet;
1. не менять статусную модель заказа;
1. не добавлять новые статусы заказа;
1. не создавать отдельный state machine для возврата из настроек;
1. не менять сценарии `возврат`, `чаевые` и другие CTA, определяемые существующим статусом;
1. не менять backend API регистрации push;
1. не менять VAPID/FCM-конфигурацию без отдельной задачи;
1. не менять PWA Service Worker;
1. не переписывать существующий WebPush flow целиком;
1. не удалять существующий защитный/регрессионный тест, проверяющий `denied → settings`, а только актуализировать его под новое поведение.

5. Gherkin

Subtask 1 — Recovery UI после запрета

1. Subtask 1: Given пользователь находится в статусе заказа, где доступно подключение уведомлений
And `Notification.permission === "denied"`
When отображается действие уведомлений
Then пользователь видит объяснение, что уведомления запрещены для текущего сайта
And видит кнопку «Открыть настройки»
And видит кнопку «Смотреть готовность».

Subtask 2 — Открытие настроек

1. Subtask 2: Given `Notification.permission === "denied"`
When пользователь нажимает «Открыть настройки»
Then приложение пытается открыть настройки разрешений уведомлений для текущего сайта доступным способом
And не изменяет статусную модель заказа.

Subtask 3 — Fallback при невозможности deep-link

1. Subtask 3: Given браузер не позволяет приложению автоматически открыть нужные настройки
When пользователь нажимает «Открыть настройки»
Then приложение показывает универсальную инструкцию по ручному разрешению уведомлений для текущего сайта
And пользователь получает понятный следующий шаг без необходимости угадывать, где находится настройка.

Subtask 4 — Android Chrome

1. Subtask 4: Given пользователь использует Android + Chrome
And уведомления для текущего сайта находятся в состоянии `denied`
When пользователь проходит recovery flow
Then он получает рабочий путь к настройке разрешения уведомлений текущего сайта
And после разрешения может вернуться в PWA.

Subtask 5 — Поддерживаемые браузеры

1. Subtask 5: Given браузер поддерживает существующий WebPush flow проекта
And уведомления для текущего сайта находятся в состоянии `denied`
When пользователь запускает recovery flow
Then используется доступный для этого браузера способ перехода к настройкам
And при невозможности автоматического перехода показывается fallback-инструкция.

Subtask 6 — Возврат к статусной модели

1. Subtask 6: Given пользователь находится в recovery UI
When пользователь нажимает «Смотреть готовность»
Then он возвращается к обычному экрану/статусной модели заказа
And дальнейшие кнопки определяются существующим статусом заказа
And новый отдельный recovery-state не создаётся.

Subtask 7 — Повторное разрешение

1. Subtask 7: Given пользователь ранее запретил уведомления
And затем разрешил уведомления для текущего сайта в настройках
When он возвращается в PWA
Then существующая логика WebPush должна определить актуальное состояние permission
And дальнейшая подписка/регистрация выполняется существующим WebPush flow
And новый backend-контракт для этого сценария не добавляется.

Subtask 8 — Регрессия существующего `denied → settings`

1. Subtask 8: Given существующий сценарий `denied → settings` покрыт тестами
When реализуется recovery flow
Then тесты продолжают проверять наличие CTA и toast/recovery UI
And не допускают возврата к состоянию, при котором после `denied` пользователь остаётся без понятного действия.
