## Текст заказчика (Google Doc, дословно)

TASK_105: Оптимизация формы оплаты под цифровой клавиатурой

Бизнес-цель: Устранить перекрытие элементов формы оплаты при открытии цифровой клавиатуры в shop PWA. Обеспечить доступность всех полей и кнопки «Оплатить» без наложений, деформации формы и нарушения существующих платёжных сценариев.

Тип: UX/UI-полировка существующего pay-стека с предварительным техническим аудитом.

Веха: В2, UX-полировка.

Приоритет: Высокий — блокируется основной пользовательский сценарий оплаты картой.

Идентификатор: TASK_98 — перед созданием проверить, свободен ли номер. В названии файла использовать название задачи, а не номер.

1. Связь с картой интеграций

- Затронутые сервисы из "INTEGRATIONS.md": Т-Банк — только в части отображения платёжной формы, если её поля предоставляются внешним виджетом. Контракт интеграции не меняется.
- Точки взаимодействия: существующий pay-стек shop PWA, контейнер платёжной формы, системная экранная клавиатура через Web API.
- Identity Mapping: не требуется.
- Обработка ошибок: при недостатке доступной высоты форма должна переходить к внутренней прокрутке. Ошибки загрузки или отображения платёжного виджета обрабатываются существующей логикой.
- Безопасность: не изменять обработку платёжных данных, токенизацию, сохранение карт и механизмы взаимодействия с Т-Банком.
- Смежные модули, которые нельзя ломать:
  - скрытие CTA при открытии клавиатуры — задача #80;
  - phone-auth slim — "TASK_89-UI-EXT";
  - сумма заказа — "TASK_101";
  - история заказов и повтор заказа — "TASK_91", "TASK_94";
  - Quick Repeat — задача #87;
  - существующие сценарии оплаты через СБП и привязки карты.

2. Связь с картой компонентов

Обязательный аудит перед реализацией. Переданные сведения о компонентах не заменяют проверку фактического содержимого "docs/operations/session/COMPONENT_MAP.md". Если карта доступна в контексте проекта, использовать зафиксированные в ней пути и владельцев.

- Затронутые компоненты:
  - "PaymentMethodsSheet.svelte" — раскладка способов оплаты и формы карты;
  - "CartSheet.svelte" — отображение карточки товара и хост pay-стека;
  - "shopWebViewLayout.js" — расчёт keyboard inset и доступной высоты.
- Условно затрагиваемые компоненты:
  - viewport meta — только если аудит подтвердит необходимость изменения;
  - "cartSheetThresholds.js" — по умолчанию только чтение; изменение допускается исключительно при доказанной необходимости и отдельном тесте регрессии.
- Общий файл с другой задачей: да.
  - "PaymentMethodsSheet.svelte": разрешена только раскладка pay-стека. Изменения строки «Итого», сохранённых карт, привязки карты и СБП запрещены.
  - "CartSheet.svelte": разрешено только условное скрытие карточки товара в pay-режиме. Поведение каталога и обычной корзины сохраняется.
  - "shopWebViewLayout.js": разрешены только необходимые изменения расчёта доступной высоты для pay-стека. Keyboard-path задачи #80 и "phoneAuthActive" задачи "TASK_89-UI-EXT" должны сохраниться.
- Новый компонент (не в карте): нет, если аудит не выявит необходимость создания нового компонента или helper. Любой новый компонент или helper должен быть явно добавлен в карту.
- Владение: перед изменением общего файла проверить владельцев по "COMPONENT_MAP.md". Не перезаписывать и не рефакторить участки, принадлежащие другим задачам.

- Тесты затронутых компонентов и helper-функций — в соответствующих существующих каталогах тестов.

- Keyboard-path "shouldHideCartCheckoutCta" задачи #80.
- Логику "phoneAuthActive" и phone-auth slim задачи "TASK_89-UI-EXT".

4. Сценарии и чек-лист (Gherkin)

Аудит и технические ограничения

- [ ] Subtask 1: Определить источник карточки товара в pay-стеке
  
  - Given: открыт pay-стек и доступен исходный код затронутых компонентов.
  - When: исследуются "CartSheet.svelte", "PaymentMethodsSheet.svelte" и связанные компоненты.
  - Then: в результатах аудита зафиксированы фактический компонент-источник карточки товара и минимальная точка условного скрытия без изменения обычной корзины.

- [ ] Subtask 2: Определить способ рендеринга полей карты
  
  - Given: форма оплаты отображает поля номера карты, срока действия и CVV.
  - When: проверяется DOM и интеграция платёжного виджета.
  - Then: документировано, являются ли поля собственной разметкой или содержимым iframe Т-Банка. Если это iframe, изменения ограничиваются внешним контейнером и доступной областью.

- [ ] Subtask 3: Определить причину перекрытия кнопки оплаты
  
  - Given: блок «Мир ••XXXX / Сканировать новую карту» перекрывает кнопку «Оплатить».
  - When: исследуются CSS-позиционирование, sticky/fixed-слои, размеры контейнеров и keyboard inset.
  - Then: зафиксирована причина перекрытия и выбран минимальный способ её устранения без изменения платёжной логики.

- [ ] Subtask 4: Проверить все источники открытия pay-стека
  
  - Given: pay-стек используется чекаутом, Quick Repeat, повтором из истории и привязкой карты.
  - When: исследуются вызывающие сценарии и связанные тесты.
  - Then: сформирован список регрессионных проверок для каждого существующего сценария.

Раскладка и поведение интерфейса

- [ ] Subtask 5: Рассчитать доступную высоту через существующий layout helper
  
  - Given: "shopWebViewLayout.js" рассчитывает параметры экранной области и keyboard inset.
  - When: выполняется расчёт доступной высоты pay-стека при изменении "visualViewport".
  - Then: результат учитывает фактически доступную область и существующую модель keyboard inset; добавлен тест на расчёт высоты и сохранено прежнее поведение других экранов.

- [ ] Subtask 6: Скрыть карточку товара только в pay-стеке
  
  - Given: корзина содержит товар, а пользователь открыл pay-стек.
  - When: отображается экран способов оплаты.
  - Then: карточка товара не отображается, строка «Итого» остаётся видимой. В каталоге и обычной корзине карточка отображается как прежде.

- [ ] Subtask 7: Устранить перекрытие кнопки оплаты
  
  - Given: pay-стек открыт, блок «Мир / Сканировать новую карту» отображается под формой.
  - When: форма раскладывается в доступной области экрана.
  - Then: блоки не пересекаются, кнопка «Оплатить» полностью видна и кликабельна, а элементы формы не деформируются.

- [ ] Subtask 8: Адаптировать форму к открытой цифровой клавиатуре
  
  - Given: экран оплаты открыт на устройстве с viewport 412×915 CSS px.
  - When: пользователь фокусируется на поле номера карты и открывается клавиатура.
  - Then: форма занимает доступную область над клавиатурой; видны строка «СБП», поля карты, чекбокс сохранения, кнопка оплаты и блок сохранённой карты. Ни один элемент не перекрывает другой.

- [ ] Subtask 9: Сохранить видимость активного поля при переключении
  
  - Given: цифровая клавиатура открыта и поле номера карты находится в фокусе.
  - When: пользователь переходит к полю «ММ/ГГ», затем к CVV.
  - Then: активное поле остаётся в видимой области, размеры полей стабильны, а раскладка не скачет.

- [ ] Subtask 10: Восстановить обычную раскладку после закрытия клавиатуры
  
  - Given: экран оплаты сжат под открытую клавиатуру.
  - When: пользователь закрывает клавиатуру.
  - Then: pay-стек возвращается к обычной высоте без артефактов, лишних отступов и нарушения прокрутки.

- [ ] Subtask 11: Обеспечить работу на компактных экранах
  
  - Given: viewport имеет размер 360×640 или 390×844 CSS px и открыта цифровая клавиатура.
  - When: доступной высоты недостаточно для одновременного размещения всех элементов.
  - Then: включается внутренняя прокрутка контейнера формы; кнопка оплаты доступна пользователю, а прокрутка всей страницы не используется как основной механизм компенсации.

- [ ] Subtask 12: Сохранить существующие сценарии оплаты
  
  - Given: используются СБП, сохранённая карта, привязка новой карты, Quick Repeat или повтор заказа из истории.
  - When: каждый сценарий проходит через pay-стек.
  - Then: платёжная логика, тексты и поведение сценариев сохраняются; единственное согласованное визуальное изменение — скрытие карточки товара в pay-режиме.

- [ ] Subtask 13: Сохранить совместимость с keyboard-path и phone-auth
  
  - Given: существуют тесты задачи #80 и "TASK_89-UI-EXT".
  - When: запускаются соответствующие регрессионные тесты после изменений layout helper.
  - Then: скрытие CTA при открытой клавиатуре и поведение phone-auth остаются без регрессий.

- [ ] Subtask 14: Проверить необходимость изменения viewport meta
  
  - Given: реализован расчёт доступной высоты через существующий helper.
  - When: проверяется поведение shop PWA в Chrome и PWA-режиме на целевых устройствах.
  - Then: "interactive-widget=resizes-content" добавляется только при подтверждённой необходимости; если оно не требуется, viewport meta остаётся без изменений. Нативные Android-параметры не используются.

- [ ] Subtask 15: Выполнить финальную регрессию и зафиксировать результаты
  
  - Given: все изменения реализованы и автоматические тесты проходят.
  - When: выполняется ручной прогон на Pixel 6 и проверяются viewport 360×640 и 390×844.
  - Then: приложены скриншоты до/после, зафиксированы результаты всех платёжных сценариев и обновлена карта компонентов.

5. Целевая раскладка и критерии измерения

Целевое устройство: Google Pixel 6, viewport 412×915 CSS px.

Ориентировочная оценка:

Зона| Высота
Шапка браузера / Custom Tab| ~105 px
Цифровая клавиатура| ~365 px
Доступная область под форму по исходной оценке| ~445 px
Строка «СБП»| ~50 px
Поле номера карты с подсказкой| ~85 px
Поля «ММ/ГГ» и CVV| ~85 px
Чекбокс сохранения карты| ~50 px
Кнопка «Оплатить»| ~65 px
Блок «Мир / Сканировать новую карту»| ~50 px
Суммарная высота перечисленных элементов| ~385 px

Высоты являются ориентировочными, допустимое отклонение — ±8 px для соответствующих элементов. Расчёт доступной области необходимо подтвердить измерениями в реальном Chrome/PWA: размеры viewport, системной клавиатуры и шапки браузера не считать константами.

Критерии раскладки:

- ни один интерактивный элемент не перекрывается;
- кнопка «Оплатить» целиком находится над клавиатурой;
- сохранённые карты не перекрывают кнопку;
- при недостатке места доступна внутренняя прокрутка;
- высота iframe, если он используется платёжным виджетом, не считается управляемой нашей стороной.
