# Вход и регистрация по номеру телефона (SMS / Flash Call) + защита от спама

Бизнес-цель: Добавить возможность авторизации, регистрации и входа в PWA по номеру телефона через SMS или Flash Call (звонок-сброс), задействовав уже существующие таблицы в БД (mobile_customers, mobile_otp_codes).

## Глобальные ограничения
- Запрещено изменять структуру или создавать новые таблицы `mobile_customers` и `mobile_otp_codes` (они уже существуют).
- Запрещено хардкодить API-ключи провайдеров (SMS.ru / SMSAero / Zvonok / Smsc) — использовать только ENV-переменные.
- Запрещено отправлять реальные платные SMS/звонки при `ENV['SHOP_OTP_LOG_FALLBACK'] = true` (только логирование).

## Сценарии и чек-лист (Для todo.md)

- [ ] Шаг 1: Нормализация телефонных номеров
  - Given: Пользователь вводит номер телефона в произвольном формате (8900..., 7900..., +7 (900)...).
  - When: Срабатывает хелпер/сервис нормализации перед сохранением или поиском в БД.
  - Then: Номер приводится к единому стандарту `+79XXXXXXXXX`. Некорректные форматы отклоняются с валидационной ошибкой.

- [ ] Шаг 2: Интеграция с провайдером (SMS / Flash Call клиент)
  - Given: Создан сервис-клиент (`Shop::SmsClient` / `Shop::FlashCallClient`) по образцу `Shop::BrevoClient`, настроены ENV-переменные.
  - When: Вызывается метод отправки через провайдера.
  - Then: Для SMS отправляется текстовое сообщение. Для Flash Call запрашивается входящий звонок. При `ENV['SHOP_OTP_LOG_FALLBACK'] = true` код пишется в `Rails.logger`. При краше сети провайдера (500/400) ошибка перехватывается, возвращается понятный ответ, состояние БД не нарушается.

- [ ] Шаг 3: Сервис отправки OTP-кодов (Shop::PhoneOtp - Send)
  - Given: Пользователь запросил код, передав `phone` и `channel` ("sms" или "flash_call").
  - When: Выполняется логика сервиса `Shop::PhoneOtp`.
  - Then: Погашаются прошлые неиспользованные коды пользователя в `mobile_otp_codes` (`is_used: true`). Для SMS генерируется 4–6 значный случайный код. Для Flash Call кодом авторизации становятся последние 4 цифры входящего номера. Новый код записывается в `mobile_otp_codes` (TTL = 10 минут, `attempts: 0`).

- [ ] Шаг 4: Защита от спама (Cooldown)
  - Given: Пользователь уже запрашивал OTP-код (SMS, Flash Call или Email).
  - When: Проходит менее 60 секунд с момента `created_at` последнего кода и поступает новый запрос на отправку.
  - Then: Повторная отправка блокируется. Задержка применяется не чаще 1 раза в 60 секунд на один номер (и аналогично для Email-OTP).

- [ ] Шаг 5: Проверка кода и связка аккаунтов (Verify)
  - Given: Пользователь ввел код, в БД есть активная запись в `mobile_otp_codes`.
  - When: Вызывается метод проверки кода.
  - Then: Код проверяется (максимум 5 попыток, используется `secure_compare`). Находится или создается клиент в `mobile_customers` по полю `phone`. Если у текущего сессионного пользователя уже был подтвержден Email, Email и Phone связываются в одной записи `mobile_customers`. Генерируется `refresh_token` в `mobile_sessions`, возвращается авторизованная сессия. При превышении лимита попыток код аннулируется.

- [ ] Шаг 6: API-эндпоинты и Rate-limit
  - Given: Настроены маршруты Rails и `rack_attack`.
  - When: Поступают запросы на `POST /shop/api/phone_otp/send` (принимает `{ phone, channel }`), `POST /shop/api/phone_otp/verify` (принимает `{ phone, code }`), `GET /shop/api/phone_otp/status`.
  - Then: Эндпоинты возвращают корректные payload и статусы. Добавлен/обновлен rate-limit в `config/initializers/rack_attack.rb` для эндпоинтов телефона. При ошибках сети провайдера (500/400) API возвращает соответствующий HTTP-статус, не падая с 500 на уровне Rails.

- [ ] Шаг 7: Фронтенд - Форма ввода телефона и экран кода
  - Given: Пользователь открыл PWA и перешел к авторизации.
  - When: Пользователь взаимодействует с формами ввода.
  - Then: Форма имеет маску `+7 (XXX) XXX-XX-XX` и выбор способа (SMS / Flash Call). На экране ввода кода для Flash Call отображается подсказка: *"Введите последние 4 цифры номера, с которого вам звонят"*. Для SMS — поле ввода 4–6 значного кода. Отображается таймер обратного отсчета (60 секунд) перед возможностью повторной отправки.

- [ ] Шаг 8: Фронтенд - Интеграция и авторизация
  - Given: Пользователь успешно прошел верификацию на фронтенде.
  - When: Получен успешный ответ от API с `refresh_token`.
  - Then: `refresh_token` сохраняется в `localStorage`, интерфейс переводится в авторизованный статус. При ошибках API (400/500) отображается соответствующее уведомление об ошибке.

## Стратегия тестирования
- Фреймворк: RSpec (Backend Rails), Vitest/Jest (Frontend PWA)
- Путь к файлам тестов: `spec/` (Backend), `src/**/*.test.ts(x)` (Frontend)
- Критические кейсы: Нестандартные форматы телефонов при нормализации, истечение TTL (10 минут), достижение лимита попыток (5), границы кулдауна (ровно 60 секунд), асинхронность и краш сети провайдера (500/400), связка Email и Phone при различных сценариях входа, проверка `secure_compare` на тайминг-атаки.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус).
2. Линтер и тайпчекер (tsc) выполняются без ошибок.
3. SMS-вход: Пользователь может ввести номер, получить SMS с кодом, успешно войти и остаться авторизованным.
4. Flash Call-вход: Пользователь может выбрать звонок, ввести последние 4 цифры входящего номера и авторизоваться.
5. Защита баланса: Повторная отправка кода заблокирована на 60 секунд (для SMS, Flash Call и Email).
6. Связка данных: Если пользователь зашел по телефону, а затем указал email (или наоборот), данные сохраняются в одну карточку mobile_customers.
7. Dev-режим: В локальной среде разработки коды пишутся в лог без реальной отправки смс.
