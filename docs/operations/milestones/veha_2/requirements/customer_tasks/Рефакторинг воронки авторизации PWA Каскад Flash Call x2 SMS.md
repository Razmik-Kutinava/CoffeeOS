# Рефакторинг воронки авторизации PWA (Каскад Flash Call x2 > SMS)

**Артефакты:** docs/operations/milestones/veha_2/artifacts/auth_funnel_flash_call_x2_sms_ru/

Бизнес-цель: Повысить конверсию регистрации у кассы за счет перехода к 2-экрановому Wizard с автоматическим 3-уровневым каскадом верификации (Flash Call #1 → Flash Call #2 → СМС) без трения и лишних полей, снизив стоимость привлечения (CAC).

## Глобальные ограничения
- При построении UI/UX компонентов строго руководствоваться существующим UX Guide проекта.
- Запрещено использовать поле Email, радиокнопки ручного выбора канала и отдельные кнопки подтверждения кода.
- Запрещен хардкод: Все API-ключи, api_id и буквенные имена отправителей (from) хранить строго в ENV (`ENV['SMS_RU_API_ID']`, `ENV['SMS_RU_FROM']`).
- Dev-режим: При `ENV['SHOP_OTP_LOG_FALLBACK'] = true` реальная отправка СМС/вызовов блокируется (код пишется в `Rails.logger`), либо в SMS.ru передается параметр `test=1`.

## Сценарии и чек-лист (Для todo.md)

- [ ] Шаг 1: Очистка UI и Экран 1 (Ввод номера телефона)
  - Given: Пользователь открыл экран авторизации. Старые элементы (Email, радиокнопки) удалены.
  - When: Пользователь взаимодействует с Экраном 1.
  - Then: Поле ввода имеет автофокус и маску `+7 (9XX) XXX-XX-XX`. Кнопка «Продолжить» активна строго при вводе 10 цифр. При клике отправляется запрос `POST /shop/api/phone_otp/send` с `channel: "flash_call"` и происходит бесшовный переход на Экран 2. При ошибках сети отображается системное уведомление (toast).

- [ ] Шаг 2: Экран 2 (Ввод кода, авто-сабмит и обработка ошибок)
  - Given: Пользователь перешел на Экран 2.
  - When: Пользователь вводит код, ошибается или нажимает кнопку возврата.
  - Then: 
    - Отображается поле ввода из 4 отдельных ячеек (согласно UX Guide). 
    - При вводе 4-й цифры происходит авто-сабмит `POST /shop/api/phone_otp/verify`.
    - При неверном коде (HTTP 422): подсвечивать ячейки ошибкой, включать shake-анимацию, очищать поле и возвращать фокус на 1-ю ячейку.
    - Отображается кнопка «Изменить номер» (возврат на Экран 1). При клике — сбрасывать таймеры каскада и сбрасывать стейт авторизации.

- [ ] Шаг 3: Стейт-машина каскада (Flash Call #1 и #2)
  - Given: Пользователь находится на Экране 2, запущен таймер каскада.
  - When: Проходит время или пользователь нажимает кнопку повторного звонка.
  - Then:
    - Шаг 1 (0–20 сек): Подсказка «Введите последние 4 цифры номера, с которого вам звонят. На звонок отвечать не нужно.» и таймер «Ждем звонок... 00:20».
    - Шаг 2 (20–40 сек): Появляется кнопка «Запросить звонок еще раз». При нажатии (или по истечении 20 секунд) вызывается `POST` с `channel: "flash_call"`, таймер перезапускается еще на 20 секунд.

- [ ] Шаг 4: Стейт-машина каскада (SMS Fallback)
  - Given: Прошло 40 секунд с начала верификации (или завершился Flash Call #2).
  - When: Наступает таймаут (40 сек) или пользователь нажимает кнопку «Отправить код в СМС».
  - Then:
    - Шаг 3 (40сек+): Появляется кнопка «Отправить код в СМС».
    - При клике (или авто-переходе на 40-й секунде) отправляется запрос `POST /shop/api/phone_otp/send` с `channel: "sms"`.
    - Текст подсказки меняется на: «Отправили 4-значный код в СМС на номер +7 (9XX) XXX-XX-XX».
    - Запускается кулдаун повторной отправки кнопки СМС на 60 секунд.

- [ ] Шаг 5: Бэкенд — Интеграция `Shop::SmsRuClient`
  - Given: Настроен сервис `Shop::SmsRuClient` для взаимодействия с API sms.ru.
  - When: Вызывается метод отправки для `channel: "flash_call"` или `channel: "sms"`.
  - Then:
    - Для Flash Call (`channel: "flash_call"`): Запрос к `https://sms.ru/code/call` с `phone`, `api_id` и `ip` (`request.remote_ip`). Из ответа SMS.ru проверяется `json["status"] == "OK"`, извлекается `json["code"]` и сохраняется/перезаписывается в БД `mobile_otp_codes` (TTL = 10 мин).
    - Для СМС (`channel: "sms"`): Из БД `mobile_otp_codes` извлекается **последний сохраненный код** и отправляется через `https://sms.ru/sms/send` (`to`, `msg="Ваш код: XXXX"`, `from=ENV['SMS_RU_FROM']`, `json=1`, `ip`).
    - При сетевых ошибках, HTTP 400/500 или ответных JSON c `status != "OK"` (например, `status_code: 207`) ошибка обрабатывается, сервер не падает с 500, а возвращает вменяемый JSON с описанием проблемы.

- [ ] Шаг 6: Бэкенд — Кулдауны и Rate Limit
  - Given: Настроены `Rack::Attack` и сервис OTP.
  - When: Пользователь запрашивает повторную отправку кода.
  - Then: Для `flash_call` кулдаун между запросами составляет 20 секунд, для `sms` — 60 секунд. При превышении частоты вызовов возвращается HTTP status 429 Too Many Requests.

## Стратегия тестирования
- Фреймворк: RSpec (Backend Rails), Vitest/Jest (Frontend PWA)
- Путь к файлам тестов: `spec/services/shop/sms_ru_client_spec.rb`, `spec/requests/shop/api/phone_otp_spec.rb`, `src/**/*.test.ts(x)`
- Критические кейсы:
  - Frontend: Точность срабатывания стейт-машины таймера (20с → 20с → СМС на 40с), авто-сабмит ровно при вводе 4-й цифры, очистка и сброс поля при ошибочном коде (422), сброс таймеров при смене номера.
  - Backend (SMS.ru): Парсинг ответа `/code/call`, сохранение и перезапись `json["code"]` при повторном звонке. Проверка отправки СМС с актуальным кодом. Передача `request.remote_ip` во все запросы. Эмуляция ответов SMS.ru с ошибками в JSON (`status: "ERROR"`) и сетевых сбоев.

## Exit Criteria (Критерии выхода)
1. Все RSpec и Vitest тесты проходят без ошибок.
2. Линтер и тайпчекер (tsc) выполняются без ошибок.
3. Интерфейс на 100% соответствует UX Guide (удалены Email/радиокнопки, работает 2-шаговый Wizard).
4. Ошибки ввода кода (422) корректно анимируются и очищают форму.
5. Звонок Flash Call совершается через SMS.ru, код из ответа перезаписывается и валидируется.
6. На шаге СМС отправляется тот же актуальный код, что закладывался под последний звонок.
7. Защита по IP (`request.remote_ip`) передается во все запросы к SMS.ru.
8. Rate limits в `Rack::Attack` соответствуют таймингам каскада (20с для звонка / 60с для СМС).
