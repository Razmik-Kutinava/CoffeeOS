# TASK_100: Точные сообщения при ошибке оплаты и отдельный CTA

> **ID заказчика:** TASK_100 · **CBR:** #100 · **Intake:** 2026-10-05  
> **Источник:** [Google Doc](https://docs.google.com/document/d/1YobR2fPhH0_6MDuAkD56tup7kGSE78gbf30NgpAx1_s/edit?usp=sharing)  
> Артефакты: нет (только Google Doc)

**Тип:** новая задача (сценарий нигде не зафиксирован)

**Расширяет:** `docs/operations/milestones/veha_2/requirements/customer_tasks/TASK-26-REPEAT-ORDER-INVALID-TOKEN-EXT.md`

**Бизнес-цель:** При ошибке оплаты показывать пользователю конкретное сообщение в зависимости от подтверждённой причины ошибки и отдельно показывать действие, которое следует выполнить. Не смешивать текст причины ошибки с CTA.

## 1. Карта интеграций

Затронуто:

1. backend payment API → передача `error_code` и `error`;
2. frontend checkout → классификация ошибки оплаты;
3. `PaymentMethodsSheet.svelte` → отображение сообщения и CTA.

Не затрагивать:

1. контракт HTTP 422 из Patch 1;
2. механику получения/обновления payment token;
3. FSM авторизации/оплаты за пределами классификации и отображения ошибки.

## 2. Карта компонентов

Компоненты:

1. `app/frontend/lib/shopPayFsm.js`
2. `app/frontend/routes/Checkout.svelte`
3. `app/frontend/components/PaymentMethodsSheet.svelte`
4. связанные тесты payment error / repeat invalid token.

**Общий файл с другими задачами:** да.

Граница:

1. разрешено изменить только классификацию и отображение пользовательского сообщения/CTA для payment error;
2. запрещено менять существующую механику repeat-order, payment token, открытие/закрытие BottomSheet и другие сценарии оплаты.

`COMPONENT_MAP.md` на этапе Spec не изменять.

## 3. Текущее поведение — факт

Backend передаёт `error_code` и текст ошибки.

Frontend получает эти значения, но текущий resolver сводит ряд ошибок к одному сообщению:

«Недостаточно средств, или карта заблокирована банком, или истёк срок действия карты»

При этом отдельного CTA с инструкцией пользователю нет: сообщение ошибки и действие фактически смешаны.

## 4. Scope

### Разрешено

1. классифицировать payment error по подтверждённой семантике;
2. использовать отдельные пользовательские тексты согласно Матрице;
3. отделить текст ошибки от CTA;
4. для подтверждённой карточной ошибки без отдельного текста использовать карточный fallback;
5. для ошибки без подтверждённой карточной семантики использовать общий payment fallback;
6. добавить/изменить тесты, фиксирующие матрицу.

### Запрещено

1. определять неизвестный `error_code` как блокировку карты без подтверждения;
2. придумывать отдельный текст для каждого `error_code`;
3. менять HTTP-контракт backend;
4. менять payment token / auth store / refresh token;
5. менять FSM оплаты за пределами необходимой классификации ошибки;
6. менять механику открытия/закрытия `PaymentMethodsSheet`;
7. автоматически открывать форму добавления карты;
8. менять сценарии SBP;
9. менять тексты, не относящиеся к payment error.

## 5. Матрица пользовательских сообщений

**Матрица является источником истины для реализации и тестов.**

| Категория | Условие | Сообщение | CTA |
| --- | --- | --- | --- |
| Недостаточно средств | error_code = 1051 | Недостаточно средств на карте | Изменить карту |
| Истёк срок карты | error_code = 1014 | Срок действия карты истёк | Изменить карту |
| Слишком много попыток | error_code = 119 или 2200 | Слишком много попыток оплаты. Попробуйте позже | Попробовать позже |
| Карточная ошибка | подтверждённая карточная семантика, но нет отдельного пользовательского текста | Не удалось списать деньги. Обратитесь в банк — этой картой нельзя оплатить заказ. | Изменить карту |
| Общая ошибка оплаты | нет подтверждённой карточной семантики | Не удалось выполнить оплату. Попробуйте ещё раз | Повторить оплату |

### Правила классификации

1. `1051` всегда относится к категории «Недостаточно средств».
2. `1014` всегда относится к категории «Истёк срок карты».
3. `119` и `2200` относятся к категории «Слишком много попыток».
4. Если backend/code подтверждает, что ошибка относится именно к карте, но отдельного пользовательского текста для неё нет → карточный fallback.
5. Если подтверждённой карточной семантики нет → общий payment fallback.
6. **Не считать неизвестный `error_code` автоматически карточной ошибкой.**
7. Если конкретный `error_code` невозможно уверенно классифицировать по существующему коду/backend message → `[ОТКРЫТЫЙ ВОПРОС]`. До выяснения классификацию не придумывать.

## 6. Gherkin

1. **Subtask:** Given payment error `1051`, When ошибка отображается в PaymentMethodsSheet, Then пользователь видит `Недостаточно средств на карте` и CTA `Изменить карту`.
2. **Subtask:** Given payment error `1014`, When ошибка отображается в PaymentMethodsSheet, Then пользователь видит `Срок действия карты истёк` и CTA `Изменить карту`.
3. **Subtask:** Given payment error `119` или `2200`, When ошибка отображается в PaymentMethodsSheet, Then пользователь видит `Слишком много попыток оплаты. Попробуйте позже` и CTA `Попробовать позже`.
4. **Subtask:** Given подтверждённая карточная ошибка без отдельного пользовательского текста, When ошибка отображается в PaymentMethodsSheet, Then пользователь видит `Не удалось списать деньги. Обратитесь в банк — этой картой нельзя оплатить заказ.` и CTA `Изменить карту`.
5. **Subtask:** Given ошибка оплаты без подтверждённой карточной семантики, When ошибка отображается в PaymentMethodsSheet, Then пользователь видит `Не удалось выполнить оплату. Попробуйте ещё раз` и CTA `Повторить оплату`.
6. **Subtask:** Given неизвестный `error_code`, When его невозможно классифицировать по существующему коду/backend message, Then классификация не придумывается и вопрос помечается как `[ОТКРЫТЫЙ ВОПРОС]`.
7. **Subtask:** Given payment error, When отображается сообщение ошибки, Then текст причины ошибки и CTA являются отдельными UI-элементами и не объединяются в одну строку.

## 7. Защитные тесты

Обязательно сохранить проверки:

1. `1051` не должен возвращаться к старому общему тексту про недостаток средств / блокировку / срок карты;
2. `1014` не должен классифицироваться как недостаток средств;
3. `119/2200` не должны классифицироваться как карточная ошибка;
4. неизвестный `error_code` не должен автоматически считаться блокировкой карты;
5. ошибка не должна автоматически открывать форму добавления новой карты;
6. существующий repeat-order invalid-token flow не должен измениться.

## 8. Общий файл и граница с другими задачами

`shopPayFsm.js` является общим кодом для нескольких задач.

**Не трогать:**

1. payment token;
2. repeat-order flow;
3. HTTP 422 contract;
4. payment method selection;
5. SBP;
6. открытие/закрытие BottomSheet;
7. другие состояния FSM, не связанные с отображением payment error.

Изменения ограничить классификацией payment error и передачей отдельного `message` + `CTA`.

## 9. i18n

Все пользовательские тексты должны быть вынесены в существующий механизм i18n.

Не добавлять hardcoded пользовательские строки в JS/Svelte.

Ключи i18n должны соответствовать категориям матрицы, а не отдельным `error_code`, если несколько кодов имеют одну категорию.

## 10. Открытые вопросы

До Build проверить только фактическую классификацию остальных `error_code`.

Не требуется отдельно придумывать текст для каждого кода.

Правило:

1. `1051` → недостаточно средств;
2. `1014` → срок карты истёк;
3. `119/2200` → слишком много попыток;
4. подтверждённая карточная ошибка без отдельного текста → карточный fallback;
5. ошибка без подтверждённой карточной семантики → общий payment fallback.

Если для конкретного кода невозможно определить категорию по существующему коду/backend message:

`[ОТКРЫТЫЙ ВОПРОС]`

В этом случае **не придумывать классификацию**.

Если после проверки остаются `[ОТКРЫТЫЙ ВОПРОС]`, документ не готов к Build.
