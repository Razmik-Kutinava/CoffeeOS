# TASK_83: Поведение крестика (dismiss) в статусной шторке

Бизнес-цель: Формализовать поведение локального dismiss заказа через крестик (×) в статусной шторке, чтобы реализация и тесты однозначно соответствовали продуктовому решению.

## 1. Связь с картой интеграций
- **Затронутые сервисы из `@INTEGRATIONS.md`:** нет.
- **Смежные модули, которые НЕЛЬЗЯ ломать:** блок чека / `receiptView`, Cable-подписка.

## 2. Связь с картой компонентов
- **Затронутые компоненты из `@COMPONENT_MAP.md`:** `ActiveOrdersAccordion`, `OrderStatusSheet`.
- **Общий файл с другой задачей:** да — с задачей «Восстановление чека». В рамках этой задачи разрешена только логика dismiss:
  - `ActiveOrdersAccordion.svelte:139–150` — `aoa__dismiss`;
  - `orderStatusSheet.js:119–132` — `dismissOrder` / `refreshMode`.
  Блок чека принадлежит соседней задаче и не изменяется.
- **Новый компонент (не в карте):** нет.

## 3. Разрешенный и Запрещенный Scope
- **Разрешено менять/создавать:**
  - `ActiveOrdersAccordion.svelte:139–150` — только dismiss-обработку;
  - `orderStatusSheet.js:119–132` — только `dismissOrder` / связанную логику `refreshMode`;
  - тесты, необходимые для покрытия зафиксированного dismiss-контракта.
- **Строго запрещено менять:**
  - блок чека / `receiptView`;
  - `shopOrderCable.js` и Cable-подписку;
  - API и интеграционные контракты;
  - статусную бизнес-логику, не связанную с dismiss;
  - компоненты и файлы вне указанного Scope.

## 4. Сценарии и Чек-лист (Gherkin)

- [ ] **Subtask 1: Зафиксировать dismiss как локальное действие**
  - Given: в статусной шторке отображается заказ.
  - When: пользователь нажимает крестик (×).
  - Then: вызывается существующий `onDismiss(order)`, заказ передается в `dismissOrder`, состояние dismiss обновляется локально без API-вызова.
  - Error: нажатие на × не должно изменять серверный статус заказа.

- [ ] **Subtask 2: Зафиксировать поведение dismiss при Cable-обновлении**
  - Given: пользователь закрыл заказ крестиком, `dismissedIds[id] = true`, после чего заказ получает обновление через Cable.
  - When: состояние заказа обновляется до перехода в `ready`.
  - Then: **реализация выполняется согласно принятому продуктовому решению:** заказ [остается скрытым / снова отображается] до перехода в `ready`.
  - Error: Cable-обновление не должно само по себе отменять локальный dismiss, если это запрещено принятым продуктовым решением.

- [ ] **Subtask 3: Зафиксировать поведение dismiss после перезагрузки**
  - Given: пользователь закрыл заказ крестиком.
  - When: страница перезагружается и состояние статусной шторки создается заново.
  - Then: **реализация выполняется согласно принятому продуктовому решению:** заказ [остается скрытым / снова отображается] после перезагрузки.
  - Error: перезагрузка не должна изменять серверный статус заказа.

- [ ] **Subtask 4: Реализовать принятое поведение в `ActiveOrdersAccordion`**
  - Given: пользователь видит крестик dismiss у заказа.
  - When: пользователь нажимает ×.
  - Then: `aoa__dismiss` вызывает dismiss-логику без изменения блока чека и без API-вызова.
  - Error: ошибка dismiss не должна затрагивать `receiptView` или Cable-подписку.

- [ ] **Subtask 5: Реализовать принятое поведение в `OrderStatusSheet`**
  - Given: `dismissOrder(sheet, id)` получает идентификатор заказа.
  - When: выполняется dismiss.
  - Then: `dismissedIds`, `userDismissed` и `refreshMode` приводят состояние шторки к поведению, зафиксированному в Subtask 2–3.
  - Error: dismiss не должен менять серверный статус заказа.

- [ ] **Subtask 6: Покрыть dismiss-контракт тестами**
  - Given: продуктовое поведение dismiss зафиксировано.
  - When: запускается существующий тестовый набор.
  - Then: тесты проверяют клик ×, локальное скрытие, Cable-обновление и восстановление состояния после перезагрузки согласно принятому контракту.
  - Error: существующие сценарии статусной шторки не должны регрессировать.

## 6. Продуктовые решения до RED/GREEN

Перед переходом к реализации необходимо зафиксировать:

1. **Поведение после Cable-обновления:** заказ остается скрытым до `ready` либо снова появляется в шторке.
2. **Поведение после перезагрузки:** dismiss сохраняется либо заказ снова появляется.

До принятия этих двух решений Cursor не должен самостоятельно выбирать поведение.
