## Проблема (заказчик)

Табло в формате to-do list: ручное перетаскивание, нет крупной кнопки статуса, нет цветовой обратной связи, модификаторы не видны, нет FIFO, гость не всегда получает понятный статус, нет механик исключений в карточке.

---

## Решение (текст заказчика)

### Блок 1. Интерактивная карточка

- Квадратный блок фиксированного размера: номер, время, состав с модификаторами (**+ ПО КРЕПЧЕ** / **БЕЗ Сахара**).
- Кнопка ≥ 80 px: «Оплачен» → **ГОТОВИТСЯ**; «Готовится» → **ГОТОВ**.
- Цвет: оплачен — синий; готовится — оранжевый; готов — зелёный.

### Блок 2. FIFO

- Очередь по `created_at`, без ручного reorder.
- При смене статуса карточка переходит в следующую колонку.

### Блок 3. Уведомления клиенту

- «Оплачен» → «Готовится»: **«Ваш заказ начали готовить»**.
- «Готовится» → «Готов»: **«Заказ готов, забирайте!»**
- WebSocket; при сбое — повтор до 3 раз, интервал 5 с.

### Блок 4. Исключения

- **Отмена (MVP упрощённо):** overlay «СТОП! ЗАКАЗ ОТМЕНЁН», подтверждение; без звука/списания.
- **Брак / переделка / возврат:** фаза 2/3.

### Ограничения

- Цепочка: Принят → Оплачен → Готовится → Готов.
- Без ручного порядка и произвольного следующего статуса.
- Брак — не бариста (фаза 2/3).

### Текст заказчика (дословно)

> **Задача:** Реализовать звуковое оповещение о поступлении новых заказов на табло бариста (PWA/браузер)
>
> **Описание задачи**
>
> **Проблема**  
> Бариста не всегда своевременно замечают поступление новых заказов на экране табло, так как заняты приготовлением напитков и не могут постоянно контролировать экран визуально. Это приводит к увеличению времени реакции на заказ, росту времени ожидания клиента и снижению общей скорости обслуживания.
>
> **Решение**  
> Продуктовые требования: Бариста получает автоматическое звуковое уведомление при поступлении нового заказа, что позволяет сократить время реакции и повысить скорость обслуживания без необходимости постоянного визуального контроля экрана.  
> Технологические требования: Реализация на стороне фронтенда с использованием JS (HTML5 Audio API / Web Audio API). Использование WebSocket (или Server-Sent Events) для получения события о новом заказе без перезагрузки страницы. Реализация механизма обхода политики автоплея браузеров (Autoplay Policy) через инициализацию AudioContext по действию пользователя.
>
> **User Story**  
> Как бариста,  
> Я хочу слышать звуковой сигнал при поступлении нового заказа на табло,  
> Чтобы я мог сразу начать его готовить, не отвлекаясь на постоянный визуальный контроль экрана, и сократить время обслуживания клиента.
>
> **Use Case (Алгоритм взаимодействия)**
> 1. Бариста открывает табло в браузере или PWA.
> 2. Бариста нажимает кнопку «Открыть смену» (или проходит авторизацию).
> 3. Система инициализирует AudioContext (воспроизводит короткий технический пик или тишину), разблокируя аудио-движок браузера для текущей сессии.
> 4. Сервер отправляет событие о новом заказе через WebSocket-соединение.
> 5. Фронтенд получает событие, сбрасывает указатель трека (`audio.currentTime = 0`) и вызывает метод `.play()` для аудиофайла.
> 6. Звук воспроизводится, новый заказ отображается на экране.
>
> **Ограничения (чего не делаем)**
> - Не разрабатываем нативное мобильное приложение (решение реализуется только для Web/PWA).
> - Не меняем существующую бизнес-логику формирования, валидации и маршрутизации заказов на бэкенде.
> - Не реализуем пользовательские настройки звука (выбор мелодии, регулировка громкости из интерфейса) в рамках данной задачи.
>
> **Критерии приёмки**
>
> | Измеритель | Целевой показатель | Критерий успеха (допустимое отклонение) |
> |------------|-------------------|----------------------------------------|
> | Процент успешных воспроизведений звука при поступлении нового заказа (после инициализации AudioContext) | 100% | 100% (отклонение не допускается) |
> | Время задержки между получением WebSocket-сообщения и фактическим началом воспроизведения звука | ≤ 0.5 секунды | ≤ 1.0 секунды |
> | Наличие визуального индикатора при блокировке звука браузером | Отображение индикатора с текстом: «Звук заблокирован. Кликните по экрану для включения» | 100% случаев перехвата ошибки NotAllowedError (или аналогичной) от `.play()` |
>
> **Технические детали для разработки**
> - Формат аудиофайла: `.mp3` или `.wav`.
> - Длительность аудиофайла: 1.5 – 3.0 секунды.
> - Кэширование: Файл должен быть загружен и закэширован на стороне клиента при инициализации, чтобы не скачиваться повторно при каждом заказе.
> - Обработка ошибок: Использовать `try/catch` или `.catch()` на промисе `.play()`. При ошибке выводить стандартизированное сообщение в консоль разработчика и отображать визуальный индикатор на экране табло.
>

### Ссылки заказчика — что важно для нас

**Chrome Autoplay Policy:**
- Звук без жеста пользователя блокируется; приглушённый autoplay разрешён, со звуком — только после взаимодействия с доменом (click/tap) или PWA на главном экране.
- `AudioContext`, созданный до жеста, в состоянии `suspended` → нужен `resume()` после клика («Открыть смену»).
- Промис `.play()` может отклониться с `NotAllowedError` → ловить и показывать UI, не предполагать что звук играет.

**MDN Web Audio API:**
- Цепочка: `AudioContext` → источник (`AudioBufferSourceNode` / `<audio>`) → `destination`.
- Для короткого сигнала: предзагрузка буфера / `HTMLAudioElement` + `currentTime = 0` перед каждым `play()`.
