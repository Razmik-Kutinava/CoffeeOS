## Текст задачи (дословно) — Google Doc Spec

TASK_115: CODE:BLACK — явное членство точек в сети

**Тип:** новая задача (сценарий нигде не зафиксирован)
**Версия:** v4 (2026-10-25)
Бизнес-цель: обеспечить надёжное серверное определение точек, относящихся к бренду CODE:BLACK, независимо от организаций-франчайзи; признак задаёт глобальный администратор в админ-панели при создании и редактировании точки.

### 1. Карта интеграций — затронуто / нет
Затронуто: таблица "tenants" ("db/schema.rb:1380-1396"); админ-панель "/admin/tenants" ("Platform::TenantsController", "app/controllers/platform/tenants_controller.rb:17-63,88-130,146-151", форма "app/views/platform/tenants/_form.html.erb:1-63", политики "TenantPolicy", "PlatformPolicy"); журнал "admin_audit_logs" ("db/schema.rb:26-42"); серверные потребители списка точек сети (история CODE:BLACK, проверка ссылки SMS); тесты.
Не затронуто: каскад отправки SMS; платежи, checkout, Quick Repeat, Wallet; объединение клиентских записей; общая модель организаций-франчайзи; проверка статуса точки витриной.

### 2. Карта компонентов
- "Tenant" ("app/models/tenant.rb:9-14,63-69"): строки type и status без enum, валидации name, slug, type, status, country, currency.
- "Platform::TenantsController": создание и обновление выполняются в транзакции и вызывают "TenantOnboarding::Provision"; поле добавляется в список разрешённых параметров.
- Форма и список точек: поле «Сеть CODE:BLACK» и колонка в списке.
- Новый явный серверный признак на точке: булев NOT NULL с default false (либо отдельная сущность; выбор при сборке с обоснованием); по умолчанию и при неизвестном значении точка в сеть не входит.
- "AdminAuditLog": запись изменения признака (сейчас журнал для точек не пишется: в контроллере и в "app/services/platform/tenant_onboarding/" обращений нет).
- Доступ: только роль "uk_global_admin" на трёх уровнях ("base_controller.rb:8,38-42", "platform_policy.rb:6-8", "tenant_policy.rb:6-32"); код роли в БД содержит кириллическое «ук» ("app/models/user.rb:74-76"): тесты используют точную строку. Менеджеры и франчайзи точки не редактируют ("manager/tenant_context_controller.rb:8-27").
Общий файл с другими задачами: да ("Tenant", "Organization", определение текущей точки, общие API авторизации). Граница обязательна.

### 3. Текущее поведение — факты аудитов
- "tenants.organization_id" допускает "NULL" ("db/schema.rb:1389,1602", "tenant.rb:40"); "organizations" содержит name и slug ("db/schema.rb:692-698"); явного признака сети нет.
- Типы точек: "sales_point", "production_kitchen" ("tenant.rb:9"); статусы в модели: "active", "warning", "suspended", "blocked", "frozen" ("tenant.rb:10"); код пишет также "inactive", которого нет в модели ("app/services/platform/prod_single_point_cleanup.rb:55,61"). Торговая точка: type == "sales_point" ("tenant.rb:12-14"). Новая точка с платформы создаётся как sales_point/active ("platform/tenants_controller.rb:13").
- Витрина статус точки не проверяет: "Tenant.find_by(id: tid)" ("shop/api/base_controller.rb:27"); статус учитывается только в запасном варианте с единственной точкой ("tenant_resolution.rb:27").
- Название CODE:BLACK встречается в брендинге и конфигурации, но не является проверяемым признаком.
- Формой создания и редактирования точек владеет "uk_global_admin"; удаления точек нет.
- Под RLS в "tenants" при флаге "app.shop_city_lookup" видны только активные торговые точки ("20260918123000_add_rls_tenants_shop_city_lookup_policy.rb:5-26"); чтение признака других точек из клиентского контекста зависит от результата TASK-PRODUCTION-RLS-VERIFY-HARDEN.
Фактическое состояние production и перечень production-точек не подтверждены.

### 4. Scope
Разрешено: явный серверный признак; поле в форме и колонка в списке; запись в "admin_audit_logs"; безопасное поведение для неизвестного значения; серверный способ получить точки CODE:BLACK; тесты.
Запрещено: определять членство по "organization_id", "slug", названию; включать все точки CoffeeOS автоматически; включать существующие точки автоматически при выкладке; ослаблять tenant isolation и RLS; менять авторизацию, роли, SMS, платежи, push, Wallet; менять "TenantOnboarding::Provision" сверх сохранения значения признака по умолчанию; менять проверку статуса точки витриной.
Решение владельца 2026-10-21 (R6): членство задаётся вручную в админ-панели при создании и редактировании точки; по умолчанию точка не в сети; существующие точки владелец отмечает сам.

### 5. Gherkin
- [ ] Subtask 1: Given точка существует и принадлежит организации-франчайзи, When сервер определяет принадлежность к CODE:BLACK, Then решение основано на явном серверном признаке, а не на организации или slug.
- [ ] Subtask 2: Given точки CODE:BLACK принадлежат разным организациям, When сервер получает список точек сети, Then все явно включённые точки учитываются независимо от "organization_id".
- [ ] Subtask 3: Given точка использует CoffeeOS, но не включена в CODE:BLACK, When сервер получает список точек сети, Then она не включается.
- [ ] Subtask 4: Given принадлежность не определена, When формируется выборка сети, Then точка не включается; неизвестное значение не трактуется как разрешение.
- [ ] Subtask 5: Given две точки принадлежат разным сетям или одна не включена, When выполняется выборка, Then данные и доступ не расширяются за пределы явного членства.
- [ ] Subtask 6 (форма): Given глобальный администратор создаёт или редактирует точку, When отмечает «Сеть CODE:BLACK» и сохраняет, Then признак записывается.
- [ ] Subtask 7 (журнал): Given признак изменён при создании или редактировании, Then в "admin_audit_logs" появляется запись (кто, когда, было, стало); изменение других полей точки журнал не затрагивает, если это не будет решено отдельно.
- [ ] Subtask 8 (новая точка): Given точка создаётся без отметки, Then она не входит в сеть.
- [ ] Subtask 9 (существующие точки): Given выкладка завершена, Then ни одна существующая точка не включена автоматически; в списке точек видна колонка признака.
- [ ] Subtask 10 (права): Given пользователь не "uk_global_admin" (менеджер, франчайзи, остальные роли), When пытается изменить признак, Then изменение отклонено, как для остальных полей точки.
- [ ] Subtask 11 (тип точки): Given точка с type = "production_kitchen", Then признак не может быть включён; признак доступен только для type = "sales_point".
- [ ] Subtask 12 (чтение сетью): Given потребитель запрашивает точки сети, Then выборка не зависит от status точки: закрытая точка (status не "active") остаётся в сети; видимость неактивных точек под RLS определяет TASK-PRODUCTION-RLS-VERIFY-HARDEN.
- [ ] Subtask 13 (статус и членство): Given точка меняет статус (suspended, blocked, frozen, warning), Then признак членства не меняется автоматически.

### 6. TDD-проверка
Обязательные тесты: членство у нескольких организаций; исключение точки вне сети; неизвестное значение; отсутствие зависимости от "organization_id" и "slug"; запись в "admin_audit_logs"; права по ролям (точная строка роли); новая точка не в сети; production_kitchen не может быть в сети; закрытая точка остаётся в сети; регрессия tenant isolation.
Точные команды определить по структуре тестов при сборке.
Статус: документ готов к Build (миграция, форма, журнал); чтение членства из клиентского контекста ждёт E.
