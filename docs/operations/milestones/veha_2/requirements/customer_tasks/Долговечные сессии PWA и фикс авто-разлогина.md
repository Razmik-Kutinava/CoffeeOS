# Долговечные сессии PWA и фикс авто-разлогина 
Бизнес-цель: Устранить принудительный выход пользователей PWA из аккаунта при закрытии приложения и по истечении 24 часов за счет внедрения персистентных кук и механизма Silent Refresh.

## Глобальные ограничения
- Запрещено изменять существующую схему БД (таблица `mobile_sessions` уже готова и не меняется).
- Запрещено ломать или изменять существующий флоу оформления заказов и базовую логику проверки email.
- Запрещено использовать жесткое 24-часовое удаление данных в `shopLocalStorage.js`.
- Запрещено изменять сигнатуры существующих методов `Shop::EmailOtp.verify!` и `Shop::CustomerSession.set_customer_id!` (только расширение их логики/вызов).

## Сценарии и чек-лист (Для todo.md)

- [ ] Шаг 1: Настройка персистентного session_store (Backend)
  - Given: Rails-приложение, где кука сессии не имеет срока жизни и стирается ОС.
  - When: Разработчик настраивает `config/initializers/session_store.rb`.
  - Then: Кука сессии сохраняется с ключом `_coffeeos_session`, TTL `90.days`, `same_site: :lax`. Сессия не стирается при выгрузке PWA.

- [ ] Шаг 2: Создание MobileSession при успешном OTP (Backend)
  - Given: Пользователь успешно ввел код, сессия не авторизована.
  - When: Выполняется `Shop::EmailOtp.verify!`.
  - Then: В БД создается/обновляется запись `MobileSession` (customer_id, `refresh_token` = `SecureRandom.hex(32)`, `expires_at` = 90.days.from_now, `is_active` = true). API `/verify` возвращает этот `refresh_token` в ответе.

- [ ] Шаг 3: Реализация эндпоинта Silent Refresh (Backend)
  - Given: В БД есть запись `MobileSession` (активная/просроченная/неактивная).
  - When: Приходит POST-запрос на `/shop/api/session/refresh` с телом `{ refresh_token: "..." }`.
  - Then: 
    - Если токен валиден (`is_active: true`, `expires_at > Time.current`): восстанавливается сессия (`Shop::CustomerSession.set_customer_id!`), старый токен деактивируется, генерируется новый, `expires_at` продлевается на 90 дней (`update_last_used!`), продлевается запись в `shop_email_verifications`. Возвращается 200 с новым токеном и профилем.
    - Если токен невалиден/просрочен: возвращается 401 Unauthorized.

- [ ] Шаг 4: Сохранение токена и скользящий TTL в LocalStorage (Frontend)
  - Given: Пользователь успешно авторизован или совершает действие в PWA.
  - When: Фронтенд сохраняет данные через `shopLocalStorage.js`.
  - Then: `refresh_token` сохраняется в `localStorage` по ключу `shop_refresh_token` без авто-удаления. Метка `savedAt` обновляется при каждом успешном действии/запросе (скользящий TTL), жесткое сжигание через 24 часа удалено.

- [ ] Шаг 5: Автоматическое восстановление сессии при старте PWA (Frontend)
  - Given: PWA запускается, бэкенд вернул статус "Гость", но в `localStorage` есть `shop_refresh_token`.
  - When: Инициализируется фронтенд-приложение.
  - Then: 
    - Делается фоновый POST `/shop/api/session/refresh`.
    - При ответе 200: сохраняется новый `refresh_token`, UI переводится в состояние "Авторизован".
    - При ответе 401 (или ошибке сети/краше): стирается `shop_refresh_token` из `localStorage`, UI переводится в состояние "Гость".

## Стратегия тестирования
- Фреймворк: RSpec (для Backend Rails), Jest/Vitest (для Frontend JS).
- Путь к файлам тестов: `spec/` (Backend), `__tests__/` или `*.spec.js` рядом с компонентами (Frontend).
- Критические кейсы: 
  - Граничные значения TTL (ровно 90 дней, 90 дней + 1 секунда).
  - Ротация токенов (проверка, что старый токен после refresh возвращает 401).
  - Поведение фронтенда при сетевых ошибках (500/400) во время Silent Refresh (должен оставаться в состоянии Гостя, не падать с крашем).
  - Проверка, что `shopLocalStorage.js` не удаляет данные по истечении 24 часов.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус).
2. Линтер и тайпчекер (tsc) выполняются без ошибок.
3. При выгрузке PWA из памяти и повторном открытии пользователь остается авторизованным.
4. Через 24 часа активная сессия НЕ сбрасывается.
5. Ручное удаление `refresh_token` из `localStorage` или истечение 90 дней корректно переводит пользователя в состояние неавторизованного гостя.
6. Существующий флоу оформления заказов и проверки email не сломан.
