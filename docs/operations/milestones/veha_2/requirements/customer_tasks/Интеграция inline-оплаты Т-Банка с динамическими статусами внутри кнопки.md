# Интеграция inline-оплаты Т-Банка с динамическими статусами внутри кнопки

**Бизнес-цель**: Реализовать бесшовный процесс оплаты без увода пользователя на внешние платежные формы или экраны эквайринга, повышая конверсию за счет динамической обратной связи (смена текста/состояния кнопки) на всех этапах обработки транзакции банком.

## Глобальные ограничения
- **Запрещено** хранить, логировать или передавать на фронтенд секретные ключи (`TerminalKey`, `Password`). Они должны находиться исключительно в `.env` бэкенда.
- **Запрещено** перенаправлять (redirect) пользователя на внешние веб-страницы или формы Т-Банка при любых сценариях.
- **Запрещено** изменять базовый URL API Т-Банка: `https://securepay.tinkoff.ru/v2/`.
- **Запрещено** менять сигнатуры существующих API-эндпоинтов, не участвующих в данной фиче.

## Сценарии и чек-лист (Для todo.md)
*Каждый пункт `- [ ]` — атомарный таск для TDD-цикла (сначала пишется failing-тест, затем реализация).*

- [ ] **Шаг 1: Бэкенд — Инициализация и Charge для рекуррентных платежей**
  - **Given**: Валидные данные платежа (сумма, описание, опционально `RebillId`).
  - **When**: Вызывается внутренний эндпоинт инициализации оплаты.
  - **Then**: Если есть `RebillId`, вызывается `POST /v2/Charge`. Иначе вызывается `POST /v2/Init` с `PayType: "O"` (двухстадийная оплата). В запросе корректно рассчитывается `Token` (SHA-256) с использованием `TerminalKey` и `Password`. Возвращается `PaymentId`.

- [ ] **Шаг 2: Бэкенд — Опрос статуса и автоматическое подтверждение (Confirm)**
  - **Given**: Существующий `PaymentId` со статусом `AUTHORIZED` в Т-Банке.
  - **When**: Вызывается внутренний эндпоинт `GET /api/payment/status`.
  - **Then**: Бэкенд опрашивает `POST /v2/GetState`. При получении `AUTHORIZED` бэкенд автоматически инициирует `POST /v2/Confirm` для списания средств и возвращает фронтенду статус `CONFIRMED`.

- [ ] **Шаг 3: Бэкенд — Обработка Webhook (NotificationURL)**
  - **Given**: Асинхронное уведомление (Webhook) от Т-Банка с финальным статусом транзакции.
  - **When**: Бэкенд получает POST-запрос на `NotificationURL`.
  - **Then**: Статус платежа гарантированно финализируется в БД, игнорируя возможные race conditions с polling-запросами.

- [ ] **Шаг 4: Фронтенд — State Machine кнопки (IDLE → PROCESSING)**
  - **Given**: Кнопка в состоянии `IDLE` с текстом "Оплатить [Сумма] ₽" и атрибутом `active`.
  - **When**: Пользователь кликает по кнопке.
  - **Then**: Кнопка получает атрибут `disabled`, отображается спиннер, текст меняется на "Ещё чуть-чуть..." (Фаза 1, статус NEW). Запускается polling статуса с бэкенда каждые 1500 мс.

- [ ] **Шаг 5: Фронтенд — Динамическая ротация текста в PROCESSING**
  - **Given**: Кнопка в состоянии `PROCESSING` (текст "Ещё чуть-чуть...").
  - **When**: Проходит 1800 мс.
  - **Then**: Текст плавно меняется на "Связываемся с банком..." (Фаза 2, FORM_SHOWED/AUTHORIZING). Через следующие 1800 мс меняется на "Платеж принимается банком..." (Фаза 3, AUTHORIZED). Цикл повторяется до получения финального статуса.

- [ ] **Шаг 6: Фронтенд — Финализация SUCCESS**
  - **Given**: Активный polling и состояние `PROCESSING`.
  - **When**: Бэкенд возвращает статус `CONFIRMED`.
  - **Then**: Все таймеры (ротации и polling) останавливаются. Кнопка становится зеленой, отображается иконка галочки, текст меняется на "Оплачено!".

- [ ] **Шаг 7: Фронтенд — Финализация ERROR и парсинг кодов ошибок**
  - **Given**: Активный polling и состояние `PROCESSING`.
  - **When**: Бэкенд возвращает статус `REJECTED` или `CANCELED`.
  - **Then**: Таймеры останавливаются. Кнопка становится красной. Если код ошибки банка `1051` или указывает на недостаток средств, текст = "Недостаточно средств". Иначе текст = "Ошибка оплаты, попробуйте снова". Через 3 секунды кнопка сбрасывается в `IDLE`.

- [ ] **Шаг 8: Фронтенд — Обработка таймаута (15 секунд)**
  - **Given**: Активный polling и состояние `PROCESSING`.
  - **When**: Проходит 15000 мс без получения финального статуса (`CONFIRMED`/`REJECTED`).
  - **Then**: Таймеры останавливаются, кнопка становится красной, текст = "Время ожидания истекло". Через 3 секунды кнопка сбрасывается в `IDLE`.

## Стратегия тестирования
- **Фреймворк**: 
  - Frontend: Vitest / Jest + React Testing Library.
  - Backend: Jest / Supertest (или аналогичный для вашего стека).
- **Путь к файлам тестов**: 
  - `src/components/PaymentButton/__tests__/`
  - `src/api/payment/__tests__/`
  - `backend/src/controllers/__tests__/payment.controller.spec.ts`
- **Критические кейсы**:
  - **Edge cases**: Имитация сетевой ошибки 500/400 от бэкенда во время polling (кнопка должна перейти в ERROR с текстом "Ошибка оплаты, попробуйте снова" и сброситься через 3 сек).
  - **Лимиты времени**: Строгая проверка интервалов: ротация текста каждые 1800 мс, polling каждые 1500 мс, глобальный таймаут ровно на 15000 мс.
  - **Асинхронность**: Race condition между приходом Webhook и активным polling (данные не должны дублироваться или конфликтовать, статус должен быть финальным).
  - **Безопасность**: Тест на отсутствие `TerminalKey`/`Password` в исходящих фронтенд-запросах и логах.

## Exit Criteria (Критерии выхода)
1. Все новые тесты проходят (зеленый статус, покрытие критических путей ≥ 90%).
2. Линтер (ESLint) и тайпчекер (`tsc --noEmit`) выполняются без ошибок и предупреждений.
3. Ручная проверка в Dev-окружении подтверждает отсутствие редиректов и корректную смену состояний кнопки при эмуляции всех статусов Т-Банка (включая ошибку 1051 и таймаут).
