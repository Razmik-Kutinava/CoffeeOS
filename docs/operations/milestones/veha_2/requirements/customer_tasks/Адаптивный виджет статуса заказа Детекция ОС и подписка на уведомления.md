# Адаптивный виджет статуса заказа: Детекция ОС и подписка на уведомления (Apple Wallet / WebPush)

**Бизнес-цель**: Обеспечить максимальный процент доставки уведомлений о готовности заказа за счет автоматического определения операционной системы пользователя и предложения нативного, наиболее эффективного варианта подписки (Apple Wallet для iOS, WebPush для Android/Desktop) в нижнем баре заказа.

## Глобальные ограничения
- **Запрещено** использовать тяжелые сторонние библиотеки для определения ОС (использовать только легковесную утилиту `getDeviceOS`).
- **Запрещено** использовать инлайн-стили для верстки (кроме динамических `blobUrl`). Все стили должны быть реализованы через Tailwind CSS в соответствии с дизайн-системой проекта.
- **Запрещено** менять глобальную архитектуру модальных окон. Для кнопки "Состав заказа" использовать стандартный компонент модалки, принятый в проекте.
- **Обязательное требование UX**: Размещение кнопок, отступы, типографика, скругления и поведение индикаторов загрузки (лоадеров) должны строго соответствовать устоявшимся UX-паттернам и UI-киту внутри текущего проекта.

- [ ] **Шаг 1: Утилита детекции ОС (`src/utils/deviceDetect.ts`)**
  - Given: Чистое окружение с возможностью мока `navigator.userAgent` и `navigator.platform`.
  - When: Вызывается функция `getDeviceOS()`.
  - Then: Функция возвращает `'ios'` для iPhone/iPod и iPadOS 13+ (MacIntel + maxTouchPoints > 1), `'android'` для Android, `'desktop'` в остальных случаях (включая SSR, где `window` undefined).
  - *TDD*: Написать `src/utils/__tests__/deviceDetect.test.ts` с моками UserAgent до реализации функции.

- [ ] **Шаг 2: Базовая верстка и рендер компонента (`src/components/orders/OrderStatusBottomBar.tsx`)**
  - Given: Компонент смонтирован, `getDeviceOS()` возвращает `'ios'`, `'android'` или `'desktop'`.
  - When: Происходит рендер компонента.
  - Then: Отображается фиксированный нижний бар (`fixed bottom-0 left-0 right-0 z-50`, bg `#1E1E1E`, `rounded-t-2xl`). В правой секции (`flex flex-col gap-2 w-44`) рендерятся две кнопки. Нижняя: "Состав заказа". Верхняя: текст зависит от ОС (iOS: " Карта в Apple Wallet", Android/Desktop: "🔔 Уведомление о готовности"). Стили кнопок соответствуют UI-киту проекта (bg `#FF8A3D`, `text-xs font-semibold text-black`, `rounded-lg`, `h-9`).
  - *TDD*: Написать снапшот-тесты и тесты на наличие текстов в зависимости от мока `getDeviceOS`.

- [ ] **Шаг 3: Интеграция нижней кнопки "Состав заказа"**
  - Given: Компонент отрендерен.
  - When: Пользователь кликает на нижнюю кнопку.
  - Then: Открывается стандартная модалка проекта с деталями чека. Состояние лоадера не активируется.
  - *TDD*: Написать тест на вызов функции открытия модалки (mock) при клике.

- [ ] **Шаг 4: iOS Flow – Добавление в Apple Wallet**
  - Given: ОС = `'ios'`, localStorage не содержит `order_{id}_wallet_added = true`.
  - When: Пользователь кликает на верхнюю кнопку.
  - Then: 
    1. Кнопка переходит в состояние `isLoading = true` (отображается стандартный для проекта спиннер).
    2. Выполняется GET запрос на `/api/v1/orders/:id/wallet_pass` с `responseType: 'blob'`.
    3. При успехе (200): создается `blobUrl`, выполняется `window.location.href = blobUrl`. В localStorage записывается `order_{id}_wallet_added = true`. Текст кнопки меняется на "[ ✓ Карта добавлена ]", `isLoading = false`.
    4. При ошибке (400/500): `isLoading = false`, выводится стандартный для проекта toast об ошибке, текст кнопки не меняется.
  - *TDD*: Написать тест с моками `fetch`, `window.location` и `localStorage`.

- [ ] **Шаг 5: Android/Desktop Flow – WebPush подписка**
  - Given: ОС = `'android'` или `'desktop'`, `Notification.permission !== 'granted'`.
  - When: Пользователь кликает на верхнюю кнопку.
  - Then:
    1. Кнопка переходит в состояние `isLoading = true`.
    2. Вызывается `Notification.requestPermission()`.
    3. Если `'granted'`: инициализируется ServiceWorker, получается PushSubscription (с VAPID key), отправляется POST запрос на `/api/v1/orders/:id/push_subscription` с `{ subscription, platform: 'android' }`. При успехе (200): текст кнопки меняется на "[ ✓ Уведомления включены ]", `isLoading = false`.
    4. Если `'denied'`: `isLoading = false`, выводится мягкий toast-информер («Уведомления запрещены в настройках браузера»).
    5. При сетевой ошибке (400/500): `isLoading = false`, выводится toast об ошибке сети.
  - *TDD*: Написать тест с моками `Notification`, `ServiceWorkerRegistration` и `fetch`.

- [ ] **Шаг 6: Проверка сохраненного состояния при инициализации**
  - Given: Компонент монтируется, в localStorage уже существует `order_{id}_wallet_added = true` ИЛИ `Notification.permission === 'granted'`.
  - When: Завершается начальная инициализация компонента.
  - Then: Верхняя кнопка сразу рендерится в финальном состоянии ("✓ Карта добавлена" или "✓ Уведомления включены") без возможности повторного клика (disabled или измененный обработчик).
  - *TDD*: Написать тест на проверку начального рендера при заданных условиях localStorage/permissions.

## Стратегия тестирования
- **Фреймворк**: Vitest + React Testing Library (или Jest, в зависимости от текущего стека проекта).
- **Путь к файлам тестов**: 
  - `src/utils/__tests__/deviceDetect.test.ts`
  - `src/components/orders/__tests__/OrderStatusBottomBar.test.tsx`
- **Критические кейсы**:
  - **Edge cases**: Мимикрия UserAgent (iPadOS 13+ как MacIntel), работа в SSR-окружении (`typeof window === 'undefined'`).
  - **Асинхронность**: Корректная обработка состояний `isLoading` при задержке сети (mock `setTimeout` или `vi.advanceTimersByTime`).
  - **Ошибки сети**: Обработка HTTP 400 и 500 без краша приложения, корректный откат флага `isLoading`.
  - **Браузерные API**: Корректный мок `Notification.requestPermission`, `navigator.serviceWorker`, `window.location.href` и `localStorage`.

### Расхождение

Шаг 5: Android/Desktop Flow – WebPush подписка

Given: ОС = `'android'` или `'desktop'`, `Notification.permission !== 'granted'`.

When: пользователь разрешает уведомления и `Notification.requestPermission()` возвращает `'granted'`.

Then: должен быть инициализирован ServiceWorker, получена PushSubscription с VAPID key и продолжен существующий WebPush flow.

По факту: регистрация `/firebase-messaging-sw.js` завершается ошибкой из-за CSP ответа Service Worker: шаблон Service Worker использует `importScripts("https://www.gstatic.com/firebasejs/11.0.0/...")`, а глобальный `script-src` CSP не разрешает `https://www.gstatic.com`.

Факты:

- `app/views/shop/firebase_sw/show.js.erb:2-3` — Service Worker загружает Firebase SDK через `importScripts` с `https://www.gstatic.com`.
- `config/initializers/content_security_policy.rb:10-13` — глобальный `script-src` не содержит `https://www.gstatic.com`.
- `app/controllers/shop/firebase_sw_controller.rb:5-11` — endpoint `/firebase-messaging-sw.js` обслуживается отдельным контроллером, поэтому CSP может быть задана локально для этого ответа.

### Исправленный сценарий

- [ ] Шаг 5 (patch v1): Android/Desktop Flow – WebPush подписка

Given: ОС = `'android'` или `'desktop'`, `Notification.permission === 'granted'`.

When: пользователь запускает существующий WebPush flow.

Then:

1. Ответ `/firebase-messaging-sw.js` имеет локальную CSP, разрешающую фактически используемый `https://www.gstatic.com` в `script-src`.
2. ServiceWorker успешно регистрируется.
3. Существующий Firebase WebPush flow продолжает выполнение `getToken()` с существующим VAPID key и ServiceWorker registration.
4. При успешном получении токена существующая регистрация подписки продолжается без изменения backend-контракта.
5. Глобальная CSP проекта остаётся без расширения.
