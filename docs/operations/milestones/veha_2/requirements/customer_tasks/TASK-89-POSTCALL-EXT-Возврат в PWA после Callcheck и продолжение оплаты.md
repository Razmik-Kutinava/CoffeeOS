## Текст задачи (дословно) — Google Doc Spec

TASK_89-POSTCALL-EXT: Возврат в PWA после Callcheck и продолжение оплаты
Расширяет: docs/operations/milestones/veha_2/requirements/customer_tasks/TASK_89: Авторизация и регистрация PWA — Callcheck → SMS.md
Тип: дополнительная задача — новый пользовательский сценарий возврата из телефонного приложения в PWA
Бизнес-цель: пользователь, который покинул PWA для выполнения Callcheck-звонка, должен понимать, что делать после звонка, вернуться в исходный checkout без потери состояния и автоматически продолжить пользовательский flow до экрана оплаты и привязки карты.
1. Карта интеграций — затронуто / нет
Интеграции не изменяются
SMS.ru;
Callcheck;
/init_callcheck;
/check_status;
/verify_sms;
алгоритм регистрации MobileCustomer;
customer session;
refresh token.
Затрагивается
lifecycle PWA при переходе пользователя в телефонное приложение;
восстановление состояния активного Callcheck после возврата;
продолжение frontend auth flow;
переход после успешной регистрации/авторизации к экрану оплаты;
открытие PaymentMethodsSheet для привязки карты.
2. Карта компонентов
Затронутые компоненты
PhoneAuthWizard;
PhoneAuthCodeStep;
Callcheck cascade/state;
checkout host;
checkout lifecycle/state;
PaymentMethodsSheet — только в части автоматического открытия после успешной регистрации/авторизации.

Да.
Граница:
Эта задача:
Callcheck → переход пользователя в телефон → возврат в PWA → восстановление проверки → регистрация/авторизация → автоматический переход к оплате/привязке карты.

3. Текущее поведение — факт
По текущему пользовательскому сценарию:
Пользователь находится в checkout PWA.
Вводит номер телефона.
Запускает Callcheck.
Для выполнения звонка пользователь переходит из PWA в телефонное приложение.
После завершения звонка пользователь возвращается в PWA.
При возврате отсутствует достаточно очевидное продолжение пользовательского сценария.
Пользователь не должен понимать, нужно ли повторно нажимать кнопку звонка, ждать результата или выполнять другое действие.
После успешного Callcheck текущий frontend завершает auth flow, но автоматического перехода к экрану оплаты/привязки карты нет.
Backend-регистрация/авторизация после подтверждённого Callcheck уже является частью TASK_89 и не должна дублироваться в этой задаче.
4. Целевой пользовательский flow
Фиксируется единая последовательность:
Ввод телефона → Callcheck → телефонное приложение → возврат в PWA → проверка существующего Callcheck → регистрация/авторизация → экран оплаты → привязка карты.
4.1. Перед переходом в телефон
После запуска Callcheck пользователь должен получить понятное объяснение:
Позвоните на указанный номер
Выполните звонок с этого телефона. После завершения звонка вернитесь в приложение — проверка продолжится автоматически.
Должно быть однозначно понятно:
Позвонить → завершить звонок → вернуться в PWA.
Системный диалог ОС/браузера о переходе в другое приложение не контролируется PWA и не является частью UI этой задачи.
4.2. Пользователь покидает PWA
При переходе из PWA в телефон:
активная Callcheck-сессия сохраняется;
номер пользователя сохраняется;
checkout state сохраняется;
новая Callcheck-попытка автоматически не создаётся.
4.3. Пользователь возвращается в PWA
Возврат в PWA не считается успешным Callcheck.
После возвращения:
восстанавливается текущий auth flow;
используется существующая Callcheck-сессия;
выполняется проверка актуального статуса Callcheck.
4.4. Callcheck ещё выполняется
Если статус pending:
Пользователь видит состояние:
Проверяем номер
Проверяем результат звонка. Пожалуйста, подождите.
PWA продолжает polling существующего Callcheck.
Новая попытка звонка не создаётся только из-за возвращения пользователя в PWA.
4.5. Callcheck подтверждён
Если получен confirmed:
завершается существующий механизм регистрации/авторизации TASK_89;
устанавливается авторизованное состояние пользователя;
auth wizard завершается;
автоматически открывается PaymentMethodsSheet.
Пользователь не должен самостоятельно искать кнопку оплаты после успешной авторизации.
Целевой flow:
Callcheck confirmed → регистрация/авторизация → PaymentMethodsSheet → привязка карты.
4.6. Привязка карты
После автоматического открытия PaymentMethodsSheet пользователь продолжает существующий checkout flow и выполняет привязку банковской карты.
Эта задача не изменяет внутреннюю механику привязки карты.
4.7. Callcheck не подтверждён
Если существующая Callcheck-попытка окончательно не подтверждена:
Callcheck → SMS fallback
согласно TASK_89.
После успешного SMS-подтверждения действует тот же конечный flow:
регистрация/авторизация → PaymentMethodsSheet → привязка карты.
5. Scope
Разрешено
изменить UI состояния Callcheck перед переходом пользователя в телефон;
явно сообщить необходимость вернуться в PWA после звонка;
сохранять состояние активного Callcheck при уходе из PWA;
обрабатывать возврат PWA в foreground;
после возврата проверять статус существующей Callcheck-сессии;
продолжать polling при pending;
показывать пользователю состояние ожидания;
после confirmed продолжать существующий auth flow TASK_89;
после успешной регистрации/авторизации автоматически открыть PaymentMethodsSheet;
сохранить checkout state;
сохранить SMS fallback;
обработать повторный уход/возврат пользователя без создания новых Callcheck-попыток.
Для lifecycle-обработки использовать устойчивый механизм мобильного web, позволяющий обнаруживать возврат страницы в активное состояние.
Запрещено
создавать новый Callcheck только из-за возврата пользователя в PWA;
повторно инициировать звонок автоматически;
повторно регистрировать пользователя;
менять алгоритм регистрации из TASK_89;
менять поиск существующего MobileCustomer;
менять SMS fallback;
менять интеграцию SMS.ru;
менять расчёт суммы заказа;
менять состав заказа;
менять визуальный UI, относящийся к TASK-89-UI-EXT;
менять внутреннюю механику PaymentMethodsSheet;
требовать от пользователя вручную нажимать CTA оплаты после успешной регистрации/авторизации;
сбрасывать номер телефона при уходе в телефон;
сбрасывать checkout при возврате;
создавать отдельную авторизационную сессию при каждом возврате в PWA.
6. Gherkin
Subtask 1: объяснение перед звонком
Given пользователь ввёл корректный номер телефона
When запускается Callcheck
Then пользователь видит инструкцию выполнить звонок
And явно видит инструкцию после звонка вернуться в PWA.
Subtask 2: переход в телефон
Given Callcheck находится в состоянии ожидания
When пользователь переходит из PWA в телефонное приложение
Then активная Callcheck-сессия сохраняется
And номер телефона сохраняется
And checkout state сохраняется.
Subtask 3: возврат в PWA
Given существует активная Callcheck-сессия
When пользователь возвращается из телефонного приложения в PWA
Then текущий auth flow восстанавливается
And выполняется проверка существующей Callcheck-сессии
And новый Callcheck не создаётся.
Subtask 4: Callcheck pending
Given пользователь вернулся в PWA
And Callcheck имеет статус pending
Then пользователь видит состояние «Проверяем номер»
And polling существующей Callcheck-сессии продолжается
And новая попытка Callcheck не создаётся.
Subtask 5: Callcheck confirmed
Given пользователь вернулся в PWA
And Callcheck имеет статус confirmed
When PWA получает результат проверки
Then выполняется существующий механизм регистрации/авторизации TASK_89.
Subtask 6: автоматический переход к оплате
Given Callcheck подтверждён
And регистрация/авторизация успешно завершена
When auth flow завершается
Then PaymentMethodsSheet автоматически открывается
And пользователь продолжает checkout без дополнительного поиска кнопки оплаты.
Subtask 7: привязка карты
Given PaymentMethodsSheet автоматически открыта после успешной регистрации/авторизации
Then пользователь может продолжить существующий flow привязки банковской карты.
Subtask 8: Callcheck не подтверждён
Given Callcheck завершился без подтверждения
Then используется SMS fallback TASK_89.
Subtask 9: успешный SMS fallback
Given SMS fallback успешно завершён
And регистрация/авторизация успешно завершена
Then автоматически открывается PaymentMethodsSheet
And пользователь продолжает flow привязки карты.
Subtask 10: повторный уход и возврат
Given активная Callcheck-сессия ещё валидна
When пользователь несколько раз покидает и возвращается в PWA
Then используется существующая Callcheck-сессия
And новый init_callcheck только из-за lifecycle-события не выполняется.
