1. Жизненный цикл заказа (Order Management)
Система должна поддерживать не только «идеальный путь» продажи, но и реальные сценарии работы кофейни.

1.1. Статусы и переходы
**[В1] Shop:** корзина → mock-оплата → заказ `accepted` (имитация, `SHOP_SIMULATE_PAYMENT=1`).

**[В2] Shop (prod):** cash → `accepted`; card/sbp → `pending_payment` → редирект **Т-Банк** → callback → `accepted` + списание. **`SHOP_SIMULATE_PAYMENT=0`.**

**[В1] Barista POS:** создание заказа с оплатой (cash/card/sbp) → `accepted`; заказ привязан к `cash_shift_id`.

Целевые/расширенные статусы (полный цикл — позже):
Draft: Формирование корзины.

Pending / pending_payment: **[В2]** ожидание оплаты через **Т-Банк** (card/sbp) до callback.

Paid / accepted: Успешная оплата, запуск списания ингредиентов **[В1 — списание при accepted]**.

Cancelled: **[В1]** отмена бариста — **обязательная причина** (`order_cancel_reasons`), запись в `admin_audit_logs`; возврат на склад при статусе preparing.

1.2. Модификаторы и Комбо
Обязательные модификаторы: Выбор зерна или типа молока, без которого заказ невозможно закрыть.

Дополнительные опции: Сиропы, двойная порция, добавки.

Комбо-конструктор: Автоматический пересчет цены при добавлении в корзину набора (например, «Завтрак: Кофе + Сендвич»).

2. Работа в Offline-режиме (Business Continuity) — **Веха 3**
⚠️ В Вехах 1–2 POS работает только online. Offline — **В3** (не реализован).
POS-терминал (Rails+Hotwire) должен сохранять полную работоспособность при потере связи с бэкендом (Rails).

Локальный буфер: Все заказы сохраняются в локальную базу (IndexedDB) и помечаются статусом local_only.

Визуальная индикация: Бариста видит статус синхронизации (Зеленый/Желтый/Красный).

Синхронизация: При восстановлении связи заказы отправляются на сервер в порядке очереди с использованием drift_offset для корректного времени транзакции.

Идемпотентность: Каждый локальный заказ имеет уникальный client_uuid, чтобы исключить дубли при повторной отправке.

3. Складской учет и Движение товаров (Inventory)

**[В1] Реализовано (v0.1, упрощённо):**
- Списание по техкарте (`product_recipes`) при продаже: сервис `Inventory::OrderRecipeDeduction` (shop/barista) + DB-триггер при переходе заказа в `accepted`.
- Остаток в `ingredient_tenant_stocks` может уходить в **минус** — продажа не блокируется.
- Prep_kitchen: ручные движения — черновик `StockMovement` → подтверждение меняет остаток; stop-list, min_qty.
- Отмена заказа бариста (preparing) — возврат через `StockMovement` типа return.
- **Техдолг В1:** часть списаний при продаже идёт **без** строки `StockMovement` (прямой UPDATE остатка). Полный журнал «сначала движение» — **Веха 3**.

Целевая модель Event Sourcing (**Веха 3**): каждое движение — событие в `StockMovement`; приемка, waste, инвентаризация — по мере развития продукта.

**[В1] История отмен:** отмена заказа бариста только с `reason` → `admin_audit_logs` (`order_cancelled`). Полный анти-фрод (подозрительные правки, алерты) — **Веха 3**.

Целевое (**Веха 3**): Z-отчёт, **единая** дисциплина на всех каналах, запрет правок в закрытых чеках без следа. *(Гибрид смены В1–В2 — см. таблицу выше.)*

5. Раздел: Ролевая модель (Access Control)

**[В1]** В демо реализованы роли и панели (session-login, RBAC):

| Роль | Панель | Кратко |
|------|--------|--------|
| `uk_global_admin` | `/admin` (УК) | org, tenant, каталог, выдача доступов |
| `franchise_manager` | `/manager` | свои точки, read-only меню |
| `general_manager` | `/manager` | меню, цены, staff, склад точки |
| `shift_manager` | `/manager` | оперативка **текущей открытой** смены |
| `barista` | `/barista` | POS, своя смена, заказы |
| `prep_kitchen_manager` | `/prep_kitchen` | движения, stop-list, min_qty |
| `prep_kitchen_worker` | `/prep_kitchen` | просмотр, без мутаций |

**Клиент витрины** — без роли в системе: `/shop`, Shop API (`X-Shop-Api-Key` / same-origin CSRF). Заказ без `CashShift`.

Ниже — детализация **шести системных ролей** (коды — как в RBAC):

**1. УК — `uk_global_admin`**
* Горизонт: организация и сеть точек (platform scope).
* Панель: `/admin` (platform) — организации, точки (tenant), глобальный каталог, выдача доступов, онбординг точки.
* **[В1]** Разрешено: CRUD org/tenant, каталог УК, назначение ролей пользователям.
* **[В2]** Онбординг **3+ org × точки** из УК; карточка входов (URL витрины, модули, staff); **feature flags** по модулям tenant.
* **[В2]** UX: overlay skeleton при ответе API **>5 с** (barista/manager/shop).
* **[В1]** Запреты: POS баристы, `/manager` точки, `/prep_kitchen`, операции «на линии» смены.

**2. Франчайзи — `franchise_manager`**
* Горизонт: свои точки внутри организации.
* Панель: `/manager` (переключение между своими tenant).
* **[В1]** Разрешено: дашборд, просмотр меню точек (**без** изменения цен и PTS).
* **[В1]** Запреты: `/barista`, `/prep_kitchen`, `/admin`; PATCH цен/меню; POS и смены.

**3. Управляющий точки — `general_manager`**
* Горизонт: одна точка (текущий tenant в сессии).
* Панель: `/manager` — меню и цены (PTS), staff, склад точки, устройства, отчёты.
* **[В1]** Разрешено: редактирование меню/цен **своей** точки, staff, inventory manager.

**4. Менеджер смены — `shift_manager`**
* Горизонт: **текущая открытая** смена, одна точка.
* Панель: `/manager` — оперативные разделы (заказы/смены «сегодня»).
* **[В1]** Разрешено: оперативка открытой смены, смены/заказы без доступа к закрытой истории и «широким» отчётам.

**5. Бариста — `barista`**

* Панель: `/barista` — POS, личная `CashShift` (open/close).

6. Защита от деструктивных действий (Negative Logic)
Блокировка «будущего»: Запрет на ввод дат документов из будущего.

Payload Validation: Ограничение размера загружаемых фото/логотипов для предотвращения перегрузки БД.

Security Lockdown: При попытке несанкционированного доступа к данным другого тенанта (Tenant Breach) происходит мгновенная блокировка сессии и запись в аудит-лог.

7. UI/UX Реактивность и системные состояния
Интерфейс должен оперативно информировать пользователя о смене режимов работы системы, чтобы избежать паники и ошибок ввода.

7.1. Режим Offline (Потеря связи)
Индикация: При обрыве соединения в верхней части экрана (Status Bar) появляется неблокирующий индикатор «Работа в оффлайн-режиме».

Обратная связь: Система выводит разовое уведомление (Toast): «Связь потеряна. Все данные сохраняются локально. Работайте в обычном режиме».

Ограничения: Функции, требующие связи (например, баланс бонусов в реальном времени), переходят в состояние «Недоступно» с пояснением «Нужен интернет».

7.2. Режим Синхронизации (Back Online)
Процесс: При восстановлении связи индикатор меняется на «Синхронизация данных...» (Spinner).

Завершение: После успешной отправки всех локальных заказов индикатор исчезает или становится зеленым.

Конфликты: Если заказ не может быть принят сервером, бариста получает уведомление: «Ошибка синхронизации заказа №XXX. Направлено администратору».

7.3. Критические ошибки и Безопасность
RLS Breach (Нарушение прав): Если система детектирует попытку доступа к чужим данным, интерфейс должен мгновенно блокироваться с сообщением: «Ошибка авторизации. Сессия завершена» и принудительным выбросом на экран логина.

Database Timeout: Если запрос к базе длится более 5 секунд, UI показывает «скелетон» или лоадер, чтобы пользователь не нажимал кнопку повторно.
