# TASK_93-J — Блок J: Push / уведомления / worker

Зонтик: **TASK_93** / `#93` — Critical path hardening.  
Этот SBR-прогон: **только TASK_93-J**.

Title чата: `Задача 93 — Critical path hardening (блок J)`.

---

## 1. Зачем

| Проблема | Сейчас |
|----------|--------|
| **J1** | `Barista::OrderStatusUpdateService` после txn синхронно зовёт `GuestOrderBroadcaster` → **sync** `AppleWallet::PassUpdater` (APNs) + push notifier. В `PaymentStatusUpdater#with_lock` тоже `GuestOrderBroadcaster` — HTTP push/APNs может держать lock/запрос |
| **J1b** | `ReadyPushJob` для FCM делает `SendPushNotificationJob.perform_now` (ок в job, но wallet sync в broadcaster на POS — плохо) |
| **J2** | `FcmClient#fetch_access_token!` на **каждый** deliver, без cache; мёртвые токены (UNREGISTERED) не чистятся |
| **J3** | `SMS_GRACE = 15.s` и `set(wait: SMS_GRACE)` — **одинаково** → гонка expiry grace vs запуск cascade (#82) |
| **J4** | Worker на Fly часто stopped; T‑Bank уже `perform_now` + fallback; cascade/push на `perform_later` могут не бежать без `SOLID_QUEUE_IN_PUMA` / отдельного worker — runbook неполный |

## 2. Цель блока

**Смена статуса / webhook не ждут APNs/FCM; OAuth FCM кэшируется + мёртвые токены чистятся; каскад ready→SMS без race grace; очередь гарантированно обрабатывает callback/cascade (runbook + код).**

## 3. Scope / Non-scope

**В scope (J1–J4):**
- Вынести APNs/Wallet/FCM с request path и из `payment.with_lock`
- `FcmClient` token cache + invalidate dead tokens на customer
- `SMS_GRACE` vs `wait:` — развести с буфером
- Runbook Solid Queue / `SOLID_QUEUE_IN_PUMA` + довести hot-path (cascade/ready push / tbank) чтобы не терялись

**Вне scope:** UI WebPush recovery (#90), текст SMS (C), Redis Attack (I), склад (A), полный отдельный Fly `worker` process (можно рекомендовать в L).

## 4. Продуктовые правила (SPEC до RED)

| Правило | Решение |
|---------|---------|
| **R1** | После commit статуса: Cable broadcast можно sync (быстро); **APNs / PassUpdater / FCM deliver — только `perform_later`** (или уже существующие jobs). Broadcaster **не** вызывает PassUpdater sync |
| **R2** | `PaymentStatusUpdater`: внутри `with_lock` только DB; broadcaster/push — **после** lock (reload + enqueue) |
| **R3** | `ReadyPushJob` / `SendPushNotificationJob`: FCM в job; `perform_now` внутри ReadyPush допустим только если ReadyPush уже async |
| **R4** | OAuth access_token: cache в Redis/SolidCache с TTL ~50 min (`expires_in` от Google − skew) |
| **R5** | FCM response `UNREGISTERED` / `INVALID_ARGUMENT` token → `customer.update!(push_token: nil, push_enabled: false)` (или mark) + log |
| **R6** | Cascade: `wait: SMS_GRACE + BUFFER` (например **+5s**) **или** grace = wait − buffer; job в начале `sleep`/check `!in_sms_grace?` с коротким requeue. Зафиксировать одно: рекомендация **`wait = SMS_GRACE + 5.seconds`**, grace без изменения 15s |
| **R7** | Runbook: на Fly либо `SOLID_QUEUE_IN_PUMA=true` на web, либо отдельный worker process always-on; checklist в artifacts |
| **R8** | Критичные jobs (TbankCallback, OrderReadyCascade, ReadyPush): стратегия «web perform_now fallback» **или** guaranteed Puma plugin — довести единообразно в доке + тестах контракта |
