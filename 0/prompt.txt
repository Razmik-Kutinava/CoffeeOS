# Задача: Хранение и отображение фискальных чеков в личном кабинете

**Бизнес-цель:** обеспечить получение фискальных данных от кассы «Чеки Т-Бизнес», их надежное хранение и отображение пользователю в истории заказов PWA. Фискальный чек должен появляться в карточке заказа после фискализации оплаты, возврата или закрытия предоплаты, при этом повторная доставка уведомления от Т-Банка не должна создавать дубликаты.

## 1. Связь с картой интеграций

Затронутые сервисы из @INTEGRATIONS.md: Т-Банк Интернет-эквайринг / «Чеки Т-Бизнес».

Новый/изменяемый контракт: входящее HTTP(S)-уведомление о фискализации от Т-Банка.

Точка входа: NotificationURL, настроенный в терминале интернет-эквайринга (существующий эндпоинт `/callbacks/tbank`, различение типа уведомления — по полю Status).

Identity Mapping: внешний PaymentId / OrderId должен быть сопоставлен с внутренним платежом/заказом. Использовать существующий внутренний mapping, не создавать параллельную идентификацию заказа.

Фискальные данные: сохраняются только поля, фактически присутствующие в согласованной схеме уведомления: ссылка на чек, ФН/ФД/ФП и тип фискальной операции.

Raw payload: сохраняется исходный JSON уведомления для диагностики и возможности последующего разбора новых полей.

Обработка ошибок: невалидное уведомление не должно создавать фискальную запись; временная недоступность backend должна позволять корректно обработать повторную доставку после восстановления.

Ретраи: успешное уведомление должно получать HTTP 200 с телом OK; повторная доставка должна быть идемпотентной.

Смежные модули, которые НЕЛЬЗЯ ломать: существующая обработка платежных уведомлений, checkout/payment flow, история заказов, возвраты, авторизация PWA, существующий механизм сопоставления PaymentId/OrderId.

## Изменения в связке: Т-Банк Интернет-эквайринг — фискализация

Точки входа: NotificationURL backend-приложения — существующий эндпоинт `/callbacks/tbank`, обрабатывающий отдельный тип уведомлений о фискализации по полю Status.

Identity Mapping: внешний PaymentId/OrderId сопоставляется с существующим внутренним payment/order. Фискальная запись не создается без успешного mapping на внутренний заказ.

Handling Errors: валидное уведомление после успешного сохранения получает HTTP 200 и тело OK (включая исправленные платёжные ветки, см. Subtask 9а). Повторная доставка должна быть идемпотентной. При временной недоступности backend обработка выполняется при последующем retry Т-Банка. Уведомление с неизвестным заказом не привязывается к другому заказу и отправляется в существующий механизм диагностики.

Security: входящий Token обязательно валидируется до записи данных. Секреты/ключи интеграции хранятся в .env/существующем secret storage и не передаются в PWA.

Stored Data: сохраняются только подтвержденные поля фискального payload: ссылка на чек, доступные ФН/ФД/ФП, тип операции, время получения, внешний идентификатор и raw JSON.

Idempotency: повторное уведомление не должно создавать новую запись. Для этого используется уникальный внешний идентификатор или согласованная комбинация полей.

PWA Contract: API истории/деталей заказа возвращает пользователю только необходимые для отображения данные фискального чека.

Recovery: при отсутствии notification предусматривается ручная процедура восстановления через доступный архив уведомлений Т-Банка; детали процедуры фиксируются после подтверждения актуального процесса со стороны Т-Банка.

Out of scope: запрос фискального чека через API кассы по PaymentId, генерация собственного QR по ФН/ФД/ФП, копирование документации Т-Банка в проект.
