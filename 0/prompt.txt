# Задача-2: Фикс промо-цены 11₽: чтение суммы из конфига

Бизнес-цель: Устранить расхождение между конфигурацией промо и фактической суммой платежа. Цена промо должна определяться настройкой конкретной точки в `point_campaign_settings`, а не захардкоженной константой, чтобы отображаемая и реально списываемая суммы всегда совпадали.

## 1. Связь с картой интеграций
- **Затронутые сервисы из `@INTEGRATIONS.md`:** Нет новых интеграций.
- **Смежные модули, которые НЕЛЬЗЯ ломать:** `Payments::TbankAdapter`, `card_binding_attempts`, velocity, antifraud-логика, существующая логика `is_growth_event` и дедупликации промо.
- **Изменение внешних контрактов:** Нет. `docs/integrations/*.md` не изменяется.

## 2. Разрешенный и Запрещенный Scope
- **Разрешено менять/создавать:**
  - `app/services/payments/growth_promo.rb` — чтение `promo_amount_rub` в `price!` и `charge_amount`;
  - `app/services/platform/point_campaign_settings_sync.rb` — только при необходимости консолидации дефолтного значения;
  - `app/controllers/shop/api/user_cards_controller.rb` или фактический путь текущей реализации `Shop::Api::UserCardsController` — синхронизация `amount_rub` с источником `charge_amount`;
  - тесты `growth_promo.rb`;
  - тесты `Shop::Api::UserCardsController`.
- **Строго запрещено менять:**
  - структуру `point_campaign_settings`;
  - миграции БД для `point_campaign_settings`;
  - УК-форму создания/редактирования точки;
  - `card_binding_attempts`;
  - velocity;
  - antifraud-логику;
  - `Payments::TbankAdapter`;
  - `subscription_plans`;
  - `subscriptions`;
  - любые работы по оформлению или billing подписки;
  - внешние интеграционные контракты.

## 3. Сценарии и Чек-лист (Gherkin)

- [ ] **Subtask 1: Добавить failing-тест на нестандартную промо-цену**
  - Given: Для точки X в `point_campaign_settings.config["promo_amount_rub"]` задано `15`.
  - When: Рассчитывается сумма промо-платежа для гостя с включённым чекбоксом.
  - Then: Тест ожидает сумму `15₽` и фиксирует текущее падение из-за использования `11₽` из константы.

- [ ] **Subtask 2: Перевести `price!` на чтение промо-цены из конфигурации точки**
  - Given: Для точки X в конфиге задано `promo_amount_rub = 15`.
  - When: Вызывается `price!`.
  - Then: Метод возвращает `15₽`, полученные из `point_campaign_settings.config`.

- [ ] **Subtask 3: Перевести `charge_amount` на тот же источник промо-цены**
  - Given: Для точки X в конфиге задано `promo_amount_rub = 15`.
  - When: Рассчитывается сумма фактического списания.
  - Then: `charge_amount` возвращает `15₽`, совпадающие с `price!`.

- [ ] **Subtask 4: Реализовать единый fallback для отсутствующего `promo_amount_rub`**
  - Given: В `point_campaign_settings.config` отсутствует ключ `promo_amount_rub`.
  - When: Рассчитывается промо-цена.
  - Then: Используется единый дефолт `11₽` из одного источника, без дублирующих констант.

- [ ] **Subtask 5: Удалить дублирование дефолтной промо-цены**
  - Given: В кодовой базе существуют `PointCampaignSetting::DEFAULT_PROMO_AMOUNT_RUB` и `Payments::GrowthPromo::AMOUNT_RUB` со значением `11`.
  - When: Реализуется единый источник дефолтной суммы.
  - Then: Расчёт промо-цены использует один источник дефолта, а дублирующая константа не используется.

- [ ] **Subtask 6: Добавить тест на fallback 11₽**
  - Given: Конфиг точки не содержит `promo_amount_rub`.
  - When: Выполняется расчёт промо-платежа.
  - Then: `price!` и `charge_amount` возвращают `11₽`.

- [ ] **Subtask 7: Синхронизировать `amount_rub` API карт с расчётом списания**
  - Given: Для точки X `promo_amount_rub = 15`.
  - When: `Shop::Api::UserCardsController` формирует ответ для фронта.
  - Then: `amount_rub = 15` и используется тот же источник, что и при фактическом списании.

- [ ] **Subtask 8: Добавить API-регрессионный тест для нестандартной цены**
  - Given: Для точки X в конфиге установлено `promo_amount_rub = 15`.
  - When: Фронт запрашивает данные через `Shop::Api::UserCardsController`.
  - Then: В ответе `amount_rub = 15`.

- [ ] **Subtask 9: Проверить стандартное поведение промо**
  - Given: Для точки используется дефолтная конфигурация без ручного изменения суммы.
  - When: Гость проходит стандартный промо-флоу.
  - Then: Сумма списания и `amount_rub` API остаются `11₽`.

- [ ] **Subtask 10: Проверить growth-событие при нестандартной цене**
  - Given: Для точки задана нестандартная промо-цена и платёж успешно завершён.
  - When: Обрабатывается успешный промо-платёж.
  - Then: `is_growth_event = true`, а существующая дедупликация по `phone`/`method_hash` продолжает работать независимо от суммы.

- [ ] **Subtask 11: Выполнить regression-прогон growth/one-click зоны**
  - Given: Изменён источник промо-цены, но остальная платёжная логика не менялась.
  - When: Запускается полный существующий тест-сьют growth/one-click.
  - Then: Все связанные тесты проходят без регрессий.

- [ ] **Subtask 12: Выполнить live-проверку на тестовой точке**
  - Given: На тестовой точке изменён `promo_amount_rub` через существующий конфигурационный механизм.
  - When: Выполняется промо-флоу с оплатой.
  - Then: Реальная сумма списания соответствует значению из конфига; после проверки стандартное значение не нарушено.
