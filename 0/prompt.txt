# SBR: Jobs / очередь — не доверять «голому» PK без tenant-контекста

**ID:** `V3-SEC-JOB-TENANT-GUC`  
**Источник:** security backlog (ops-граница + defense in depth)  
**Тип:** security / background jobs / RLS  
**Приоритет:** medium (код) + **high если queue БД торчит наружу** (ops)  
**Ветка:** `develop`  
**Канон:** `@spec-build-review.mdc` · `@coffeeos-core` (tenant/RLS)  
**Якоря:**
- `docs/product/security/phase_3_tenant_rls/RLS_TENANT_AUDIT.md` § Background jobs  
- `config/environments/production.rb` → `queue_adapter = :solid_queue`  
- `app/jobs/**/*.rb`  
- `app/jobs/application_job.rb`  
- `fly.toml` (`worker = ./bin/jobs`)

---

## 1. Проблема простыми словами

HTTP-запрос витрины/кассы обычно делает: «я точка X» → Postgres RLS режет чужие строки.

Фоновые job’ы часто делают иначе:

1. В очередь кладут `order_id`  
2. Worker: `Order.find_by(id: order_id)` **без** `SET LOCAL app.current_tenant_id`  
3. Дальше шлёт пуш/SMS/broadcast

Это **нормально**, пока задачи в очередь кладёт **только наш код** (после webhook/подписи/своего сервиса).

Плохо, если кто-то может **подложить задачу в очередь** (доступ к queue DB / админке очереди / скомпрометированный worker). Тогда «обработай заказ UUID» выполнится без проверки сессии гостя.

Это **не дыра в `/shop/api`**. Это: *очередь = служебный вход*.

**Уточнение по стеку CoffeeOS:** ActiveJob в production = **Solid Queue** (отдельная DB `queue`), не Sidekiq. Исторически в доках/ТЗ заказчика писали «Sidekiq» — для агента значит **фоновые job’ы**, адаптер смотреть в `production.rb`.

---

## 2. Цель / DoD

### A. Ops (обязательно задокументировать + проверить)

1. Queue DB / Solid Queue **не** доступны из интернета.  
2. Нет публичного UI очереди без auth УК.  
3. Runbook: кто имеет доступ к `fly console` / DB queue, что считается инцидентом.  
4. Запись в security doc: «queue = trusted; compromise = high».

### B. Code defense in depth (основной SBR-код)

1. Общий хелпер: после загрузки `Order` (или сущности с `tenant_id`) job **ставит GUC** на `order.tenant_id` (+ `Current.tenant_id`) на время работы.  
2. Order-scoped job’ы из аудита переведены на хелпер (список ниже).  
3. Job **не** принимает «произвольный tenant_id от клиента HTTP» без связи с записью — tenant берётся из найденной записи.  
4. Тесты: job с order точки A не пишет/не читает «как будто» точка B без GUC там, где RLS включён на роли теста.  
5. Обновить `RLS_TENANT_AUDIT.md`: было OK(queue internal) → FIXED defense-in-depth.

**Не цель:** выкинуть PK lookup; переписать все job’ы мира; внедрять Redis/Sidekiq; `fly deploy` без апрува.

## 3. Acceptance Criteria

### AC-1 — Хелпер

Существует что-то вроде:

`ApplicationJob#with_order_tenant!(order)`  
или `Rls::JobTenantContext.with(order)` / `ApplicationRecord` helper  

Внутри transaction/`connection`:
- `Current.tenant_id = order.tenant_id`
- `SET LOCAL app.current_tenant_id = …` (quote как в project rules)
- optional `app.current_user_id` = nil / system
- `ensure` сброс Current

### AC-2 — Order-scoped jobs используют хелпер

Минимум обернуть (из аудита + grep):

| Job | Сейчас |
|-----|--------|
| `Barista::BroadcastOrderBoardJob` | `Order.find_by(id:)` |
| `Shop::ReadyPushJob` | `Order.find_by(id:)` |
| `Shop::OrderReadyCascadeJob` | `Order.find_by(id:)` |
| `SendOrderReceiptEmailJob` | через OrderEmail → order |
| `Shop::SendPushNotificationJob` | notification → tenant |
| `Payments::TbankCallbackJob` | найти payment/order → GUC по tenant заказа |

`BroadcastTvColumnsJob` уже с `tenant_id` — сверить, что GUC тоже ставится (или оставить scoped `where(tenant_id:)` + GUC).  
`StuckPaymentsCheckJob` / `TelegramAlertJob` — global by design; в audit пометить **OK intentional**, не ломать.

### AC-3 — Enqueue только из доверенного кода

Не добавлять публичный HTTP «запусти job по order_id» без auth.  
Проверить grep: нет контроллера, который `perform_later(params[:order_id])` без ownership (если найдётся — fix или ISSUES).

### AC-4 — Ops checklist в doc

Новый короткий runbook **или** секция в `DEVICE_TOKENS`/`RLS_TENANT_AUDIT`:

- Solid Queue DB только private  
- worker process только внутри Fly  
- инцидент: подозрение на forge job args → ротация DB creds + audit `solid_queue_jobs`

### AC-5 — Тесты

1. Unit/job test: после `perform`, внутри блока GUC = tenant заказа (можно читать через `SHOW app.current_tenant_id` / helper).  
2. Regression: ready cascade / broadcast smoke local (существующие job tests, если есть — не красные).  
3. Негатив (опционально MVP+): подсунуть order_id другой точки — job либо no-op, либо работает только в tenant записи (не «переключает» на чужой GUC из args).

| Слой | Результат |
|------|-----------|
| Ops | Очередь не торчит; runbook есть |
