# TASK_93-D — Блок D: История заказов / ЛК список

Зонтик: **TASK_93** / `#93` — Critical path hardening.  
Этот SBR-прогон: **только TASK_93-D**.

Title чата: `Задача 93 — Critical path hardening (блок D)`.

---

## 1. Зачем

`GET /shop/api/orders/history` считает:

```ruby
per_page = [ [ params[:per_page].to_i, 1 ].max, 50 ].min
```

Без `per_page` → `.to_i` = **0** → `max(0,1)` = **1** → в ответе максимум **один** заказ.

Клиенты без param:
- `PersonalAccount.svelte` → `api("/orders/history")`
- `Orders.svelte` → `api('/orders/history?today=1')` («Заказы за сегодня»)

`shopAccountOrders.js` шлёт `per_page=20` — ок, но основные экраны ЛК/сегодня — нет.

## 2. Цель блока

Списки показывают **нормальную пачку** заказов (default 20–50), не один заказ по умолчанию.

## 3. Scope / Non-scope

**В scope (D1–D3):**
- `Shop::Api::OrdersController#history` — default `per_page`
- Соседние list с тем же антипаттерном `params[:per_page].to_i` без default (если найдутся в shop API orders)
- Клиенты: `PersonalAccount.svelte`, `Orders.svelte`, `shopAccountOrders.js` — согласованный default
- Тесты D3

**Вне scope:** active orders sheet, Quick Repeat, пагинация UI «load more» (можно оставить page=1), A/B/C, deploy.

## 4. Продуктовые правила

| Правило | Решение |
|---------|---------|
| **R1** | Default `per_page` = **20** (канон; max по-прежнему **50**) |
| **R2** | Явный `per_page` от клиента уважается в диапазоне 1..50 |
| **R3** | `per_page` пустой / `"0"` / мусор → default **20**, не 1 |
| **R4** | `today=1` фильтр без изменений; меняется только размер страницы |
| **R5** | Клиенты без param полагаются на серверный default; `shopAccountOrders` может продолжать слать 20 |

## 6. Не ломать

1. История только своего `customer_id` + tenant.  
2. `today=1` — только заказы с сегодня.  
3. Гость без session → `[]`.  
4. Изоляция tenant (существующий test).  
5. `active` endpoint — не ломать окно ACTIVE_ORDERS.

## 7. Матрица приёмки D1–D3 ↔ тесты

Блок D закрыт только если **все** T-D* PASS.

### D1 — Серверный default

| ID | Тест | Arrange | Assert |
|----|------|---------|--------|
| **T-D1a** | `history without per_page returns default page size` | session customer + **≥3** mobile orders | `GET /orders/history` **без** per_page → `json.length == 3` (или min(3, default)); **не** 1 |
| **T-D1b** | `history blank/zero per_page uses default not one` | ≥3 orders; `per_page=` или `per_page=0` | length > 1 (ожидаемо 3 / default) |
| **T-D1c** | `history per_page capped at 50` | при желании 51+ orders; `per_page=999` | length ≤ 50 |
| **T-D1d** | `history respects explicit per_page=2` | ≥3 orders; `per_page=2` | length == 2 |

Реализация default (пример для GREEN):

```ruby
raw = params[:per_page].presence&.to_i
per_page = raw.nil? || raw < 1 ? 20 : [ raw, 50 ].min
```

### D2 — Клиент согласован

| ID | Тест / проверка | Assert |
|----|-----------------|--------|
| **T-D2a** | `shopAccountOrders` default `perPage \|\| 20` | остаётся 20; не слать 1 |
| **T-D2b** | PersonalAccount / Orders | либо без param (сервер 20), либо явный `per_page=20`; **не** `per_page=1` |
| **T-D2c** | (опционально) оба экрана используют `fetchAccountOrderHistory` | один клиентский путь — предпочтительно в GREEN |

Если нет JS runner — DoD: code review + T-D1a гарантирует, что текущие вызовы без param уже чинятся сервером. В REVIEW — grep: нет `per_page=1` в frontend shop orders.

### D3 — Главный приёмочный сценарий

| ID | Тест | Assert |
|----|------|--------|
